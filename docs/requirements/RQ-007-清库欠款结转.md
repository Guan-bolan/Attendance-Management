# RQ-007 清库时的欠款结转（期初余额）

状态：**实施中**（2026-11-13 回写状态：代码已落地，见下「实施现状」；原「草案 v1」的 U1–U3 三个待定项已由实施答案锁定）
日期：2026-11-11（2026-11-13 补「实施现状」段）
提出人：YG

---

## 背景

YG 的真实场景：

> 上一年账目已经算清了，但现在没钱发工资。下一年考勤又开始，我想清库，不影响这一年。

**现在的设计会把这笔欠款清掉**：

```
2026 年：张伟该发 100,000，已发 0 → 结余 100,000（欠他）
清库 2026：删掉 2026 的考勤 → 累计应发 = 0，累计已发 = 0 → 结余 = 0
          ↑ 欠的 10 万凭空消失
```

而且清库闸门①（期间净额 ≠ 0 就拦）会**直接拒绝清库** —— 想清也清不了，两头堵死。

## 重要口径：账期按**农历年（春节）**算

YG 2026-11-11 明确：

> 我们都是按照农历年，也就是春节算。一般都是春节算清本年的账，**无论结不结得清楚**。

含义：

1. **「本年」= 从今年春节到明年春节前一天**，不是 1-1 到 12-31
   （例：2026 农历年 ≈ `2026-02-17 ~ 2027-02-05`；具体日期见下表）
2. **春节时结算**，结不清就结转（这正是本需求要解决的）
3. 归档 / 清库的区间由用户自选，但界面**应提供「按春节年」快捷**，不必每年手填两个日期
4. **结余算法不受影响**（它按"今天"算，与区间无关）；受影响的只是归档/清库的**区间边界**与结转的 `source_from/source_to`

内置春节日期表（公历，用于快捷）：

| 农历年 | 春节 | 区间 |
|---|---|---|
| 2024 | 2024-02-10 | 2024-02-10 ~ 2025-01-28 |
| 2025 | 2025-01-29 | 2025-01-29 ~ 2026-02-16 |
| 2026 | 2026-02-17 | 2026-02-17 ~ 2027-02-05 |
| 2027 | 2027-02-06 | 2027-02-06 ~ 2028-01-25 |
| 2028 | 2028-01-26 | 2028-01-26 ~ 2029-02-12 |
| 2029 | 2029-02-13 | 2029-02-13 ~ 2030-02-02 |
| 2030 | 2030-02-03 | 2030-02-03 ~ 2031-01-22 |

> 表外年份：手填日期即可，**不引入农历库**（一个依赖换来每年一次的便利，不值）。表的实现要在一处（`shared`），界面与结转共用。

## 做什么

**清库时把未结清的金额「结转」下来**（会计上的期初余额 / carry-forward）。

### 1. 新增结转表（迁移 011，纯加法）

```sql
CREATE TABLE carryovers (
  id          INTEGER PRIMARY KEY,
  worker_id   INTEGER NOT NULL REFERENCES workers(id),
  amount_cents INTEGER NOT NULL,        -- 正 = 欠工人；负 = 工人欠（超发）
  source_from TEXT NOT NULL,            -- 来源区间起（清库的那段）
  source_to   TEXT NOT NULL,            -- 来源区间止
  note        TEXT,
  created_at  TEXT NOT NULL,
  reversed_by INTEGER NULL REFERENCES carryovers(id)  -- 冲销指向（只增不改）
);
CREATE INDEX idx_carryovers_worker ON carryovers (worker_id);
```

### 2. 结余公式加一项

```
还欠多少 = 结转合计 + 累计应发 − 累计预支 − 累计已发
```

- 结转合计 = 该工人所有结转记录的净额（含冲销的负数）
- 结转**不受区间影响**（它是存量，和"截至今天"同性质）
- 结转**计入 `balanceBoard` 的行集合**：只有结转、没考勤没预支没发放的工人也要出现在表里

### 3. 清库行为改变

闸门① 从「**硬拦**」改成「**提示 + 结转**」：

- 期间净额 ≠ 0 时，弹窗显示「这 N 人还有未结清的钱，清库后会转成上期结转保留」，列出每人金额
- 用户勾确认 → 清库，同时**为每个净额 ≠ 0 的工人生成一条结转记录**（`source_from` / `source_to` = 被清掉的区间）
- 净额 = 0 的人不生成结转（避免垃圾行）
- 结转记录**写进档案 manifest**（`clearance` 里已有每人四数，再加每人结转金额）

### 4. 界面

- 结余表的「看明细」展开区多一行：`上期结转 100,000.00（来自 2026-02-17 ~ 2027-02-05）`
- 清库弹窗：把「净额 ≠ 0 就拦住」的文案改成「会结转」的文案 + 逐人金额
- 结转来源可追溯：界面上能点开看"这笔结转是哪次清库带过来的"
- **归档 / 清库的时间范围加「按春节年」快捷**（读 `shared` 里的春节表；选哪年就填成 `[该年春节, 下一年春节前一天]`）

### 5. 结转只增不改

记错了用**冲销**（记一条反向结转），不真删——与预支、发放同一套哲学。

## 不做什么

1. 不做「手工新增结转」（只能由清库自动生成，避免伪造期初）
2. 不做「跨工人的结转合并」
3. 不做「结转按区间统计」（结转是存量，区间语言对它无意义）
4. 不改工资表（工资表看的是区间应发，与结转无关）
5. 不改月度汇总
6. **不加"必须等春节后才许清上一年"的日期检查**（YG 2026-11-11 明确：用户自己知道什么时候该清）。程序只保证「清掉的那段、未结清的金额会结转下来」，不管你什么时候清、清的是哪一段

## 验收标准

- [ ] **1** 造 2026 农历年数据（`2026-02-17 ~ 2027-02-05`）：张伟应发 100,000、已发 0 → 结余 100,000
- [ ] **2** 归档该区间 → 点清库：弹窗显示「张伟 未结清 100,000，清库后转为上期结转」；勾确认后清库成功
- [ ] **3** 清库后主库：该区间的考勤没了，`carryovers` 多一条（张伟 · 100,000 · 来源 `2026-02-17 ~ 2027-02-05`）
- [ ] **3b** 归档 / 清库的时间范围有「**按春节年**」快捷：选「2026」→ 自动填 `2026-02-17 ~ 2027-02-05`；选「2027」→ `2027-02-06 ~ 2028-01-25`
- [ ] **4** 结余表：张伟「还欠多少」仍显示 **100,000**（不是 0）；展开明细能看到「上期结转 100,000.00（来自 2026…）」
- [ ] **5** 录 2027 年考勤：张伟挣 50,000 → 还欠 = 100,000 + 50,000 = **150,000**
- [ ] **6** 发 60,000 → 还欠 = 150,000 − 60,000 = **90,000**
- [ ] **7** 结转冲销：记一条 −100,000 的冲销结转 → 还欠 = 90,000 − 100,000 = **−10,000**（负数标红，说明超发了）
- [ ] **8** 结转随档案走：档案包里含结转记录；从档案恢复后欠款仍在
- [ ] **9** 净额 = 0 的人清库后**不生成**结转行（查库确认）
- [ ] **10** 结转合计参与 `balanceBoard` 的行集合：只有结转、没任何其它记录的工人也出现在结余表里
- [ ] **11** 界面不出现「分钟」；金额走 `shared/calc.ts`

## 约束

- 新增迁移只许加法；`carryovers` 不改任何既有表
- 结转**只增不改**（冲销留痕）
- 结余只有一处实现（`repo/balance.ts`），结转也接在那里
- 清库闸门顺序不变（②有副本 → ③副本是新的 → ①期间净额），只把 ① 的动作从「拒绝」改成「提示 + 结转」
- 结转记录必须写进档案 `manifest`

## 已知风险

1. **结转会让"清库后数字归零"这个直觉失效**：清库后还欠多少不变（因为转下来了）。这是对的，但界面要说明「清库 ≠ 抹账」。
2. **结转与档案的关系**：如果清库后又从档案合并回来同一段数据，那段考勤回来了，但结转还在 → **会重复计算**。**处置（2026-11-13 补注，以 `docs/decisions.md` D-038 与 `services/archive.ts` 的注释为准）**：合并时**分三种情形**——① 同来源区间的主库结转：跳过并进冲突清单（硬闸）；② 本次合并**真的插入了**该区间的考勤 → 在同一个事务里**自动插一条负数结转把它冲销掉**（根治「考勤回来了、欠款还在」的双算；文案改成「已自动冲销」，不再劝人手动处理）；③ 那几条考勤**主库本来就有**（本次一条都没插）→ 不自动冲销，只回 `carryoverOverlapWarnings` 让人处置。**原「只跳过 + 提示人工处理」的说法只覆盖 ① 与 ③**，② 是后加的实现（YG 实机踩过），本轮审计发现文档没跟上，故在此补注。
3. **多次清库会累积多条结转**：界面上要能按来源区间分开显示，不能只给一个总数。
