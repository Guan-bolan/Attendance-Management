## 背景

换电脑、硬盘坏了、系统重装，是这台软件唯一真正的「末日场景」。现在只有两条路：

1. **整目录冷备**（`docs/DELIVERY.md` §4 第 3 条）：关掉软件、把整个 `Documents\Attendance\` 手工拷到移动硬盘。要用户自己知道该拷哪个目录、必须在关软件后拷、还容易只拷了 `app.db` 漏掉 `photos\`（照片不在库里，库只是索引）。
2. **数据库快照**（维护页）：只有几 MB 的 `app.db`，**不含照片**。换台机恢复出来是「有账无图」——记录都在，点开任何一条都是缺照片。

缺的是「一键把整库（含照片）打成一个包，换台新电脑一键恢复」这个出口。

## 做什么

1. **立即备份**
   - 弹保存对话框 → 选路径与文件名 → 生成一个 zip。
   - 库的部分必须 `VACUUM INTO` 出一致性副本（先 `checkpoint`），**不许裸拷 `app.db`**。
   - `photos\` 按相对路径进包，**流式**（`archiver.file()` 排队，不许把图片读进内存）。
   - `archives\` 按 U6 收三件本体，跳过 `backups\` 与 `.superseded-*`。
   - 包根放 `manifest.json`：格式版本、生成时间、软件版本、schema 版本（迁移常量）、三个源目录绝对路径、**U8 的两组条数**、`app.db` 字节数、照片总字节。
   - 进度可见、可取消；失败不许留下半成品 zip。
   - 备份前**停收件箱 watcher**，结束后恢复；若库内照片行与磁盘文件数不一致，**拒绝备份**并报出差异（U7）。

2. **恢复数据**
   - 弹打开对话框 → 选一个 zip。
   - **校验**（任一不过就拒绝，当前数据一个字节都不动）：zip 结构完整、`manifest.json` 可解析、格式版本受支持且不高于当前软件、包内 `app.db` 能打开且 `integrity_check = ok`、包内条数与 manifest 对得上、包内路径无越界条目（`..` / 绝对路径 / 盘符 / Windows 保留名）。
   - **空间检查**：可用空间 ≥「退路 zip + 解压暂存 + 保留的旧目录」三者之和的估算值。
   - **造退路**：把当前整库打成退路 zip（数据根上一级，同前缀只留 1 份）；退路失败 → 整个恢复中止。
   - **解压到数据根同级的暂存目录** → 再校验一次 → **旧目录改名保留** → 暂存目录一次 `renameSync` 原子落位（照 `migrateDataRoot` 的形状）。
   - **改写三行目录设置**：按 U5 写成「本机实际生效的数据根 / 其下 `photos` / 其下 `inbox`」。写法沿用 `migrateDirs.ts` 的「原值等于旧根下默认值就写空串」口径，让重启后回落新根默认值。
   - **置 `pendingRestart`**：界面弹**不可关闭**的 Modal + 顶部红条，写清「数据已换成 <包名> 的内容，请重启软件」，并给「立即重启」按钮（U10）。
   - **回执**：按 U12 给出两组对照条数。

3. **快照默认份数**（B8）：**已落地，不在本次实施范围**，作为回归项保留。

4. **文档同步**：`map.md`（P-09 / F-09 / 关键数据）、`DELIVERY.md`（备份与恢复章节新增「整库压缩包」这一路）、`AGENTS.md` 若有需要。

## 不做什么

1. **不做云备份 / 自动定时备份**——只做手动一键备份。
2. **不做增量备份**——每次都是全量。
3. **不做加密 / 密码保护**——包就是个普通 zip。
4. **不做跨版本降级恢复**：包内 schema 版本高于当前软件支持的最高版本时拒绝并提示升级。
5. **不改快照机制本身**（生成、轮转、恢复、列表语义都不动），只在同一张卡片里加两个按钮。
6. **不动归档机制**：档案包仍是独立目录形态，不改成 zip。
7. **不做部分恢复**（只恢复照片 / 只恢复库）。
8. **不保留旧数据目录**（U4 裁决的直接后果）：旧目录在落位前改名，落位成功后按 U3 的时点清理，不给用户留两份几 G 的副本。

## 约束

- 备份**不能默认落在数据目录里面**；用户主动选进去时拒绝（U9）。
- 库的部分只许 `VACUUM INTO`（`checkpoint` 之后），不许裸拷 `.db`、不许读进内存再写。
- 照片必须**流式**进包。
- zip 条目名只放相对路径，解压时拦截 `..` / 绝对路径 / 盘符 / Windows 保留名（沿用 `resolveInside` 的越界口径），防 zip slip。
- 恢复是**唯一不可逆**的新操作：校验不过就拒绝、退路失败就中止、落位前失败当前数据不动。
- 新增迁移只许加法（是否需要见 U3）。
- 新增 IPC 通道必须同时进 `CHANNELS` 与 `ipc.ts` 处理器表；**「恢复数据」及其写操作绝不能进只读白名单**（它关连接、换库，被放行会在目录迁移途中顶掉正在读的库）；「立即备份」按既有判据（查库 + 写用户选的文件，同 `payments:export`）可进白名单，但与「恢复」分开处置。
- **改主进程 DTO / IPC 回包形状时，`src/renderer/src/api.ts` 的手抄副本必须同批改**（本仓无类型生成，不同步时两个 `tsc` 都不报，只在运行时字段拿不到）。
- **依赖**：本仓运行期依赖里只有 `archiver`（只能压不能解），**没有**任何直接声明的解压库。若必须引入，须是 `package.json` 里的**显式**依赖（不许直接 import 传递依赖），并记进 `docs/decisions.md`。
- 提交前四道门禁：`npm run test`、两个 `tsc --noEmit`、`npm run build`。

## 已知风险

1. **恢复是整库替换，不可逆**。缓解：包内校验 + 空间检查 + 退路 zip + 落位前不动当前数据 + 重启提示五道。改这块先读 `docs/decisions.md` D-020 / D-022。
2. **换机后路径改写会改变「照片在别的盘」的习惯**：原机若把照片指到 `D:\照片`，恢复后照片落到本机数据根下。这是 U5 的必然代价，回执里要说明。
3. **包体积**：照片一年几个 G，zip 后近似原体积（jpg 已压缩）。备份/恢复都要有进度与空间检查。
4. **恢复中途断电**：落位阶段的原子性与可恢复性必须在 SDS 里逐步骤写明。
5. **与「目录迁移」互相干扰**：两者都动数据根、都要置 `pendingRestart`，必须互斥（复用既有锁，不许新造第二套）。
6. **U4 的代价**：整目录替换意味着旧快照史一并消失。恢复后维护页的快照列表只剩「退路 zip 之外」的 0 份——用户若想留快照史，得自己先单独备份。这条要写进交付说明。
7. **包内绝对路径在换机后失效**：`snapshots.path` / `archives.path` 都是绝对路径。**（U17b：包里带 `snapshots\`，所以恢复后快照文件在、但登记行的路径是备份机路径 → 必须按包内实际文件名重写，否则维护页显示「文件缺失」；实施时已处理。原「恢复后快照列表必然为空」的说法随 U14 一并作废。）** `archives\` 随包走，但**档案登记行里的 `path` 是备份机路径**，恢复后档案柜会全部「目录不存在」——**必须在实施时改写 `archives.path`** 到本机数据根下同名目录，否则年度档案等于白带。
