# 开发与维护工作流手册

> 适用场景：用 AI 从零开发一个软件，以及之后长期维护它。
> 目标读者：你自己，以及任何接手这个项目的人。
> 不适用：一次性的脚本、写个 demo 就扔的实验。

## 0. 这份手册想解决什么

三个具体问题：

1. **每次沟通都要重讲一遍。** 新会话不记得项目怎么跑、页面在哪、上次为什么那么选。
2. **说不精确。** 口语描述 bug 和需求天生有损，AI 理解偏了，返工。
3. **越做越乱。** 没有地图，改到后面自己都不知道系统长什么样。

这三件事有一个共同解法：**把共享记忆从对话里搬进文件里，并且规定好谁在什么时候读哪个文件。**

记住一句话，后面所有内容都是它的展开：

> **对话双方的记忆不共享，所以记忆必须外置。**

我们这里的「对话双方」包括：你和我、我和子 agent、今天的主会话和明天的主会话。它们之间没有任何共享的上下文。唯一能传下去的是文件。

---

## 1. 核心原理与四条推论

**原理**：一次任务里，谁需要什么信息，就提前把它写成文件，让需要的人自己读。不要靠对话传递。

四条推论，决定了整个流程的形状：

**推论一：任务书必须自包含。**
子 agent 看不到我们的对话。它拿到多少信息，完全取决于任务书里写了什么。任务书漏了「不许动支付模块」，它就会去动。这不是它笨，是它不知道。

**推论二：主会话只持有结论，不持有过程。**
子 agent 读 40 个文件、试错 3 次，这些都在它自己的上下文里，结束即消失。主会话只收到一段结论。这是主会话能连跑一天的唯一原因。

**推论三：判断和执行的错误代价不同，所以要分开。**
理解错一行需求，改一行文档就行；理解错一个方案，写完 800 行才发现，代价是几十倍。所以把「确认理解」单独做成一步，放在写代码之前。

**推论四：文档会腐烂，所以必须挂到流程上。**
文档不是写完就完事的东西。它只有在「每次改动都顺手更新」时才成立。挂不到流程上的文档，三个月后会比没有更糟——因为 AI 会照着错的地图行动。

## 2. 文档体系：谁装哪种记忆

不同的记忆寿命不同，所以要放在不同的文件里。混在一起的结果是：每个文件都又长又旧。

| 文件 | 装什么 | 谁读 | 更新时机 | 寿命 |
|---|---|---|---|---|
| `AGENTS.md` | 不变的规矩：怎么跑、什么不许动、去哪找东西 | 每个会话自动读 | 项目结构或约定变化时 | 长期 |
| `docs/map.md` | 稳定结构：页面 / 模块 / 功能 ↔ 代码位置 | 需要定位时 | 每次改动涉及结构后 | 长期 |
| `docs/decisions.md` | 关键决策：选了什么、为什么、否决了什么 | 需要理解「为什么」时 | 做出决策时 | 长期追加 |
| `docs/requirements/RQ-xxx.md` | 一次需求的完整定义 | 实施前 | 需求阶段，之后锁死 | 中等 |
| `docs/plans/PL-xxx-plan.md` | 一次改动的方案 | 审核、实施时 | 变更时 | 中等 |
| `docs/plans/PL-xxx-sds.md` | 一次改动怎么做出来的细节 | 实施时 | 定稿后锁死 | 中等 |
| `docs/issues/IS-xxx.md` | 一个具体问题 | triage 后、修复时 | 状态变化 | 短 |
| 主会话上下文 | 当前这批任务的调度状态 | 只有我 | 一直在变 | 一次工作 |

### 建议的目录结构

```
项目根/
├── AGENTS.md
├── docs/
│   ├── map.md
│   ├── decisions.md
│   ├── requirements/
│   │   └── RQ-001-xxx.md
│   ├── plans/
│   │   ├── PL-001-plan.md
│   │   └── PL-001-sds.md
│   └── issues/
│       └── IS-001-xxx.md
└── src/...
```

### 三条关于文件的原则

**一，宁可短，不要全。** `AGENTS.md` 每一轮都要占上下文。判断标准：这段话是不是每个任务都用得上。用不上就单独放文件，`AGENTS.md` 里留一行指针。

**二，一个文件一件事。** 别把需求、方案、进度塞进同一个文档。它们寿命不同，更新节奏不同，混在一起就会互相拖累。

**三，写完就锁。** 需求卡定稿后、SDS 定稿后，之后的改动必须走「变更」而不是「顺手改」。否则你永远不知道实施的是哪一版。

## 3. 全流程总图

两条主干，按规模选一条。

```
【新增能力 / 较大改动】

  想法
   ↓
① 需求成型 ──────────→ docs/requirements/RQ-xxx.md
   ↓
② 质询 grill ─────────→ 需求卡 v2（补风险与未决问题）
   ↓
③ 方案计划 ──────────→ docs/plans/PL-xxx-plan.md
   ↓
④ 独立审核（红队）────→ 审核意见，采纳/驳回要写理由
   ↓   ↑ 不够好就回 ③，最多两轮
⑤ 写 SDS ────────────→ docs/plans/PL-xxx-sds.md
   ↓
⑥ SDS 审核 ──────────→ 同上
   ↓
⑦ 实施（主会话调度）──→ 代码 + 任务记录
   ↓
⑧ 验收 ──────────────→ 逐条对照验收标准
   ↓
⑨ 收尾 ──────────────→ 更新 map / decisions，关闭需求


【Bug 修复 / 小改动】

  现象（一句话）
   ↓
A. triage（只读定位）─→ docs/issues/IS-xxx.md
   ↓
B. 你审工单 ─────────→ 根因对不对？范围对不对？
   ↓
C. 修复（子 agent）──→ 代码
   ↓
D. 回归 ─────────────→ 按工单的复现路径复跑
   ↓
E. 收尾 ─────────────→ 关闭工单，需要时更新 map
```

两条主干在「实施」处汇合：都要主会话调度、子 agent 干活、独立 agent 审核。

**什么时候走哪条**：见第 7 节「仪式阶梯」。简单说：错误代价高、或需求不确定度高，走上面；否则走下面。

## 4. 阶段详解

每个阶段按同样的结构写：**目标 / 怎么做 / 产出 / 完成判据 / 常见错误**。

---

### 阶段 0：建立坐标系（触发式，不是固定第一步）

**目标**：让之后每一次沟通都有共同的坐标。

**先搞清楚你的起点**，三种情况做法完全不同：

| 起点 | 什么时候做 | 地图从哪来 |
|---|---|---|
| **维护 / 接手已有项目** | 第一天，立刻有用 | 读代码生成 |
| **新项目，零代码** | 第一个能跑通的切片之后 | 从 SDS 的「模块划分」表校准出来 |
| **新项目，规模还小** | 可以先不做 | 代码量小，agent 直接读得完 |

**为什么新项目不能先做**

`map.md` 的核心是「页面 / 功能 → 入口文件」这个映射。没有文件，右边那一列是空的。此时硬画，产出的只是一份设想，而这份设想 SDS 里已经有了——模块划分表就是地图的草稿。

地图还有一个更根本的前提：**它的收益和项目规模成正比**。两千行的项目，agent 直接读完全没问题，地图纯属额外维护成本。等到页面多了、模块多了、你开始说不清「是哪个页面」了，它才回本。

**触发条件**（出现任一条就该做）

- agent 开始找错地方，或者要找很久
- 你自己开始说不清某个功能在哪个文件
- 模块数量超过十几个
- 你开始频繁用「那个……就是带表格的那页」这种说法

**三种起点怎么做**

*维护 / 接手已有项目*

1. 让 agent 通读仓库生成 `map.md` 初版。它读代码比你自己回忆准
2. 你只做修正：改 ID、改命名、合并重复、删掉它编的
3. 写 `AGENTS.md`（怎么跑、什么不许动、去哪找东西）
4. 在 `AGENTS.md` 里加规矩：**改动涉及结构时，收尾必须更新 `map.md`**

*新项目*

1. 走常规流程：需求 → 计划 → SDS
2. SDS 里的「模块划分」表先当地图用，标好打算落在哪个文件
3. 第一个垂直切片做完、能跑起来之后，**立刻**把它校准成 `map.md`
4. 同时把 `AGENTS.md` 里的「怎么跑」写实——这时候命令才真的存在
5. 之后的每个需求，收尾都更新地图

*规模还小*

先不做，但**记住触发条件**。别等痛了才想起有这回事。

**产出**

- `AGENTS.md`（新项目可以晚一点写，先写约定，命令等有了再补）
- `docs/map.md`（新项目在第一个切片之后）
- `docs/decisions.md`（空文件，带标题）
- `docs/requirements/`、`docs/plans/`、`docs/issues/` 三个目录（这个可以第一天就建）

**完成判据**

随便挑三个页面，你只报 ID，agent 能直接说出对应文件和它做什么。做不到就回去补。

**常见错误**

- `AGENTS.md` 写成项目介绍。它要的是**操作性信息**：命令、约束、指针，不是背景故事。
- map 里塞满组件级细节。它只需要到「页面 / 功能 → 入口文件」这一层，再细就没人维护了。
- 项目还小就急着建地图，结果维护成本大于收益，三个月后它烂了，你反而不信它了。

### 阶段 1：需求成型

**目标**：把脑子里的想法变成一份能判对错的文档。

**怎么做**

按模板写 `docs/requirements/RQ-xxx.md`。五个必填块：

1. **背景**：为什么要做。三句话以内。
2. **做什么**：功能点，逐条。
3. **不做什么**：明确排除项。**这一条最常被漏，也是范围蔓延的头号原因。**
4. **验收标准**：可执行、可判定。
5. **约束**：不能动的模块、必须兼容的版本、性能要求。

如果是照着市面上的软件做，多写一条：

6. **参考**：产品名 + 具体页面/功能名，**用它的原词**。

> 关于「验收标准」：这是整个文档里最容易写废的一栏。
> ❌「退款功能正常」
> ✅「已支付订单点退款 → 弹二次确认 → 确认后状态变『退款中』→ 列表 10 秒内刷新 → 刷新页面状态保持」
> 判据：**换个人来测，能照着这行字判断通过与否。**

**产出**：`docs/requirements/RQ-xxx.md`

**完成判据**：验收标准每一条都能被第三者独立判定，不需要问你。

**常见错误**

- 只写「做什么」，不写「不做什么」。
- 验收标准写成形容词（「流畅」「友好」）。
- 一次需求塞进三个不相关的功能。拆开，各有各的编号。

---

### 阶段 2：质询（grill）

**目标**：把「以为自己想清楚了」变成「确实写下来了」。

**怎么做**

拿需求卡去拷问。两种方式，都用：

- **让它问你**：「按这份需求，列出你还需要的所有信息，以及你认为有歧义的地方。」
- **你问它**：「如果按这份需求做，最可能在哪出问题？哪些地方我漏了？」

**重点关注哪几类问题**

- 边界：0 条、1 万条、空值、超长、重复提交
- 状态：中途退出、断网、并发操作、权限不足
- 与现有功能的冲突：会不会破坏已有的什么
- 时间/顺序：异步、缓存、先删后建
- 回滚：做错了怎么退回去

**产出**：需求卡 v2，新增两节：

- **已知风险**：做的时候要盯住什么
- **未决问题**：还没定的，标上「谁定、什么时候定」

**完成判据**：没有新的未决问题；或者剩下的问题都属于「做了才知道，现在讨论是空谈」。

**常见错误**

- 质询变成无限讨论。定一条线：**剩下的是「实现细节」就停，是「行为定义」就不能停。**
- 把未决问题留到实施阶段。实施中的 agent 会自己拍板，而它拍的不一定是你想要的。

---

### 阶段 3：方案计划

**目标**：定「怎么做」，粒度到模块和顺序，不到代码行。

**前置：先摸底（改的是已有功能时）**

如果这次要改的东西已经在跑，先摸清它现在怎么运作：完整链路、代码分布在哪些文件、有什么隐含约定、改了会连带影响什么。

跳过这一步的典型后果：方案设计得很好，但漏了三条散落在别处的相同逻辑。摸底不评价好坏、不给建议，只回答「现在是什么样」。任务书见 `TASKBOOKS.md` §5。

**怎么做**

按模板写 `docs/plans/PL-xxx-plan.md`。核心内容：

1. **现状**：现在系统里相关的部分长什么样。引用 `map.md` 的 ID。
2. **方案**：分几步，每步改哪里、为什么这么切。
3. **影响面**：会碰到哪些已有模块，哪些要一起改。
4. **风险与对策**：从需求卡的「已知风险」继承，加上技术风险。
5. **不做的事**：这次不顺手重构什么。
6. **回滚方案**：做砸了怎么退。

**多方案时**

列 2–3 个候选，各写一句取舍，然后**明确选一个并说明理由**。不要留「都可以」。选错了后面再审。

**产出**：`docs/plans/PL-xxx-plan.md`

**完成判据**：一个没参与讨论的人读完，能说出「要改哪几个地方、按什么顺序」。

**常见错误**

- 计划写成代码。计划回答「改哪里、什么顺序」，SDS 才回答「怎么改」。
- 步骤之间没有可验证的中间态。好的切分是：**每一步做完都能跑、能测**，不是攒到最后一起验证。

---

### 阶段 4：独立审核（红队）

**目标**：在写代码前，把方案的坑挖出来。

**怎么做**

**必须另起一个 agent 实例**，用新的任务书。任务书里**不要写作者的思路**，只给材料：

> 材料：`docs/plans/PL-xxx-plan.md`、`docs/requirements/RQ-xxx.md`、`docs/map.md`，以及仓库代码。
> 任务：证明这个方案会在什么情况下失败。
> 要求：每条反对意见必须指出具体文件行号，或给出具体的失败场景（什么操作 → 什么后果）。
> 禁止：「建议再考虑一下」「可能有问题」这类没有落点的意见。
> 输出：问题清单，每条标注严重度（会挂 / 会返工 / 可接受）。

**独立性靠三件事**（缺一条，审查就会退化成盖章）：

1. **换视角**：让它「证明会失败」，不是「审一下」。
2. **换证据**：给它代码和原始材料，不给作者的总结。
3. **换权限**：只读。它不能顺手改点东西让方案看起来成立。

**怎么处理意见**

- 采纳 → 改计划，在计划的「变更记录」里写一行。
- 驳回 → **必须写理由**。驳回理由是文档里最值钱的部分，它防止下一轮重新讨论同一件事。

**轮次**：**最多两轮。** 第三轮开始基本在抠字眼，是在烧钱不是在建质量。

**产出**：审核意见 + 计划 v2

**完成判据**：新一轮的意见都变成「可接受的取舍」，而不是「必须改的问题」。

---

### 阶段 5：写 SDS

**目标**：写出一份「给一个完全没有前情的 agent，它能照着做出来」的文档。

**这是 SDS 唯一的功能性定义。** 别把它写成给老板看的漂亮文档。

**必须包含**

1. **目标与范围**（一句话，引用需求卡编号）
2. **模块划分**：新增/修改哪些文件，各自职责
3. **接口**：函数签名、参数、返回值、错误码。**写到能直接照着写代码的程度。**
4. **数据结构**：表结构变更、类型定义、迁移脚本
5. **数据流**：一次请求/一次操作从头到尾经过哪些环节
6. **错误处理**：每种失败怎么表现、怎么记日志、要不要重试
7. **边界条件**：空、超长、并发、权限
8. **测试策略**：哪些必须自动化，哪些手工验证
9. **任务拆分**：切成若干个**可独立完成、可独立验证**的任务，标好依赖顺序
10. **决策记录**：关键选择 + 为什么 + 否决了什么

第 9 条是实施阶段的直接输入——每个任务就是一张任务书的原料。

**颗粒度自检**

把 SDS 交给一个全新的 agent，只说「按这个做」，不做任何补充解释。如果它能做对，SDS 合格；如果它需要问你「这个字段是干嘛的」，说明这里没写清。

**产出**：`docs/plans/PL-xxx-sds.md`

**完成判据**：通过上面的颗粒度自检。

**常见错误**

- 塞进「愿景」「价值」这类内容。实施者不需要。
- 接口只写名字不写签名。实施者会自己发明，然后跟你的预期对不上。
- 任务拆分按「文件」切，不按「可验证的功能」切。应该切成「做完这个能测什么」。

---

### 阶段 6：SDS 审核

同阶段 4，材料换成 SDS，同样最多两轮。

这次重点看四样：

- 接口签名和数据结构**是否自洽**（A 的返回值能不能喂给 B）
- 错误处理**是否有死角**
- 任务拆分**是否有无法独立验证的**（那种「做完这三个文件才能测」的切法）
- 和现有系统的**冲突点**

---

### 阶段 7：实施

**目标**：按 SDS 把代码写出来，主会话不被细节淹没。

**两种模式**

**模式 A：原地实施（适用于中等改动）**

在当前会话里，主会话当调度员，按 SDS 的任务清单逐个开子 agent。

**模式 B：新会话实施（适用于大改动）**

开一个全新会话，输入只有 SDS 文件。新会话没有任何历史包袱，上下文全留给实施。这也是对 SDS 质量最硬的检验。

**主会话的纪律（这是全文最重要的一节）**

主会话只做四件事：

1. 把 SDS 里的任务拆成任务书
2. 发出去（能并行就并行）
3. 收结论，判断是否达标
4. 遇到关键分歧时做决策

主会话**不做**的四件事：

- 不读代码细节
- 不自己写代码
- 不调试
- 不把 diff、日志、子 agent 全文拉回自己的上下文

违反后两条，上下文必爆，而且你会在第 3 个任务上就开始糊涂。

**每个任务的循环**

```
写任务书 → 发子 agent → 它干活 → 收结论
   ↓                                    ↓
   └──── 不达标 ←──── 判断 ──── 达标 ────┘
                                          ↓
                              更新 todo + 一行落盘
```

**并行怎么做**

- 按**文件不重叠**切分。两个 agent 改同一个文件，必然冲突。
- 有依赖的串行，无依赖的并行。
- 一批不要超过 4 个，太多你判断不过来，出错也难追。

**中途要停怎么办**

在 `docs/plans/PL-xxx-sds.md` 顶部维护一个 `## 进度` 段，勾掉已完成的任务，写一行「下一步做什么、卡在哪」。**下次恢复只读这一节就够了**，不用回看对话。

**产出**：代码 + 更新后的进度段

**完成判据**：SDS 里的任务全部完成，且每个任务的验收方式都跑过。

---

### 阶段 8：验收

**目标**：确认做出来的东西，就是需求卡里说的那个东西。

**必须分三层，缺一层就会漏**

**第一层：自动化**
跑测试、跑 lint、跑构建。这一层不能靠人看，靠命令。

**第二层：功能验收**
打开需求卡，**逐条**对照「验收标准」，一条一条打勾。不许「差不多都对了」。

**第三层：视觉验收**（只针对有界面的东西）
截图/录屏，对照参考产品。渲染类的产出（报表、幻灯片、图表）另外走视觉审核。

**谁来验**

**不是实施者本人。** 另起一个 agent，任务书只给需求卡的验收标准 + 怎么跑起来，不给「我们是怎么实现的」。

**产出**：验收记录（写进需求卡或单独文件）

**完成判据**：三层全过。

**常见错误**

- 跳过第二层，直接看「感觉对了」。
- 验收人和实施人是同一个，于是它验的是「我做的和我做的一致吗」。

---

### 阶段 9：收尾

**目标**：让下一次工作不用从零开始。

**检查清单**

- [ ] `docs/map.md` 更新了吗？（新增页面 / 改了路由 / 模块职责变了）
- [ ] `AGENTS.md` 要改吗？（新增了命令、新增了约束）
- [ ] 关键决策写进 `docs/decisions.md` 了吗？（为什么这么选、否决了什么）
- [ ] 需求卡标记为已完成
- [ ] 计划/SDS 里的「未决问题」都有结论了吗？
- [ ] 有没有顺手留下的临时代码、调试开关、注释掉的旧逻辑？

**"顺手留下的东西"这一条最容易出事。** 三个月后没人记得那个 `if (DEBUG_XXX)` 是干嘛的，然后它变成了永久逻辑。

**完成判据**：明天开一个新会话，只说「继续做 X」，它能自己找到全部上下文。

## 5. 维护分支（bug 与迭代）

日常 80% 的工作在这里。它比新功能流程短，但**不能省 triage**。

### A. 现象 → triage

**你只需要说一句糙话。**

> "订单详情页点退款直接提交了，没有确认框。"

**然后开一个只读的定位 agent**（用搜索类/只读类 agent，不要用能改代码的），任务书：

> 根据这个现象，定位到具体代码位置。
> 输入：`docs/map.md`、仓库代码。
> 输出格式（必须全填）：
> - 现象复述
> - 位置：文件:行号，函数名
> - 根因假设：为什么会导致这个现象
> - 影响范围：还有哪些地方会受影响
> - 修复建议：改哪里、怎么改、有什么副作用
> - 复现路径：从哪进、点什么
> 要求：找不到就明说找不到，并列出你排查过的位置。禁止猜测后当成结论。

**这里的关键是：定位这件事由它做，不由你做。** 你原来是"看到 bug → 找页面 → 描述 → 告诉 AI"，现在变成"看到 bug → 说一句话"。

### B. 你审工单

看三样，通常三十秒：

1. **位置对不对**（它说的文件，是不是你觉得的那个地方）
2. **根因说得通吗**（是不是"改了这里就能好"）
3. **影响范围有没有漏**（同样的代码是不是在别处也有）

不对就退回去重定位，或者补一句你观察到的细节。**这一步不能省**——这里是唯一花你时间的地方，也正是该你花时间的地方。

### C. 修

工单定稿后写成 `docs/issues/IS-xxx.md`，然后开实现 agent，任务书直接引用工单。

小修可以直接在当前会话干；涉及多个文件或需要新逻辑的，走一个简版 SDS。

### D. 回归

按工单里的**复现路径**复跑一遍。同时跑自动化测试。

如果这个 bug 值得防再犯，补一条测试用例。**不是每个 bug 都值得补**，判断标准：它会不会以同样的形式再出现。

### E. 收尾

关闭工单。如果这个 bug 暴露了结构问题（比如「同一个判断散落在五个地方」），**记进 `docs/decisions.md` 或 map 的备注里**，不要顺手重构——顺手重构是范围蔓延的另一种形式。

## 6. 子 agent 编排手册

### 三种角色

| 角色 | 用哪种 agent | 权限 | 输入 | 输出 |
|---|---|---|---|---|
| 定位 / 调研 | 只读搜索类 | 只读 | 现象 + map | 工单 |
| 实现 | 通用执行类 | 可读写 | 任务书 + 工单/SDS | 代码 + 结论 |
| 审核 | 独立实例 | 只读 | 材料，不含作者思路 | 问题清单 |

**审核永远不能和实现是同一个实例**，也不能共享上下文。

### 任务书四要素

少一样，agent 就会自己发挥。

```
1. 目标：做完之后，什么事变成什么样（可判定）
2. 输入：读哪些文件；如果是定位，给什么线索
3. 边界：不许动什么；不许引入什么依赖；什么情况下停下来问
4. 验收：怎么算做完；输出格式是什么
```

**关于第 3 条**：`边界` 是最容易被省略、也最容易出事的一条。它是你和 agent 之间唯一的约束来源。

**关于第 4 条**：指定输出格式，能让你只看结论就知道对不对，不用让它把过程吐回来。

### 主会话的上下文预算

粗略的量级感：

- 一个中等任务，主会话只增加 5–10 行有效信息（结论 + 状态）
- 一次会话能调度 15–30 个这样的任务而不失控
- 一旦你发现自己开始往回翻十轮前的对话，说明该收尾开新会话了

**判断该不该开新会话的信号**

- 同一件事讨论超过三轮还没定
- 你在重复解释已经说过的东西
- 主会话开始需要「回忆」早期细节

### 反模式

| 做法 | 后果 |
|---|---|
| 把对话历史整段贴给子 agent | 它被无关信息干扰，且你的上下文白花了 |
| 主会话自己上手改代码 | 上下文被代码灌满，后面调度开始出错 |
| 让子 agent 同时改多个重叠文件 | 冲突，且难以判断谁的改动对 |
| 审核者和作者共用任务书 | 审查变成复读 |
| 一次给子 agent 太多任务 | 中途出错无法定位是哪一步的锅 |
| 子 agent 说「已完成」就信 | 必须让它给出可验证的证据（测试输出、运行结果） |

## 7. 仪式阶梯：这次该用多重

**判断标准：错误代价 × 不确定度，不看改动大小。**

一行改动在支付逻辑里，比三百行 CSS 值得更多仪式。

| 情况 | 走哪条 | 用哪些阶段 |
|---|---|---|
| 改文案、调样式、空指针 | 直接说 | 无流程，一个 agent 改完 |
| 能复现、但不知道在哪 | 维护分支 | triage → 修 → 回归 |
| 小功能，边界清楚 | 维护分支 + 简版 | 需求卡 → 实现 → 验收 |
| 中功能，跨两三个模块 | 主干（简化） | 需求卡 → 计划 → 实施 → 验收 |
| 大功能 / 不确定度高 | 主干 | 全套 |
| 重构 / 动架构 / 动数据 | 主干 + 加严 | 全套 + 两轮审核 + 新会话实施 |

**什么时候可以跳过阶段**

- 跳过计划：改动只碰一个文件，且方案唯一。
- 跳过独立审核：验收标准明确到不需要判断，且做错能一键回滚。
- 跳过 SDS：任务是 SDS 里的一条，直接当任务书用。

**不能跳过的三样**

1. **验收标准**。没有它，你不知道什么时候算做完。
2. **triage**（只要涉及定位）。跳过它等于让你自己去做最费时的翻译。
3. **收尾更新 map**。跳过它，三个月后你重新回到起点。

## 9. 反模式

按出现频率排。

**1. 流程过重，然后彻底放弃。**
一个内部小功能走全套「计划 → 多轮审 → SDS → 新会话」，你会觉得这套东西是负担，然后全部丢掉。**这是最常见的失败方式。** 用第 7 节的阶梯，多数任务只需要其中两三步。

**2. 文档写了不更新。**
`map.md` 一个月不维护就有一半是错的。那时的危害超过没有——AI 会照着错地图行动，而且它不知道自己错了。**要么挂进收尾清单，要么别建。**

**3. 假独立审查。**
同一个模型、同一份材料、同样的措辞，得到的是礼貌的盖章。要真独立就得换视角、换证据、换权限。而且两轮就该停。

**4. 主会话亲自下场写代码。**
一旦主会话开始读代码、改文件，上下文就被灌满，之后调度开始出错。**主会话的价值在判断，不在执行。**

**5. 验收标准写成形容词。**
「流畅」「好用」「正常」——这些词没法判定，于是验收变成「感觉差不多了」。

**6. 一次给子 agent 一个巨型任务。**
「把这个功能实现了」。它做到一半跑偏，你不知道从哪一步开始错的。切成能独立验证的小块。

**7. 需求讨论无限延长。**
判据是：剩下的是「行为定义」还是「实现细节」。行为定义不能留白，实现细节现在讨论是空谈，做的时候自然会知道。

**8. 顺手重构。**
修 bug 时看到烂代码，顺手改了。这次改动就多了一个没人审过的变量。记下来，单独做。

## 10. 速查卡

**每天开工**

1. 新会话自动读 `AGENTS.md`
2. 需要定位 → 先读 `docs/map.md`

**修 bug**

```
一句话现象 → 只读 agent 定位 → 你审工单（30 秒）
→ 修 → 按复现路径回归 → 关单
```

**做功能**

```
需求卡（含"不做什么"+"验收标准"）→ 质询 → 计划
→ 红队审（≤2 轮）→ SDS → 审 → 实施 → 三层验收 → 收尾
```

**主会话永远只做**

拆任务 / 发任务书 / 收结论判断 / 关键决策

**主会话永远不做**

读代码细节 / 写代码 / 调试 / 把 diff 拉回上下文

**每个子 agent 的任务书必须有**

目标 / 输入 / 边界 / 输出格式

**收尾必查**

map 更新 / decisions 更新 / 无临时代码 / 需求关单

**什么时候开新会话**
