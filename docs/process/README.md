# 过程文档归档

> 这里放的是开发过程中产生的**原始工作文档**：独立验收的判定书、审计台架的结论、红队审核意见、需求质询清单、工单定位报告、事故复盘。
>
> 它们不是「结论」，是「怎么得出结论的过程」。保留原样是为了让接手的人能看到一个决定当初是被什么证据推翻或确认的 —— 正式结论在 [`docs/decisions.md`](../decisions.md) 和 [`docs/plans/`](../plans/)，这里是可以对照的底稿。

## 这些文档的来路

项目的工作方式（见 [`docs/WORKFLOW.md`](../WORKFLOW.md)）是每个阶段派**独立的、与主会话不共享上下文的**子代理去做验收、审计、审核。子代理只能读不能改，产出的判定书要逐条带证据（期望值 / 实际值 / 文件行号 / 命令输出）。

所以这些文档有两个特点：

1. **带大量实测数据** —— 具体到某条记录是几分钱、某个文件是第几行、某次操作前后 SHA-256 变没变
2. **包含被推翻的方案** —— 审核意见里写的「这里会漏」「这条路走不通」，很多后来真的改掉了，改的结果在 decisions 里

读的时候注意：**文档里的行号是当时的行号，代码改过之后会对不上**。要定位现在的实现，以 [`docs/map.md`](../map.md) 为准。

## 归档时做过的处理

- **本机用户名脱敏**：原文里的 `C:\Users\<真实用户名>` 统一替换成 `C:\Users\<USER>`。共 3 份文件涉及。
- **其余内容一字未改**：包括判定书里的失败记录、审计发现的缺陷、审核意见里对方案的否定。
- 原文都在 `.tmp/` 下（该目录不入库），这些是副本。

## 怎么用这些文档

**想知道某个设计为什么是现在这样** → 先查 `docs/decisions.md` 的 D-xxx，再回到这里找对应的审核/审计底稿看当时的证据。

**想改一处以为「显然可以改」的地方** → 先在这里搜一下，很可能当初有人提过同样的想法并且被否了，理由写在这些文档里。

**想复现某个验收场景** → 判定书里写了当时的构造数据、操作步骤、期望值。但注意数据目录要用 `ATT_DATA_ROOT` 指到临时目录，**不要碰真实库**。
