## 2. 溢出的到底是哪一层（每日录入，录 1 条后实测宽度链）

从内容区到 table，每层 `clientWidth / scrollWidth`（`overflowX` 标注在括号里）：

| 层 | clientW | scrollW | 溢出 | overflowX |
|---|---|---|---|---|
| `main.ant-layout-content`（Layout.Content） | 962 | **1065** | **+103** | **auto** ← 横向滚动条落在这里 |
| `div.ant-space`（页面根节点） | 922 | 1045 | +123 | visible |
| `div.ant-card`（「当天记录」卡片，= 用户说的「整体的框」） | 920 | 1044 | +124 | visible |
| `div.ant-card-body` | 920 | 1044 | +124 | visible |
| `div.ant-table-wrapper` | 896 | 1032 | +136 | visible |
| `div.ant-table-container` | 896 | 1032 | +136 | visible |
| `div.ant-table-content` | 896 | 1032 | +136 | **visible**（antd 没配 `scroll` 时不给 overflow） |
| **`table`** | **1032** | 1032 | 0 | visible，`table-layout: fixed` |

结论：**是 `<table>` 本身宽过容器**（1032 > 896，超 136px），不是 antd `scroll={{x}}` 钉死的（**全项目没有任何 `scroll={{x}}`**，`grep scroll={{` 只有 0 处命中），
也不是 `.ant-table-content` 被撑开（它自己只有 896，是**可见溢出**不是滚动容器）。
`table` 到 `Layout.Content` 之间**六层全是 `overflow-x: visible`**，所以这 136px 一路穿出去：穿透 Card 边框（Card 的 scrollWidth 比 clientWidth 大 124px），
最后被唯一设了 `overflow:'auto'` 的 `Layout.Content`（`src/renderer/src/App.tsx:326`）接住 —— 这就是「必须拖下方横向滚动条」的那条。

宽度预算（为什么只有 896 可用）：
`innerW 1167` − `Sider 190`（`App.tsx:262`）= 977（Content 外框）− 纵向滚动条 15 = 962（Content clientW）− Content padding 40（`App.tsx:322-326` `padding: 20`）= **922**（页面根）− Card 边框 2 + body padding 24 = **896**（表格容器）。

## 4. 根因（一句话）

**因为「当天记录」表的列宽被写死、合计 1032px（数据列 984 + antd 展开列 48）超过容器可用的 896px，而 `备注` 列的 `ellipsis: true`（`Daily.tsx:498`）让 rc-table 把整张表钉成 `table-layout: fixed`（`node_modules/rc-table/lib/Table.js:457-474`），固定布局下表格的 used width 取 `max(容器, 列宽合计)` 而不压缩列，所以表格实宽 1032px 比容器宽 136px；`table` 到 `Layout.Content` 之间六层全是 `overflow-x: visible`，这 136px 于是穿透 Card 边框、由唯一 `overflow:'auto'` 的 `Layout.Content` 接住，表现为「条目超出整体的框 + 底部横向滚动条」。**

## 5. 修法候选

- 残留风险：窗口再被拖窄（< 1180）仍会溢出——固定布局表的天性，见 C。

- 改动面：1 行。风险低。

### C（最小、但改变交互形态）去掉 `备注` 列的 `ellipsis: true`
- 位置 `src/renderer/src/pages/Daily.tsx:498`。
- 效果：rc-table 的布局判定退回 `auto`（同批量登记），浏览器会把列压到容器内，**不会再出现横向滚动条**（除非窗口窄到 min-content 都放不下）。

## 6. 两页是不是同一个原因

**不是同一个表现，但同一套「列宽写死 + 只有一个自适应列」的写法。**

| | 每日录入 | 批量登记 |
|---|---|---|
| 表宽策略 | `table-layout: **fixed**`（被 `备注` 的 `ellipsis:true` 触发，`rc-table/Table.js:457-474`） | `table-layout: **auto**`（无 ellipsis、无 `sticky`、无固定列） |
| 声明列宽合计 | 984 + 展开列 48 = **1032** | 70+130+110+90+90+110+90+120+90 = **900** |
| 容器 | 896 | 896 |
| 赤字 | **136px** | 4px |
| 结果 | 列不能被压缩 → 表实宽 1032 → 页面横滚 **+103px**（复现 3/3） | 浏览器把 900 压成 896（每列少 0.4~1.5px，如 130→129.21）→ 溢出 **0**（复现 0/3） |
| 阈值 | 窗口 `innerW ≥ ~1245` 才不溢（W=1240 溢 30px，W=1280 溢 0） | 一直不溢，实测到 W=1000/950/900/850/800/760/700/**650** 都 0 溢；W=600 才溢 30px（表格地板宽 391.91px） |

所以：**YG 说的「每日录入」我能 3/3 复现；「批量登记」在当前 1180×800 窗口下我复现不了**（含带 2 张照片的那条记录）。
两者的差别纯粹是 `table-layout: fixed` 与 `auto` 的差别——正因为如此，两页的「列宽预算超标」是真隐患，只是批量登记被浏览器的自动压缩吃掉了。

## 7. 回归风险

1. **IS-006 ②「批量登记结果列表逐条可编辑」**：改列宽不影响「编辑」按钮（列宽 90，按钮内容 64+内边距，够用）。
   **但不能给批量登记的表加 `tableLayout="fixed"`**：它合计 900 > 896，一加就立刻像每日录入一样出横向滚动条（bug 传到第二页）。若要「两页统一 fixed」，必须同步把批量登记的列宽砍到 ≤ 848。
2. **IS-006 ③「照片列点击放大」**：`onClick` 挂在 `<img>` 上（`Daily.tsx:519`、`QuickBatch.tsx:463`），改缩略图尺寸或列宽都不动这个 handler，功能不受影响。
   约束是**列宽下限**：每日录入 44px 缩略图 → 列宽 ≥ 110px；批量登记 40px → ≥ 102px。低于此值，第二张缩略图会顶出单元格（fixed 布局下还会被裁掉）。
3. **汇总「全员」表是否同一套策略**：是。`Summary.tsx:632-663`（`allColumns`）同样是「每列写死宽度 + 末尾一个自适应列」（140+110+120+140 = 510 + 「按工地分解」自适应），
   而且它传了 `sticky`（`Summary.tsx:933`），按 rc-table 的同一段判定（`Table.js:457-474`）也会被钉成 `table-layout: fixed`。
   - 目前 510 < 容器，没出事，**本次只动「每日录入」不必同步改汇总**。
   - 但要注意它外面那层 Card body 设了 `overflowX: 'hidden'`（`Summary.tsx:916`）——万一哪天固定列宽合计超过容器，它不会出滚动条，而是**静默裁掉「按工地分解」列**。若把「列宽预算」做成共享规则，必须把汇总一起纳入校验，且不要照抄那层 hidden。
4. **备注列 0 宽**：现在 `备注` 列宽 0、内容被 ellipsis 裁掉（列头只剩一丝）。修列宽预算时必须顺手把它救回来，否则改完仍是「备注看不见」。

## 9. 没把握的地方

1. **批量登记为什么 YG 会觉得也溢出**：3 次取证都没复现（含带 2 张照片的记录）。可能他当时窗口更窄（要窄到 ~640px 才会溢），或者他看的是别的东西（照片框 / 编辑弹窗 / 表头的长文案）。**需要他补一张截图或说一下当时的窗口宽度**，否则按现有证据只能报「不能复现」。
2. 我用的是 `.tmp\v2` 副本（3 工人 / 2 工地），真实库是 16 工人 / 566 条。列宽与行数无关，但**建议修列宽时按真实库里最长的工人名 / 工地名 / 备注算一遍**——我给的建议值（工人 80）是按 2 字姓名算的，3~4 字姓名可能偏窄。
3. 取证期间我这个隔离实例被外部收尾了两次（日志是 `[db] before-quit：checkpoint + close` 的**正常退出**，不是崩溃），都在启动后 5~8 分钟；同机还有另一个 agent 的实例在跑（端口 9335、userData 指向真实 `%APPDATA%\xinmiao-attendance`）。这件事跟本次现象无关，但我没法控制它，所以每轮取证都尽量一口气跑完。
4. 结论里的绝对值绑定在「窗口 1180×800 / dpr=2」上；换窗口尺寸，溢出**像素数**会变，但「表格实宽恒等于 1032px、不随窗口变化」这一点在 1000~1440 的扫描里都成立。
