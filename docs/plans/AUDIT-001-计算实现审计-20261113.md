## 0. 一句话结论

**核心算术没有错。** 附录三人（21543.75 元）逐格手算对上；`ceilDiv` 的负数分支、`sumAmounts` 的 BigInt 精确累加与三项各自取整、`units_micro` 的 `Math.round`、元↔分的字符串拼接（`1.005` / `8.165` 直接拒绝而不是静默改钱）、乘式溢出边界（最坏 7.2e14 < 2^53）、时段互斥与判重、汇总的 `COUNT(DISTINCT)`、结余四项含冲销——**逐条验过，未发现算错**。

**但发现 5 处会让「钱/工数」与预期不符的地方**，其中 **2 处会真的让钱变**（F1、F2），1 处会丢工数（F3），2 处是门禁/口径缺口（F4、F5）。

| # | 严重度 | 一句话 | 会不会让钱变 |
|---|---|---|---|
| **F1** | **会挂** | 改一条**旧记录的备注**，会把它的「标准工日 / 加班折算」重解成**当前设置**，金额当场变 | **会**（实测 +25.00 元） |
| **F2** | **会挂** | 清库区间里有**晚于今天**的记录时，那些记录**照删**，但**不算进期间净额、也不结转** | **会**（实测 300.00 元消失） |

## 1. 五条缺陷逐条（每条都有可复现的断言）

### F1【会挂】改备注会把固化口径重解 → 金额静默变化

**位置**：`src/main/repo/entries.ts:783`（`updateEntry`）、`:713`（`overwriteEntry`）——两处都无条件调 `prepareFrozen(db, workerId, workDate)`，再把结果写回 `std_minutes` / `overtime_unit_minutes`。

**实测**（`.tmp/audit-verify/repro.test.ts` › C-01）：

```
[实测] 固化 K：480 → 360；加班费：7500 → 10000；应发：37500 → 40000
```

日薪 300 元、K=480 时录一条「整天 + 加班 120 分」→ 加班费 ⌈30000×120/480⌉ = **7500 分**。把全局加班折算改成 360（口径 11：只影响新记录）。用户**只改了一句备注** → 这条记录的 K 被重解成 360 → 加班费 **10000 分**。**+25.00 元，没有二次确认、没有快照、界面上什么提示都没有。**

**依据**：`RQ-001` 口径 11 —— 「每条考勤保存时，把当时生效的标准工日与加班折算记在这条记录上，**之后改设置只影响新记录**。例外（v6.8）：日薪与餐补两个固化列会被『改价』自动重写；**标准工日与加班折算仍按录入时固化，要改历史必须显式执行『按当前设置重算某区间』（二次确认 + 先自动快照）**」。

**反方证据（如实列出）**：`docs/plans/PL-001-sds.md:205` 明写「`updateEntry` … 部分更新后重算 attend/units 与固化四值（价按 work_date 重取、**基线按当前覆盖重解**）」——**SDS 与需求卡冲突，代码跟的是 SDS**。按「需求卡是权威」的规矩判 F1 是缺陷；若 YG 要保留 SDS 的行为，则必须补「二次确认 + 快照」。

**修法（推荐）**：`entries.ts:783` / `:713` 不再重解基线——
- `stdMinutes` / `overtimeUnitMinutes` 取 **`existing.stdMinutes` / `existing.overtimeUnitMinutes`**；
- `dailyWageCents` / `mealAllowanceCents` 仍按 `rateAt(workerId, workDate)` 重取（这是口径 9，本来就该跟价走）。

**但**：如果用户在编辑弹窗里**改了工人或日期**，基线是否该跟着换？这属于「行为定义」，请你定：
- **A（推荐）** 只有 `workerId` 或 `workDate` 真的变了才重解基线；只改备注/照片/加班/工时 → 保持原值。
- **B** 一律保持原值（连换工人也不重解）——最保守，但换工人后 K 可能与该工人的覆盖不一致。

**反证**：`createEntry(FULL, 加班 120, K=480)` → `set(全局 K=360)` → `updateEntry(id, {note:'x'})` → 断言 `overtimeUnitMinutes === 480` 且 `rangePayroll().overtime === 7500`。**现在红。**

### F2【会挂】清库区间含未来日期时：记录照删，钱不结转

**位置**：`src/main/repo/balance.ts:387`（`periodNetForRange` 的 `cut = asOf === undefined ? todayIso() : …`）→ `src/main/repo/payroll.ts:537`（`e.work_date <= ?`）→ 调用点 `src/main/services/archive.ts:2669`（**不传 asOf**）+ `:2775`（结转只收 `netCents ≠ 0` 的人）+ `:2798`（`DELETE FROM entries WHERE work_date >= ? AND work_date <= ?`）。

**实测**（`.tmp/audit-verify/repro-real.test.ts`，今天 = 2026-11-13）：

```
[实测] 今天=2026-11-13；工资表区间应发=60000（两条 = 60000）；闸门期间应发=30000；unbalancedCount=1
[实测-发放] 期间已发=0（期望 5000）
```

同一区间 `2026-01-01 ~ 2026-12-31` 里有两条记录（11-03 与 12-20，各 30000 分）：
- **工资表**看到 **60000**；
- **清库闸门**只看到 **30000**（12-20 晚于今天，被 `work_date <= 今天` 截掉）；
- 清库时**两条都删**，但只结转 30000 → **30000 分（300 元）凭空消失。**

反向同理：区间里若有一笔**未来日期**的发放（12-20 发 5000），`期间已发` 记 **0** → 结转偏大 5000 分 → 清库后「还欠」凭空多 50 元。

**依据**：`RQ-005` C15b「区间应发 = **全史累计应发** − 区间外累计应发」——「全史」不该被今天截断；`D-027` 第 2 条只对「期间预支 / 已发」写了 `≤ 今天`，对「全史累计应发」没有这个限定；`D-031` / RQ-007「欠款不能凭空消失」。

**反方证据（如实列出）**：`archive.ts:371-372` 的注释把「三项都只算 ≤ asOf（未来日期不计入）」写成了**设计**，`PL-004-sds` §6.5 同口径 —— 即代码照 SDS/计划走，但把 C2（**结余专用**的日期边界）搬到了闸门的「全史」上。

**触发条件（现实性）**：① 归档 / 清库区间选到「今天之后」（`Archive.tsx` 的「本年」按钮就给出 2026-01-01~2026-12-31）；② 区间里存在晚于今天的记录（日期录错、或提前录）。**两条同时成立才触发**，但一旦触发就是钱没了，且**界面只显示 30000 的净额**（用户勾确认时看到的就是这个错的数）。

**修法**：`archive.ts:2669` 传 `asOf = to > todayIso() ? to : undefined`（即 `cut = max(今天, to)`）。这样 `to ≤ 今天` 时行为完全不变（不影响现有验收 17 的代数等式），只有区间延伸到未来时才把「未来那一段」也算进来。

**反证**：区间内含一条 `work_date > 今天` 的记录 → 断言 `periodNetForRange(from,to).rows[0].dueCents === 两天的应发`（现红：只有一天）。**已红。**

### F3【会返工】并入「按小时」记录时工时取大，不相加

**位置**：`src/main/repo/entries.ts:886-889`（`applyMerge`）

```ts
const hoursMinutes =
  period === 'HOURS'
    ? Math.max(kept.hoursMinutes ?? MIN_HOURS_MINUTES, incoming.hoursMinutes ?? MIN_HOURS_MINUTES)
    : kept.hoursMinutes ?? null
```

同一函数 `:872` 是 `kept.overtimeMinutes + incoming.overtimeMinutes`——**加班相加，工时取大**，同一动作两种语义。

**实测**（`repro.test.ts` › C-03）：`[实测] 并入后 hoursMinutes = 240（期望 360）`。已有 120 分，再并一条 240 分 → 保留 240，丢 120 分 = 0.222 工 = 基本少 ⌈30000×120/540⌉ = **6667 分 ≈ 66.67 元**，餐补再少一截。

**为什么可疑而不是「确定算错」**：需求卡没规定并入的工数算法（口径 18 只把并入列进判重三动作）。但既然是「同键的两条要合成一条」，加班相加而工时取大就说不通；而若产品意图是「同一段活改了时长，取新的」，那就该走**覆盖**而不是并入。

**修法（需你定）**：
- **A（推荐）** 相加：`(kept.hoursMinutes ?? 0) + (incoming.hoursMinutes ?? 0)`，并补 1440 上限校验。
- **B** 保持取大，但在并入弹窗里明写「按原时长，只加加班与备注」。

**注**：`AM + AM` 并入保持 0.5 工是**对的**（同一上午不能重复计），所以矛盾只在 `HOURS`。

## 3. 验过且确认正确的（逐项有手算过程）

1. **附录三人**：张伟 675000+95625+33750 = **804375**；王芳 546000+32500+31500 = **610000**；李强 35000×20 = **700000**；合计 **2114375 分 = 21143.75 元** —— 与 RQ 附录逐格一致。
2. **`ceilDiv`**：正数 `(n+d-1)/d`；负数 `-(-n/d)` 即数学 `ceil`（`-5/2 → -2`、`-7/3 → -2`、`-1/3 → 0`）。
3. **`sumAmounts`（C 路径）**：全程 BigInt，每步 gcd 约分，**三项各自取整一次**。3 条各 100 分分钟 → `⌈9000000/540⌉ = 16667`（逐条取整才是 16668）——与 D-013 原例一字不差。混合分母 540/450 → `31778` / `1834`。
4. **`units_micro`**：`Math.round`（不是 ceil —— 只入不舍只用于金额）。FULL 540 → 1000000；AM/PM 270 → 500000；AM+PM = 1000000 = 1 工；HOURS 180 → 333333。
5. **元↔分**：`'2000.5' → 200050`、`'1.005' / '8.165' / '0.005' → E_VALIDATION`（**不静默改钱**）、`'99999999.99' → 9999999999`、`2^53−1` 正好通过、再大拒绝。
6. **溢出**：单条 `units_micro × 日薪分` 最坏 4.8e13（UI 界内）/ 7.2e14（std=2），均 < 9.007e15；一人一年的聚合从不在 float 里做。
7. **取整位置**：SQL 里**没有** `ROUND` / `CAST AS INTEGER` / 整除 / `AVG`（全 `src/main` 扫过）——分数只在 JS 的 BigInt 里算，区间末一次取整。
8. **区间边界**：`work_date >= ? AND work_date <= ?` 闭区间；跨月 / 跨年 / 单日 / 月末（2026-11、2026-02、2024-02）逐月手算；改价区间 `[生效日, 下一条生效日)` 右端不含。
9. **结余公式**（本轮台架 `repro-ledger.test.ts`，5/5 绿）：应发 63000（两天）+ 预支 10000（两笔、一笔冲销）+ 已发 20000（两笔、一笔冲销）+ 结转 0（一笔、冲销）→ **结余 33000**，逐格相等；只有结转的人也出现在表里（12345）；期间净额 31500−10000−5000 = **16500**。
10. **汇总**：`COUNT(DISTINCT worker_id)`（工地 A 59 条 → 3 人）；空天返回 `null`；行尾合计与明细同源。
11. **渲染层**：33 处 `*100` / `/100` / `Math.round` / `toFixed` **逐处判定，全部非金额**（小时↔分钟 ×60、字节 ÷1024、进度 %、缩放 %、逐日 UTC 迭代）。**金额换算 0 处**。
12. **导出**：金额一律 `Number(centsToYuan(cents))`（数值型，可 SUM），导出层不写 `/100`、不做 `Math.round`；合计在**分**里先加再换算；表结构与数据源与页面同一次 repo 调用。
