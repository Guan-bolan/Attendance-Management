## 2. 方案

### 2.0 交付形态：一次交付，5 步，6 处硬绑定（答必答问题 1）

**一次交付**。理由：备份与恢复是同一件事的两端，只交备份等于给了用户一个**读不回来的包**（比不给更糟：他会以为有备份）。所以 5 步都属于这一批，S1–S2 可以先合入主干（它们不动任何既有路径），S3–S5 必须一起到齐才能对外说「能换机」。

**但实施切成 5 步，每步做完都能启动、能跑测试、能人工验一条**。切分原则：先立底座（包格式与解压）→ 再出**安全方向**（备份，只读库、只写用户选的文件）→ 再出**不可逆操作的只读半边**（预检）→ 才动落位 → 最后文档与回归。

| 绑定 | 涉及 | 为什么不能拆 |
|---|---|---|
| **B1** | S2 内：**停收件箱 watcher** + **照片行数前置检查** + **写包** 必须同一提交 | watcher 直接写库、直接把图落进 `photos\`（`migrateDirs.ts:230-235` 的注释已写明）。只停不查：库里少一张、盘上多一张，包就自相矛盾；只查不停：检查通过之后 watcher 又吸进来一张，包内照片数与库内行数对不上，而包里那张图会变成「有图无账」。这三件事的对象是同一个瞬间，分开做等于每次都赌「检查与打包之间没人写入」。**唯一的例外是退路包**（宽松备份，跳过这条前置检查，见 §6.2）：它仍必须在停 watcher 之后写，**只跳过「少图就拒」** |
| **B2** | S4 内：**旧目录改名** + **暂存目录一次 rename 落位** + **失败反滚** 必须同一提交 | 只有改名没有落位 = 数据根**消失**；只有落位没有反滚 = 第二条 rename 失败后既没有旧库也没有新位置（`migrateDataRoot` 之所以能「失败零感知」，前提是它的旧目录一直在原地；恢复的旧目录已经被改名让位，所以反滚是这次**必须新写**的那一段） |
| **B3** | S4 内：**置 `pendingRestart`** + **`app:relaunch` 通道** + **App/Settings 的红条与不可关闭 Modal** + **写通道 `E_DB_LOCKED`** 必须同一提交 | 落位后当前进程换成了新库、但**用户的操作习惯没变**：不挡写，用户会在「已经换了的新库」里继续录，而这一步之后还要重启——D-022 的漏洞 1 就是这么来的（迁移成功后、重启前的窗口）。少任何一件，「恢复成功」就等于「恢复成功后还有一段时间能制造分叉」。**另加一条**：`app:relaunch` 虽然必须进只读白名单（等重启时它是唯一出口），但白名单同时豁免了 `migrating`（F17）→ 它的 handler 必须**自己再挡一层 `migrating`**，否则恢复落位窗口能被裸杀；同一提交里 P2 要补点名断言（F18） |
| **B4** | S4 内：**三行目录设置改写** + **`archives.path` 改写** + **`snapshots` 行清空（U14）** 必须与落位同一提交，且必须**写在暂存库上、rename 之前** | 写晚了（落位后再写）：照片全缺（IS-018 的同型故障）、档案柜全部「目录不存在」（风险 7）、快照列表一片红字；写到**旧库**上：旧库随旧目录一起被删，等于没写（P5 的教训） |
| **B5** | S3 与 S4 **跨步**：预检（S3）与落位前的二次校验（S4）必须是**同一份实现**，其中包含**档案对账**（红队第 2 条） | 两份校验必然漂移：S3 说「这个包能恢复」，S4 落位前又说不行，用户会以为软件坏了；更坏的方向是 S3 拦住了、S4 放宽了，于是「预检报错但恢复照样把数据换了」。同一份实现 = 同一个 `problems` 清单形状（照 `verifyStaged` 的 `problems: string[]` 人话口径） |
| **B6** | 每一步：**通道四处**（`constants.ts#CHANNELS` / `ipc.ts` 处理器表 / `renderer/src/api.ts` 手抄 / `READ_ONLY_CHANNELS` 判定）必须同一提交 | 前两处漏一个 `tsc` 直接报（`Record<Channel, Handler>`）+ `registerIpc` 运行期再查一次（F19）；`api.ts` 漏了 **tsc 不报**，只在运行时字段拿不到（map.md:99 的两次审核共同根因）；`READ_ONLY` 漏判会让 `migrateDirs.test.ts` P1/P2 变红，或者让恢复期的写通道漏保护（D-022 P2） |

**顺序理由（一句话版）**：S1 让「包」有确定的形状与安全的读法；S2 让用户先拿到**能救命的包**（这一步不动任何既有路径，风险最低）；S3 让「不能恢复」这件事在**动数据之前**就能说清楚；S4 才允许换库，并且换完立刻上锁；S5 把地图、交付说明、决策记录补齐，并补上第 5 道门禁。

### 2.2 各步详述

#### S1 包格式与解压底座（不接通道、不接界面）

**改哪里**

1. `package.json` 的 `dependencies` 加 `"unzipper": "0.10.14"`（**精确版本、不写 `^`**，与 `package-lock.json` 现值一致）；由实施机 `npm install` 同步 lock（本仓 `node_modules` 里已经有这一份，等于不新增下载）。
2. `src/main/types/unzipper.d.ts`（新）：只声明本功能用到的成员（`Open.file`、条目的 `path` / `type` / `compressionMethod` / `flags` / `uncompressedSize` / `compressedSize`、`stream()`）。**不引 `@types/unzipper`**：多一个 dev 依赖、多一次安装，而我们只碰这几项；`tsconfig.node.json` 的 `include` 已含 `src/main/**/*.d.ts`，声明文件自动生效。
3. `src/main/services/backupPack.ts`（新，**纯文件层**：不 `import electron`、不碰锁、不碰 watcher）：
   - 包格式常量：`manifest.json` / `app.db` / `photos/` / `archives/`、格式版本号（独立于档案包的 `ARCHIVE_FORMAT_VERSION`）。
   - manifest 的形状与逐字段校验（字段表见 §2.6）。
   - 条目名白名单校验（U11 全表，见 §2.5）：**先扫全表再解压**，一条不合就整体拒绝，`problems` 逐条人话。
   - **条目名长度判据（红队小项 1）**：`resolve(目标根, 条目名)` 的字符数 ≤ 240。**备份端与恢复端同一实现、同一阈值**：备份端用本机数据根算（算不过就拒绝备份），恢复端用**落位目标根**算（算不过就报「数据根太深 / 文件名字太长，请先把数据根改短」），并把 `maxEntryPathChars` 写进 manifest（§2.6）。理由见 §2.5 U11。
   - 只读清单：打开 zip 只读中央目录，拿到条目数组与「解压后总字节」，**不解压**。
   - 安全解压：逐条取流 → 再校验一次条目名 → 落到暂存目录；每条之间检查取消标志；累计字节超过中央目录声明总和的 1.05 倍即中止（防 zip bomb）。
4. `src/main/services/backupPack.test.ts`（新）：用 `archiver` 现造小 zip（`store` 与 `deflate` 各一份）当正样本；**另加两份正样本**：① 条目名含中文（如 `photos/2026年度/老王.jpg`、`archives/2026年度/…`）——软件自己的目录名就是中文，12 类负样本里一条中文正样本都没有属于覆盖漏洞（红队小项 2）；② 长度边界：`resolve(目标根, 条目名)` 正好 240 字符（过）与 241 字符（拒）。负样本按 §2.5 U11 的清单逐条构造。

**为什么先做这一步**：包里最危险的一段代码是「解压用户给的文件」。它不碰库、不碰数据目录、不碰界面，可以只靠单测推进；一旦接上界面，再想改它就要带着「用户已经在点恢复」的心理压力改。

**做完能验证什么**

- 自动：`npm run test` 新增用例全绿；`npx tsc -p tsconfig.node.json --noEmit`（d.ts 生效、`unzipper` 的成员被正确引用）。
- 人工：用系统「全部解压缩」打开单测产出的正样本包（`.tmp` 下），确认条目名全是 `/` 分隔的正斜杠、没有反斜杠与开头的 `/`（F7 的口径），**中文目录名解压后不乱码**。

#### S2 备份：写包 + 通道 + 界面

**改哪里**

1. `services/backupPack.ts`：写包（**流式**）。要求逐条：
   - 库：先 `checkpoint`，再 `VACUUM INTO` 到**目标 zip 同目录**的临时 `.db`（不放系统临时目录：几 GB 的库不该挤 C 盘；同目录的可用空间已经被空间检查算过），随包写完在 `finally` 删掉。
   - 照片：**以库内 `photos.rel_path` 为准**（不扫盘），按包内条目名小写去重（同一 `rel_path` 只写一份，F7），`archiver.file()` 排队、流式。
   - **档案：判据只有一条（红队第 2 条）**——逐条读 `archives` 登记行，它的 `path` 所在目录要么**进包**、要么**计入「未随包走」**，没有第三类：
     - 目录在**数据根之内**（无论在不在 `archives\` 下，例如被 `archives:repoint` 指到 `<根>\老档案\2026年度`）→ **进包**，包内固定落在 `archives\<目录名>`（三件本体：`manifest.json` + `data.db` + 该档案的 `photos\**`）。
     - 目录在**数据根之外**（如 `D:\档案`，U15）→ 不入包，计入 `archiveRowsNotInPack`。
     - 两个登记行的目录名（basename）相同 → **拒绝备份**（`E_VALIDATION`，提示先改名/重指）：包内布局与恢复时的 `archives.path` 改写都按目录名匹配，重名必然指错。
   - **为什么必须这样改**：v1 的采集判据是「在 `archives\` 下」，回执的告警判据是「在数据根**之外**」。于是「数据根内、但被 repoint 到 `archives\` 之外」的档案目录**既不收录也不计数**——恢复删旧目录时，三件本体随旧目录一起消失，而登记行随包内 `app.db` 活下来，恢复后变成「目录不存在」且文件真没了。这是全流程**唯一会静默删档案**的路径。
   - 回执里**作废**「N 份在别的盘」这个口径：统一说「N 份档案未随包走（逐条列出 id / 区间 / 原路径），恢复会删掉数据根内的旧副本，需先手工拷贝并重指」。
   - `manifest.json` 放包根（字段见 §2.6），**最后写**（这样它不会因为中途失败而留下「先声明后缺件」的包）。
   - 落盘方式：写 `<目标>.part` → 可写流 `close` 后再改名成正式文件；取消 / 失败一律删 `.part`（**绝不留下半成品 zip**，验收 3）。
2. `services/migrateDirs.ts`：**新增备份编排**（不持迁移锁，理由见 §2.3 的「备份为什么不进白名单」）。它负责：入口判定（`assertWritableNow` + **备份单飞** + **U19 盘根拒绝**）→ 停 watcher → `checkpoint` → 空间检查 → U7 前置检查 → 写包（进度帧）→ 恢复 watcher → 回包。**不收尾**：watcher 恢复与 `.part` 清理由 `finally` 保证。
   - U7 前置检查的方向区分（见 §2.5 U7）：库内照片行 **多于** 磁盘实存 → 拒绝并报「缺 N 张」；磁盘上**多出未登记文件** → 不拒，记一条 warn，并把计数写进 manifest 的 `photosUnregistered`。
   - **退路包复用这段编排时跳过「少图就拒」**（§6.2）；除此之外的拒绝条件一条不减，否则退路就不是一个合法包。
3. `shared/constants.ts`：`CHANNELS` 加 `backup:create` / `backup:progress` / `backup:cancel`；其中**后两条进 `READ_ONLY_CHANNELS`**（它们不碰库、不碰数据目录，且备份跑到一半时界面刷新要靠它们补状态，与 `migrate:cancel` / `migrate:progress` 同一判断）。**不加新错误码**（§2.9）。
4. `ipc.ts`：
   - `backup:create`：弹 `showSaveDialog`（默认文件名 `鑫淼考勤-整库备份-YYYYMMDD-HHmmss.zip`，**默认目录 = 数据根上一级**；B3），载荷允许直接给 `path`（无头验证用，与 `payroll:export` 的 `path` 同一约定）；U9 拒绝选进数据根内部；**U19：数据根是盘根时直接拒绝**（此时「上一级」就是它自己，退路与默认备份目录都会落在数据根内部，验收 2 与 4 同时崩）；**U18：恢复进行中拒绝**（文案「整库恢复正在进行，等它结束再备份」）；回执 = 路径 / 记录数 / 照片数 / 总字节 / 未登记照片数 / **进包档案数 / 未随包走档案数与清单** / `maxEntryPathChars` / 环境变量接管提示位。
   - `backup:progress`（取最后帧）、`backup:cancel`。
   - `app:showItemInFolder`：扩展名白名单从「只 `.xlsx`」改成「`.xlsx` 或 `.zip`」（**不是任意扩展名**；这个通道的安全约束是「不定位可执行文件」）。
5. `preload/index.ts`：加一个 `onBackupProgress` 订阅（推送通道名 `backup:progress`）。**这是本批唯一必须动 preload 的地方**：新增通道由 `CHANNELS` 生成、不用改，但「推送」要显式桥一次。
6. `renderer/src/api.ts`：`api.backup.create/progress/cancel` + 三个回包类型 + `onBackupProgress` 包装（与既有 `onMigrateProgress` 同形）。
7. `renderer/src/components/MaintPanel.tsx`：在「数据库快照」卡片内加**立即备份**按钮 + 进度条 + 取消 + 回执；显示「当前由环境变量 `ATT_DATA_ROOT` 接管」提示（取 `api.settings.all()` 的 `pathInfo.envDataRoot`，不新增通道）；「等重启」与「迁移中」时按钮禁用（主进程 `E_DB_LOCKED` 兜底）。

**做完能验证什么**

- 自动（`backupPack.test.ts` / `migrateDirs.test.ts` 新增）：U9 目标在数据根内 → `E_VALIDATION`；**U19 数据根 = 盘根 → `E_VALIDATION`（不产生任何文件）**；**U18 恢复进行中 → `E_DB_LOCKED`**；取消 → `.part` 消失、正式文件不存在；manifest 两组条数 = 包内实际；**档案对账恒等式**（`archives` 行数 = 进包目录数 + 未随包走数）；库内多一张照片行 → 拒绝且 detail 报「缺 1 张」；磁盘多一张未登记图 → 成功且 `photosUnregistered ≥ 1`；备份结束后 `inboxWatcherState().watching` 恢复成备份前的值。
- 人工：**验收 2**（默认目录是数据根上一级）、**3**（进度可见、回执三数、双击能解压）、**4**（包结构 + manifest 两组条数）、**5**（正式包四处 0 命中：`thumbs` / `snapshots` / `backups` / `.superseded-`）、**6**（备份前后照片文件数 N/N′ 的记录）、**18**（选进数据根 → 拒绝）、**19**（照片目录指到未插的盘 → 拒绝并报缺几张）、**21**（repoint 到数据根外 → 不收录且报数）、**25**（盘根 → 拒绝）。

#### S3 恢复预检（只读，不落位）

**改哪里**

### 2.3 与 `migrateDataRoot` 的关系（答必答问题 2）

**先定一件事：恢复的编排**就写在 `services/migrateDirs.ts` 里，解压 / manifest / 条目校验写在 `services/backupPack.ts` 里。理由：

- 两个操作共享同一组**前置状态**（收件箱 watcher、进程级 `migrating`、进程级 `pendingRestartRoot`）和同一批小工具（`ensureDir` / `removeDirQuietly` / `walkTree` / `countRows` / `openStagedReadOnly`）。放在同一个模块 = 私有函数直接复用，**不用把十几个私有函数提升成公开 API**；公开 API 一旦有了外部调用者，就再也没法保证「调用顺序」这个隐性契约。
- `backupPack.ts` 保持纯文件层（不 import electron、不碰锁）→ 可独立单测，也让「解压」这段最危险的代码与「换库」这段最危险的代码互相看不见。

**复用的私有函数（逐条给用途）**

| 私有函数（`migrateDirs.ts`） | 恢复怎么用 | 备份怎么用 |
|---|---|---|
| `assertWritableNow`（`:210-223`） | 入口第一句：等重启 / 迁移中一律拒（`E_DB_LOCKED`）；**另加 U18 的备份单飞判定** | 不直接用（备份由 IPC 的 `withMigrateGuard` 挡 + 自己查单飞；见下） |
| `stagingDirFor`（`:90-93`） | 暂存目录 = 数据根**同级**的 `<根>._migrating_<时间戳>`（同卷才能一次 rename） | — |
| `pauseInboxWatcher` / `resumeInboxWatcher`（`:236-262`） | 停；**成功后不恢复**（等重启，与迁移同一选择） | 停 → 结束后**必须恢复** |
| `throwIfCanceled` + `cancelRequested` + `cancelMigrate`（`:188-193`、`:272-274`） | 每个可中断点检查；落位开始后不再接受取消 | 备份用自己的 `backup:cancel` 单飞标志，**不共用** `cancelRequested`（否则一个取消按钮会同时打到两个操作上） |
| `assertWritableLock`（`:827-849`） | **第 9 步**抢一次写锁，挡「另一个实例在写库」；失败 → §6.3-A，当前数据不动（v1 漏了这一步，红队第 6 条） | 同样先抢一次（否则 `VACUUM INTO` 可能撞上外部写入） |
| `openStagedReadOnly`（`:852-861`） | 打开暂存库做 `integrity_check`（只读、不产生 `-wal`） | 打开临时库副本（无此需要，备份直接用原连接） |
| `countRows`（`:816-819`） | 回执的「当前库 N′ / M′」与校验用的条数 | manifest 的库内行数 |
| `walkTree` / `ensureDir` / `removeDirQuietly`（`:284-333`） | 统计与清理 | 统计与清理 |
| `pathsPatchFor`（`:967-982`） | **不复用（红队第 4 条）**：它按 `isSameDir(旧值, join(旧根, 'photos'))` 决定写空串还是绝对路径；恢复场景 `oldRoot = oldPhotoRoot = newRoot` 时 `isSameDir(newRoot, join(newRoot,'photos'))` **恒 false**（`migrateDirs.ts:971-980`）→ `photo_root` / `inbox_dir` **恒写绝对路径**。在 `ATT_DATA_ROOT` 下恢复，三行就被钉成临时根的绝对路径，**下次不带环境变量启动仍指向临时目录**（目录删了就启动失败）。恢复侧**自己决定写什么**（本版定：三行都写空串，理由见 §2.7 第 15 步），**不许声称复用旧口径** | — |
| `rewriteStagedDb`（`:1031-1097`） | **不复用（红队第 3 条）**：它只有 `UPDATE snapshots`（`:1054-1061`）、**没有 DELETE**，满足不了 U14 的「清空登记行」；而它是迁移路径共用函数，`migrateDirs.test.ts:580` 钉着 `rewritten.snapshots === 1`、`:555-557` 钉着迁移的三行写法。加参数会把两种语义塞进一个函数（迁移是「按文件名在新目录里找同名」、恢复是「清空 + 空串 + 对账」），所以**恢复侧另写** | — |
| `countFiles`（`:309-311`） | 包内文件数校验 | manifest 的包内文件数 |
| `emit` + `lastProgress`（`:195-202`） | 进度帧（`kind:'restore'`）走既有 `migrate:progress` | 进度帧走**另一条** `backup:progress`（理由见下） |

**必须新写的（不新写就会错）**

| 新写的东西 | 为什么不能套用现成的 |
|---|---|
| **落位形状：旧目录改名 → 落位 → 反滚** | `migrateDataRoot` 的目标是**空目录**，旧数据一直在原地，所以它能「失败零感知」；恢复的目标是**活的**数据根，必须先把旧目录改名让位。现有的 `rollbackLanded`（`:341-350`）是「把刚落位的目录改名回暂存名并**删除**」——恢复用它会**删掉刚换好的数据**，而且旧目录已经不在原位，删完就只剩退路 zip。所以反滚必须是**两次反向 rename**，且**不删任何东西** |
| **包校验与二次校验（同一份）** | `verifyStaged`（`:878-921`）比的是「暂存库 vs **旧库**」（表数、schema、条数全等）——恢复的语义正好相反：暂存库应当**等于包内 manifest**，跟当前库无关。硬套会把「包与当前库不一样」判成失败（而恢复的全部意义就是让它不一样） |
| **暂存库改写（三行空串 + 清 `snapshots` 行 + 档案 path 重写与对账）** | `rewriteStagedDb` 缺 DELETE、三行写法也不对（见上表两行）；而且恢复还要做「改写后逐行核对：改写后目录在暂存里不存在、又不在『未随包走』清单里 → 硬拒」（红队第 2 条） |
| **退路 zip 与它的「只留 1 份」轮转** | 迁移动用的是 `writePreMigrateSnapshot`（`:758-789`，出一份 `.db` 快照）；恢复的退路必须**是一个合法的整库包**（B4/B5），而且按 U17 比正式包**多一个 `snapshots\`**，否则「退回」还得再发明一套读法 |
| **空间检查的三项口径** | `checkFreeSpace`（`snapshot.ts:286-308`）算的是「库大小 + WAL + 1MiB」；恢复要算「退路 zip（含快照）+ 解压暂存 + 保留的旧目录」，复用它的纯函数 `assertEnoughSpace`，但需求值要自己算 |
| **`pendingRestart` 的第二种文案与 meta** | 见 F10；迁移那一路只多一个默认 kind，行为不变；**退路路径必须同时进 modal 与磁盘**（F20） |

**怎么互斥（U18；不许新造第三把锁）**

- 恢复与迁移共用**同一对模块级状态**：`migrating`（进行中）与 `pendingRestartRoot`（已换、等重启），判定顺序固定为「先等重启、后迁移中」（`assertWritableNow`，`:210-223`）。
- 恢复进入时把 `migrating` 置成 `'restore'`，结束（成功或失败）在 `finally` 里清空——与 `migrateDataRoot` 的 `:1428-1431` 一模一样的收尾。
- 于是四种交叉组合全部由既有判定覆盖：迁移中 → 恢复 `E_DB_LOCKED`；恢复中 → 迁移 `E_DB_LOCKED`；等重启 → 两者都 `E_DB_LOCKED`；正常 → 互不影响。
- **备份与恢复双向互斥（U18）**：
  - 备份侧仍**不持 `migrating`**（它会跑几分钟，锁住全部写操作不可接受），它持**单飞标志**（同一时刻只允许一个备份）。这个标志就是 U18 说的「备份持锁」那一半——它不参与任何写通道判定，**不是第三把锁**。
  - **恢复入口**：`assertWritableNow` + 查备份单飞标志 → 备份进行中一律 `E_DB_LOCKED`「备份正在进行，等它结束再恢复」（验收 24 前半）。
  - **备份入口**：`assertWritableNow`（迁移中 / 等重启）+ 单飞；恢复进行中 `migrating === 'restore'` → `E_DB_LOCKED`「整库恢复正在进行」（验收 24 后半）。
  - 判定表：备份中 → 恢复拒；恢复中 → 备份拒；迁移中 / 等重启 → 两个都拒；空闲 → 两个都放行（各自仍单飞）。
- **备份不持迁移锁**、也不进只读白名单（`backup:create` **故意不进**白名单）：迁移中 / 等重启时点备份直接 `E_DB_LOCKED`（也就满足了验收 1）。
  - 这里**驳回**需求卡「「立即备份」可进只读白名单」的许可：备份要**停 / 恢复收件箱 watcher**，而 watcher 的开关正是迁移期「不许任何人碰」的状态（D-022 漏洞 2）。放它进白名单，就有「备份在迁移中途把 watcher 又拉起来」的路径。代价只是迁移那几秒到几分钟里不能点备份——可以接受。

**指针（`data-root.json`）**：恢复**完全不碰**（U5）。迁移必须写它是因为「下次启动去哪找库」变了；恢复的路径没变，只是目录内容被换掉，`IpcPaths` 与指针目标都仍然有效（F4）。这条差异也意味着：**不要照抄 `migrateDataRoot` 的指针预写/提交/回滚三段**。

**`ATT_DATA_ROOT` 接管时**：迁移**拒绝**（`:1134-1140`，理由是「改了设置也不生效」）；恢复**必须放行**（验收 15 就是要在接管状态下恢复）。理由不对称，因为恢复根本不改「去哪里找库」，它只换内容。**代价要写进回执**：三行设置回落空串之后，下次启动若不带同一个环境变量，会回到默认文档目录（那不是这次恢复的目标）。

### 2.4 与 IS-018 / D-033 的关系（答必答问题 3）

**结论：不能抽「写回」的共用函数；只能共用「读三行」的那三行代码。**

| 维度 | IS-018 / 快照恢复（D-033 第 2 条） | RQ-008 U5 / 整库恢复 |
|---|---|---|
| 值从哪来 | **恢复前的值**：`detach` 之前读**当前库**的 `data_root` / `photo_root` / `inbox_dir` 三行（无此行 → 空串），原样写回新库 | **本机生效数据根**：不是原值，而是「启动解析出的数据根 + 它下的 `photos` / `inbox`」。原值可能是 `D:\照片`，**必须被改掉** |
| 写在哪 | 换库**之后**、在 `getDb()` 重新拿到的那个库上（与补登记快照同一时点） | 换目录**之前**、写在**暂存库副本**上（P5：不写旧库） |
| 失败怎么办 | 只 `warn`，不影响「已恢复的数据」（`:867-882`） | **必须让整个恢复失败**（写在暂存库上、落位前，失败就删暂存、当前数据不动） |
| 判断依据为什么不同 | 快照只换了 `app.db`，照片目录还是本机原来那个；「本机属性不该跟着数据回退」 | 整库恢复把**照片文件本身**也换成了包里的，而包里的照片在**包根 `photos/`** 下；只有把 `photo_root` 指到本机根下，图才找得到。同时 B6 明确要「换机后不用手工改任何设置」 |

**可以共用的只有一层**：读「三行路径设置、缺行当空串」这个读法（`snapshot.ts#readPathSettings` 已实现，`:753-755`）。抽不抽都行：抽了要在 `repo/settings.ts` 加一个读取函数并让 `snapshot.ts` 改调用（动一个刚定稿、有测试钉着的模块）；不抽就是恢复侧再写三行。

**本计划的取舍：不抽。** 理由：① D-033 第 3 条明令「两处口径一致，但实现是两套，**不许互相调用**」；② 抽出来的唯一收益是省三行读取，代价是让「恢复前的值」这个语义离开它唯一的注释现场；③ 两处的**判断依据不同**（见上表），一旦被抽成同一个函数名，下一个人很容易把它当成「一个通用写回」，从而把 U5 的「改成本机根」误用到快照恢复上——那正好会毁掉 IS-018 修好的东西。

**要在代码里互相指路**：新写的恢复侧注释里写明「这三行按 U5 算，不抄 IS-018 的值；别合并」；`snapshot.ts` 那段注释已经写了「RQ-008 走另一条路、按 U5 改写」（`decisions.md:843` 同一句话），保持不动。

| 候选 | 一句话取舍 |
|---|---|
| **A. 显式依赖 `unzipper`（选）** | 它已经在 `node_modules`、lock 与**现成 asar** 里（F16），改成显式依赖**不新增下载**；流式逐条读、支持 ZIP64；代价是 0.10.14 已停更、会带进 `bluebird` / `readable-stream@2` 等 9 个传递依赖 |

#### U2 落位形状 → **选：解压到数据根同级暂存 → 校验 → 旧目录改名 → 一次 rename 落位**

| 候选 | 一句话取舍 |
|---|---|
| **A. 同级暂存 + 两次 rename（选）** | 同卷才能一次原子 rename（`stagingDirFor` 已是现成口径）；代价是多一次改名，落位窗口（数据根不存在）从 0 变成毫秒级，崩溃后要人工把 `_replaced_` 改回去 |
| B. 直接在数据根里逐项替换（先删后写） | 不需要额外空间；代价是**没有任何原子点**：中途失败 = 库和照片各是半套，而且旧数据已经被覆盖，比现在更糟 |
| C. 解压到系统临时目录再「搬」过去 | 省数据根同级的空间；代价是跨卷 rename 会退化成复制——「一次原子落位」直接不存在，且中途失败留下半套目标目录（`stagingDirFor` 的注释已写明这个理由） |

**选 A**，并且**必须**配两条：① 旧目录的改名目标是 `<根>._replaced_<时间戳>`（同级、可辨识、好让人工恢复）；② 反滚是两次反向 rename（B2），**不删任何东西**。

#### U3 是否需新迁移 / 旧目录清理时点 → **选：不加迁移；旧目录在「落位成功 + 重开新库成功 + 置 `pendingRestart`」之后立刻删**

| 候选 | 一句话取舍 |
|---|---|
| **A. 不加迁移；落位后立刻删旧目录（选）** | 退路 zip 靠**文件名前缀**识别（`Attendance-恢复前-`），不落库，不需要表；旧目录在连接关闭后就能删（Windows 上文件句柄随 `closeDb` 释放），不给用户留两份几 G 的副本 |
| B. 加一条 `restore_history` 迁移 | 能记「什么时候用哪个包恢复过」；代价是动迁移清单与版本号（`db.test.ts` 钉着表清单），而这条记录对「退路」没有帮助——退路靠 zip 本身 |
| C. 旧目录留着，让用户自己删 | 零风险；代价是直接违反 U4 / 「不做什么」第 8 条（不许留两份几 G），而且用户不知道哪个能删 |

**选 A**，并明确两个细节：① 删之前**必须先 `closeDb`**（否则旧 `app.db` 仍被本进程打开着，Windows 上删不掉——这也是为什么顺序是「重开新库 → 置 pendingRestart → 删旧目录」）；② 删失败（外部占用 / 权限）**不改变恢复成功的结论**，只 warn + 在回执与日志里写清残留目录的绝对路径。

**驳回**「下次启动再清理」（要在 `userData` 留一个待清理标记 + 动启动流程）：多一个必须被清理的状态文件、多一次启动分支，收益只是「删不掉时自动重试」；而删不掉几乎总是因为用户自己开着里面的文件，那时报出路径比静默重试更清楚。

#### U7 备份一致性 → **选：停 watcher + 以库内 `rel_path` 为准 + 「少图拒绝 / 多图只告警」；退路包例外（宽松）**

| 候选 | 一句话取舍 |
|---|---|
| **A. 停 watcher；照片清单以库内 `photos.rel_path` 为准；库内行 > 磁盘实存 → 拒绝，磁盘多出未登记文件 → 只告警（选）** | 直接把「有账无图」挡在门外，同时不会因为照片目录里多了一张手工放进去的图就永远备不了份 |
| B. 双向严格相等才放行（U7 字面） | 语义最干净；代价是照片目录里任何一张未登记文件（手工拷进去的、`inbox` 里误放的）都会让备份**永久失败**，而用户看不出该删哪张 |
| C. 扫盘建包（把 `photos\` 整个打进包） | 不会漏图；代价是把未登记的孤儿图也打进去，包内照片数就无法与库内行数对照（U8 的两组条数失去意义），恢复后还会多出一批没有记录的图 |

**选 A**，并把方向写进回执：
- 少图：`E_VALIDATION`，detail 里给「库内 N 行 / 磁盘 M 个文件 / 缺 K 张」+ 前三张缺失的 `rel_path`。
- 多图：成功，manifest 记 `photosUnregistered`，回执里一行「照片目录里有 J 个文件没有登记，未打进包」。
- 另外：备份期间**禁止并发备份**（单飞标志），否则 watcher 的暂停/恢复会互相踩（§2.3）。
- **退路包例外（红队第 5 条）**：退路是「恢复做砸了」时唯一的安全网，它面对的场景恰恰是「照片已经丢了」。若它照抄「少图就拒」，**唯一需要恢复的机器永远造不出退路**，恢复功能永久不可用。所以退路走**宽松备份**：跳过少图拒绝，缺图只记进 manifest 的 `photosMissing`，并在回执里报数；其余（停 watcher、写包校验、空间检查）一条不减。判据写进 §6.2-B。

#### U11 文件系统细节 → **选：解压前逐条拒绝并整体中止，不做静默改名**

条目名白名单（**一条不合就整个恢复拒绝**，`problems` 逐条人话）：

| 情形 | 判据 |
|---|---|
| 绝对路径 / 盘符 / UNC | 以 `/` 或 `\` 开头、或匹配 `^[A-Za-z]:`、或以 `\\` 开头 |
| 越界 | 任一段是 `..`（与 `resolveInside` 同一口径，`paths.ts:505-519`） |
| ADS（备用数据流） | 任一段含 `:` |
| Windows 保留名 | `CON` / `PRN` / `AUX` / `NUL` / `COM1-9` / `LPT1-9`（**含带扩展名与带尾点**的写法） |
| 尾点 / 尾空格 | 任一段以 `.` 或空格结尾（Windows 会静默吃掉，落盘名与包内名不一致） |
| 控制字符 | 任一段含 `0x00-0x1F` |
| 超长 | `resolve(目标根, 条目名)` 的字符数 > **240**。**备份端与恢复端同一实现、同一阈值**：备份端用本机数据根算（算不过就拒绝备份，提示数据根太深），恢复端用**落位目标根**算（算不过就报「数据根太深 / 文件名字太长，请先把数据根改短」，**不是**「这个包坏了」）；`maxEntryPathChars` 写进 manifest，恢复预检就能提前算出会不会超 |
| 只差大小写 | 两个条目名小写后相同（NTFS 上是同一个文件，后一个会覆盖前一个） |
| 文件 / 目录同名 | 某条目名恰好是另一条目的父目录 |
| 加密条目 | 通用标志位 bit0 置位 |
| 未知压缩方法 | `compressionMethod` 不是 0（store）或 8（deflate） |
| 符号链接 / 设备条目 | 外部属性里的 Unix 类型位是符号链接 |

**正样本（v1 缺，红队小项 2）**：条目名含**非 ASCII（中文）**的包必须**通过**。软件自己的目录名就是中文（`2026年度`、`老档案`、`鑫淼考勤-整库备份-…`），而 12 类负样本里一条中文正样本都没有，属于覆盖漏洞；另加长度边界正/负样本（240 过 / 241 拒，用在源根与目标根各算一次）。

| 候选 | 一句话取舍 |
|---|---|
| **A. 预扫全表、逐条拒绝、整体中止（选）** | 一条坏条目 = 整个包不信任；当前数据一个字节不动，用户看到的是「这个包有问题，清单如下」 |
| B. 静默改名（保留名加下划线、去尾点） | 能救回一部分包；代价是 `archives.path` 的改写照「目录名」匹配（F8），改名会让**档案柜全部指错**，而且用户永远不知道自己原来的文件名变成了什么 |
| C. 只告警继续解压 | 保留最多数据；代价是半套目录落位 = 库与文件不匹配，而恢复是唯一不可逆的操作 |

**选 A**。另加一条：解压过程中累计写出的字节数超过中央目录声明总和的 1.05 倍即中止（zip bomb 的兜底）。

### 2.6 包格式与 manifest（口径，SDS 不重议）

```
<包名>.zip                 ← 默认落在数据根的上一级（B3），包根不套同名顶层目录（F7）
├─ manifest.json
├─ app.db                  ← VACUUM INTO 的一致性副本（checkpoint 之后），不含 -wal/-shm
├─ photos/                 ← 按库内 photos.rel_path 的相对路径（同一 rel_path 只写一份）
├─ archives/               ← 每个「已登记且目录在数据根内」的档案一个子目录（只在有档案时出现）
│  └─ <YYYY-MM-DD>_<YYYY-MM-DD>/
│     ├─ manifest.json
│     ├─ data.db
│     └─ photos/
└─ snapshots/              ← 【仅退路包】U17：整个 snapshots\ 收进来；正式包没有这一层
```

> **退路包（U17）与正式包只差一处**：退路包多一个 `snapshots/`，因为「退回去」必须真能退回原状（快照史跟着回来）。正式包仍不含它（B2 的体积理由不变）。退路包同样**不含** `inbox\` 里未吸入的照片与 `thumbs\`——这是 U4/U17 的既定边界，必须在交付说明与恢复回执里各写一句。
> **退路包命名**：`<数据根上一级>\Attendance-恢复前-<YYYYMMDD-HHmmss>-<SSS>.zip`（毫秒，防同一秒连续两次恢复撞名，红队第 6 条）。同目录另写一行 `Attendance-恢复退路-最近一次.txt`（内容：时间、包名、退路绝对路径），供重启后查（F20）。

manifest 字段（**U8 的两组条数都在里面**；`schemaVersion` 取**迁移常量**，不是 `user_version`）：

| 字段 | 内容 | 校验方 |
|---|---|---|
| `formatVersion` | 整库包格式版本（独立于档案包的 `ARCHIVE_FORMAT_VERSION`）；不兼容就 +1 | 恢复：不受支持 / 高于当前 → 拒绝 |
| `appVersion` | 打这一包的软件版本 | 只显示 |
| `schemaVersion` | 迁移常量（本批 = 12，F2） | 恢复：> 当前 → 拒绝（不做降级恢复） |
| `createdAt` | ISO 时刻 | 只显示 |
| `source` | 三个源目录的绝对路径（`dataRoot` / `photoRoot` / `inboxDir`） | 只显示 + 回执里给人看「这包来自哪台机」 |
| `dbBytes` | `app.db` 字节数 | 恢复：与包内实际不符 → 拒绝 |
| `photoBytes` | 照片总字节 | 恢复：与包内实际不符 → 拒绝 |
| `counts`（库内行数，U8 ①） | `entries` / `photos` / `payments` / `advances` / `carryovers` / `archives`（登记行） | 恢复：包内 `app.db` 实数对不上 → 拒绝 |
| `counts`（包内文件数，U8 ②） | `photoFiles` / `archiveFiles`（`photos/` 与 `archives/` 下的文件数）、`archiveDirs` | 恢复：包内实数对不上 → 拒绝 |
| **`archivesInPack`** | 进包的档案目录数（**红队第 2 条**的甲项） | 恢复：与包内 `archives/` 目录数不符 → 拒绝 |
| **`archiveRowsNotInPack`** | 登记行里「未随包走」的档案数（U15；数据根之外） | 恢复：`app.db` 的 `archives` 行数 ≠ `archivesInPack + archiveRowsNotInPack` → **落位前硬拒** |
| **`archiveRowsNotInPackDetail`** | 未随包走档案的 `id` / 区间 / 原路径（人话清单，回执直接用） | 只显示 |
| **`maxEntryPathChars`** | 包内最长的 `resolve(源根, 条目名)` 字符数（红队小项 1） | 恢复：用目标根重算，超 240 → 报「数据根太深」 |
| `photosUnregistered` | 备份时磁盘上多出、未登记的图片数（U7 的告警口径） | 只显示 |
| **`photosMissing`** | 【仅退路包】库内有行、磁盘缺图的张数（宽松备份的记账口径，§6.2-B） | 只显示；退路回执必须写出来 |
| **`snapshotsIncluded`** | 【仅退路包】`true` + `snapshotFiles` 份数（U17） | 恢复：为 true 时允许 `snapshots/` 存在；正式包出现该目录 → 拒绝（防两种包混用） |

**档案收录层次（U6）**：每个进包档案收 `manifest.json` + `data.db` + 档案内 `photos\`；**不收** `<档案>\backups\data-*.db`、**不收** `archives\*.superseded-*`（作废重建留下的废目录）。未登记或落在数据根之外的目录不进包，只在 manifest 与回执里报数（§2.2 S2-1）。

**`snapshots\` 与 `thumbs\` 不进正式包**（B2）：`thumbs` 可按需重建；`snapshots` 会让包体积翻倍。**退路包是例外：`snapshots\` 进包**（U17）。

### 2.7 恢复的落位时序（含每个失败分支的落点）

> 编号即顺序；「→ §6.x」是该步失败时的处理。**落位之前任何一步失败，当前数据一个字节都不动**。
> **本版 23 步**（v1 是 22 步；新增**第 9 步 `assertWritableLock`**，其余步骤整体后移一位，红队第 6 条）。

### 2.9 错误码与回包口径（本批的取舍）

- **不新增 `ErrCode`**，全部复用：包不合规 / 条目越界 / 条数不符 / **档案对账差额** / **数据根是盘根（U19）** → `E_VALIDATION`（`detail.problems` 逐条人话）；空间不足 → `E_INSUFFICIENT_SPACE`；写盘/权限/被占用 → `E_PERMISSION`；落位失败 → `E_MIGRATE_FAILED`；锁（等重启 / 迁移中 / **备份单飞中**）→ `E_DB_LOCKED`；包或文件不在 → `E_NOT_FOUND`。
  - **驳回**新增 `E_PACK_INVALID` 之类：`ipc.ts#KNOWN_CODES`（`:103-119`）与 `mapError` 还有一份运行期映射，新增一个码要同步两处，而收益只是「码更细」；`detail.problems` 已经把「哪一条不合规」说到人能看懂。
  - U18 / U19 的文案必须能区分「谁在忙」与「该改哪里」：备份单飞中 ≠ 迁移中 ≠ 等重启 ≠ 盘根，四种 `E_DB_LOCKED` / `E_VALIDATION` 文案各写一句，不许共用一句「暂时不能操作」。
- 回包形状：进度帧复用 `MigrateProgress` 的形状（`kind` 扩 `'backup'` / `'restore'`），但**推送通道分开**（`backup:progress` vs `migrate:progress`）。理由：`lastProgress` 是**一个槽**，两条操作共用一个槽会出现「备份结束后，迁移界面刷新时显示幽灵备份进度」。

## 4. 风险与对策

| 风险 | 对策 |
|---|---|
| **R1 恢复是整库替换，不可逆**（需求卡风险 1） | 五道：条目全表预检（U11）→ 完整性/条数/**档案对账**校验（同一实现，B5）→ 空间检查 → 退路 zip（写成功并回读校验后才继续）→ 落位前旧目录改名（反滚的实物） |
| **R2 换机后路径改写会改变「照片在别的盘」的习惯**（风险 2） | 回执里一句人话：「照片已放到 `<根>\photos`；原来指到别的盘的照片目录设置按换机口径改写」（B6 的必然代价） |
| **R3 包体积几个 G，备份/恢复耗时长**（风险 3） | 全程流式（不把图读进内存）；进度按文件报并**节流**（每 N 个文件或每 200ms 一帧，否则 IPC 推送会拖慢打包）；两处都有取消 |
| **R4 恢复中途断电**（风险 4） | 落位窗口只有两次 rename；崩在这个窗口的特征是「重启后说数据目录找不到」，而同级会留一个 `<根>._replaced_<时间戳>`。**人工恢复路径写进 DELIVERY**：把它改回 `<根>`，或用退路 zip 重跑恢复。**不新增启动自愈**（要判「哪个目录才是真的」，判错就是用空库顶替真库——D-020 的原始事故形态） |
| **R5 与目录迁移互相干扰**（风险 5） | 共用 `migrating` / `pendingRestartRoot` 一对（§2.3），四种交叉组合都有既有判定；不新增锁 |
| **R6 U4 的代价：旧快照史一并消失**（风险 6） | U14 已定稿：**清掉 `snapshots` 行**（第 15 步）+ 回执写「快照历史已清空，退路包在 <路径>」；DELIVERY 同步一句。退路包按 U17 **含**快照文件，所以「退回去」能把快照史带回来（验收 23） |
| **R7 包内绝对路径在换机后失效**（风险 7） | `archives.path` 由**恢复侧专用改写**按包内档案目录名重写（第 15 步）；**未随包走的行不改写、不删除**，回执逐条报「请手工拷回并重指」。恢复后这些行的目录不存在 → `verifyArchive` 抛 `E_NOT_FOUND` → 清库闸门自己会拒（`archive.ts:1763-1765`），不会误删主库；维护页/档案柜显示「目录不存在」 |
| **R8 zip slip / 恶意包** | 解压**前**全表校验（U11）+ 解压时再校验一次 + 累计字节上限（zip bomb）+ 只接受「包根有 manifest」的包（把重打包的包关在门外） |
| **R9 依赖在产物里没人验证**（v1 误写成「可能不在」） | **已由现成 asar 实证**：`node_modules` 191 条里含 `unzipper` 及全部传递依赖（F16）。真缺口是**没人执行自证** → **S5 门禁第 5 条**（`asar list` 命中 `unzipper` 并记账）；不跑 `dist` 也能在现成产物上验 |
| **R10 落位后旧目录删不掉**（被外部占用） | 不改变「恢复成功」的结论；回执与日志写绝对路径；DELIVERY 里给一句「确认新数据无误后手工删」 |
| **R11 换 DB 连接的窗口里读通道报错** | 窗口只有毫秒级，且界面被 Modal/遮罩挡着、窗口关闭被拦截（§3.1 `index.ts`）；若真被后台定时器撞上，用户看到的是一次 toast（可接受）；**不**为了它新造「暂停全部读通道」的机制 |
| **R12 备份与恢复撞在一起**（U18） | 双向互斥：恢复入口查备份单飞 → `E_DB_LOCKED`；备份入口查 `migrating === 'restore'` → `E_DB_LOCKED`；两者都不新造锁（§2.3）。备份另有单飞标志防两个备份互踩 watcher |
| **R13 数据根是盘根**（U19；`dirname('E:\\') === 'E:\\'`） | 退路会落在数据根**内部** → 恢复删旧目录时把自己删掉；默认备份目录也等于数据根内部 → 每次备份被 U9 拒（验收 2 与 4 同时崩）。**直接拒绝**：备份与恢复两个入口都报「数据根不能是盘根，请先在设置里改到子目录」，不产生任何文件；不尝试支持（§5 第 12 条） |
| **R14 退路是「假退路」**（v1 的 B2/U4/U14 组合） | 按 v1，退路只能回到「包里那一套」：快照史、`inbox\` 未吸入照片、`thumbs\` 全不回来 → §6.1 第 4 条「退回不需要新机制」不成立。**U17 已裁决：退路包含 `snapshots\`**；`inbox\` 未吸入照片与 `thumbs\` 仍不含，**必须在交付说明与恢复回执里写清**，不许让用户以为「退回去 = 一模一样」 |
| **R15 恢复中途关窗口 / 退出**（F21） | 三处拦截：窗口 `close` 拒绝 + 提示；`before-quit` `preventDefault` 且不调 `snapshotOnQuit` / `shutdownDatabase`；`snapshotOnQuit` 在恢复中/等重启(restore) 直接返回。否则 `snapshotOnQuit` 会给库拍快照并轮转删文件，「当前数据一个字节不动」在失败路径上、「恢复后数据 = 包内内容」在成功路径上都不成立 |

## 6. 回滚方案

### 6.1 五个前提事实

1. **恢复是唯一不可逆的操作**；备份、预检、设置读写都可逆。
2. 落位前，**当前数据的唯一副本一直在原地**（暂存目录只是新增的），所以「落位前失败」天然等于「什么都没发生」。
3. 落位后，当前数据的实物副本是 `<根>._replaced_<时间戳>`（第 18 步改的名）——**在第 22 步删掉它之前，反滚随时可行**。
4. 退路 zip 是**一个合法的整库包**（且按 U17 **含 `snapshots\`**），所以「退回」不需要新机制：**再点一次恢复、选它**即可（它里面的三行设置会在恢复时按 U5 改写成空串回落，所以退回去之后照片照样能打开，快照史也回来——验收 23）。
5. **退路不是「原状态的完整副本」**：它不含 `inbox\` 里未吸入的照片，也不含 `thumbs\`（U17 的边界）。这两项**必须**在交付说明（§5 恢复一节）与恢复回执里各写一句；`thumbs` 可按需重建，`inbox\` 未吸入的照片需要在恢复前自己从收件箱目录另拷一份。

### 6.2 退路 zip 的时点与写法（必须先说清）

- **时点**：包校验（第 5–7 步）**全部通过之后**、解压（第 11 步）**之前**。理由：校验不通过时不该在用户的磁盘上留下几个 G；而解压一开始就要占空间，退路必须在「开始动手」之前就存在。
- **范围（U17）**：**正式包 B2 + `snapshots\`**。退路是「恢复做砸了」时唯一的安全网，「退回去」必须真能退回原状；正式包不含快照是为了体积，退路不能省这一份。
- **宽严（红队第 5 条）**：退路 = **宽松备份**——**跳过 U7 的「少图就拒」**，缺图只记 manifest 的 `photosMissing` 并在回执报数。理由：照片已丢的机器**正是唯一需要恢复的场景**；若退路照抄严格口径，这种机器永远造不出退路，恢复永久不可用。其余拒绝条件（空间、写盘、锁、`.part` 清理）一条不减。
- **位置与命名**：`<数据根上一级>\Attendance-恢复前-<YYYYMMDD-HHmmss>-<SSS>.zip`（B5；**加毫秒**，同一秒连续两次恢复不会撞名，红队第 6 条）。
- **写法**：写 `<目标>.part` → 回读校验（重新打开列清单，确认 `manifest.json` 可解析、条目数对得上）→ 改正式名（**目标已存在就换一个毫秒再试，不覆盖**）→ **成功改名之后**才删同前缀的旧退路（保证「任何时候至少有一份可用退路」）→ **写 `<数据根上一级>\Attendance-恢复退路-最近一次.txt`**（时间 / 包名 / 退路绝对路径；写失败只 warn）。
  - **删旧失败（被占用 / 权限）只 warn**，不改变恢复流程（验收 8 的「恒 1 份」在这一刻变成 2 份，回执必须把两份的绝对路径都写出来；判据口径见 §7.3 待裁决 1）。
- **保留**：同前缀目标 1 份（B5）。成功 / 失败都保留——它是「恢复做砸了」时的唯一退路，不该被自动删。
- **路径可见性（红队第 8 条）**：退路路径出现在**四处**——① 预检回执（动手前就告诉用户会写到哪）；② 落位后的**不可关闭 Modal**（可选中复制 + 「打开所在文件夹」）；③ 恢复回执 toast（**补充**，不承载唯一信息）；④ **`Attendance-恢复退路-最近一次.txt` + 维护页常驻一行**（**重启后仍可读**）。理由：回执是瞬时 toast（F20），`pendingRestart` 是纯内存（F10），重启后没有任何入口能查。

### 6.3 三种失败情况怎么退

**A. 落位前失败**（第 5–15 步任意一步：校验不过 / 空间不足 / **抢写锁失败** / 退路写失败 / 解压失败 / 二次校验失败 / 迁移失败 / 改写失败 / 档案对账差额 / 用户取消）
- 动作：删暂存目录（`removeDirQuietly`）→ 恢复 watcher（`resumeInboxWatcher`）→ `migrating = null` → 报错（`detail.problems` 逐条）。
- 状态：**当前数据、三行设置、`data-root.json` 全部未动**；**不需要重启**（验收 14）。
- 退路 zip：若已生成则保留（无害，且是这次失败现场的物证）；若在退路写入阶段失败，删 `.part`、**保留旧的退路不动**。

**B. 退路 zip 只写了一半**（第 10 步内失败）
- 动作：删 `.part` → 恢复 watcher → 中止整个恢复 → 报错「退路备份没写成，已中止（当前数据未动）」。
- 为什么必须中止：B4 要求「动手前先把当前整库备成退路」；没有退路就落位，等于把唯一副本押在一次不可逆操作上。
- 旧退路：**不动**（先写新、后删旧，就是为了这一刻）。
- 判据（红队第 5 条）：这里的失败**不包括**「库内照片行多于磁盘实存」——那是宽松备份明确跳过的检查，只记 `photosMissing`。退路失败的合理原因只剩空间不足 / 写盘失败 / 被占用 / 抢锁失败。

**C. 落位后失败**（已 `closeDb`，数据根已被改名让位）

| 子情况 | 处置 |
|---|---|
| **C-A：第 19 步 `rename(暂存 → 数据根)` 失败** | 反向第 18 步：`rename(<根>._replaced_<ts> → <根>)` → 重开旧库（`openDb` + `setDb`）→ 恢复 watcher → 删暂存 → 报「恢复未完成，已回到原状态」。状态：与失败前逐字节一致（旧目录只是被改了个名字又改回来） |
| **C-B：第 20 步 `openDb(新库)` 失败**（新库打不开：包里的库虽然校验过，但落位后被占用/权限变了） | ① 把刚落到 `<根>` 的新目录改名成 `<根>._new_failed_<时间戳>`（**先让位，不删**——证据留在退路 zip 里，但改名这一步不能省，否则旧目录没法回到 `<根>`）；② 反向第 18 步恢复旧目录；③ 重开旧库；④ 重开旧库**成功之后**才删 `_new_failed_`（删失败只 warn 并报路径，不改变「已回到原状态」的结论）；⑤ 恢复 watcher；⑥ 报错并给出退路 zip 路径。**这一步绝不允许留下「数据根里是打不开的新库」**——那会让用户下次启动直接失败。（v1 在这里自相矛盾：既说「改名回暂存名保留证据、不删」，又说「删暂存（含新库）」，红队第 13 条） |
| **C-C：反滚本身也失败**（第二次 rename 也失败） | 这是最坏情况，**只做三件事**：① 不删任何目录、不置 `pendingRestart`、不动指针；② 日志与回执写清两个目录的绝对路径（`<根>`、`<根>._replaced_<ts>`）与退路 zip 路径；③ 告诉用户「把 `_replaced_` 那个改回 `<根>`，或用退路 zip 重跑恢复」。**不许**在这种情况下再尝试第四次 rename——每次尝试都可能把唯一副本的名字改得更乱 |

**D. 成功之后要「退回去」**（用户恢复完发现选错了包）
- 用**退路 zip** 再走一次恢复（第 6.1 条第 4 点）。这是本方案唯一支持的「反向操作」，也是为什么退路必须是一个**合法包**而不是一份裸 `.db`，以及为什么它要包含 `snapshots\`（U17）。

### 6.4 代码侧的可回退性（实施时必须遵守）

1. **B1–B6 之外不加料**：每一步只改它该改的文件；S5 之前不许顺手改 `snapshot.ts` / `archive.ts` / 迁移清单。
2. 新代码全部走新增文件 + 现有文件里**追加**分支；`pendingRestartMessage` 这类被多处调用的函数，改动要保证「迁移那一路的文案一个字不变」（有既有测试钉着 P1 的「请重启」字样）。
3. **不写调试开关**：进度/取消/预检都是正式功能，不留 `if (process.env.X)` 这种绕过分支。
4. 每步收尾都跑四道门禁；`migrateDirs.test.ts` P1/P2 不允许为了变绿去改断言（只能同步通道集合，并按 §3.2 增加点名断言）。
