## 1. 现状

### 1.1 现在这套是怎么转的

| 环节 | 现在长什么样 | 入口 |
|---|---|---|
| 发钱 | 用户自选区间 → 逐人「区间应发 / 区间预支净额 / 实发」→ 保存草稿 → **标记已发放** → 整个区间锁死 | `src/main/repo/settlement.ts`（F-11）、`src/renderer/src/pages/Settlement.tsx`（P-11） |
| 锁定 | 五类落点：考勤写通道、照片增删、预支写入、改价、归档与清库 | 见 §3.1 |
| 结余 | **不存在**。最接近的是预支页「可支额度 = 累计应发 − 累计预支」，没有「已发」这一项 | `repo/advances.ts#creditBoard`（F-10 / P-10） |
| 归档 | `manifest.json` + 独立 `data.db` + `photos/`；22 项校验；区间指纹（考勤 id 集 + 照片 id 集）；合并并 `entries` / `advances` / `settlements` 三张表 | `services/archive.ts`（F-12）、`pages/Archive.tsx`（P-12）、`pages/ArchiveViewer.tsx`（P-13） |

### 1.2 锁定的实现位置（本计划要逐条拆掉的东西）

锁不是一处开关，是 **16 个写入口 + 12 处支撑代码**：

- **考勤 8 个入口**（第一句先问锁）：`entries:create` / `overwrite` / `update` / `merge` / `delete` / `batchCreate` / `attachPhoto` / `detachPhoto`；共用 `ipc.ts#assertEntriesUnlocked`（含只为它存在的 `payloadWorkDates`）
- **照片 1 个入口**：`photos:delete`（两种 mode 都判），靠 `ipc.ts#assertPhotoUnlocked` + `photoRelatedDates` 反查这张照片关联到的所有日期（考勤侧 ∪ 预支凭证）
- **预支 2 个入口**：`repo/advances.ts` 的记一笔、冲销，写前问 `settlement.assertNotLocked`
- **改价 3 个入口**：`repo/workers.ts` 的加价 / 改价 / 删价，共用 `assertRateRangeUnlocked`（区间与任何 paid 单相交就拒）
- **归档 2 个入口**：`createArchive` 区间有 paid 单就拒；`purgeArchiveRange` 区间有 paid 单就拒（`paidSettlementsOverlapping`）
- **支撑代码 12 处**：`assertEntriesUnlocked`、`payloadWorkDates`、`assertPhotoUnlocked`、`photoRelatedDates`、`assertRateRangeUnlocked`、`lockedSettlement`、`isLocked`、`assertNotLocked`、`markPaid`、`unlock`、`saveSettlement` 的 paid 分支、`buildSettlement` 回包里的 `locked` / `lockedBy` 两个字段

### 1.3 结余相关现状

- 金额唯一出口是 `src/shared/calc.ts`，`rangePayroll` 输出「区间应发」（C 路径 + 只入不舍，D-013 / D-014），结算单与工资表都复用它 —— 结余的「累计应发」直接接管这个出口，不新写公式。
- 预支「只增不改 + 冲销」已在 `repo/advances.ts` 落地（`kind='reverse'`、`reverse_of`、冲销日期沿用原日期）—— 发放记账的「只增不改 + 冲销」照这套形状做，不另立规矩。

### 1.4 档案与清库现状

- 档案包 `data.db` 跑**同一套迁移**，所以包里的表结构与主库同版本；`manifest.counts` 记 entries / entryPhotos / photos / advances / settlements（`advancePhotos` 是 007 之后的**可选**加法字段，老包没有就不比 —— 这是本计划扩展 `payments` 条数的样板）。
- 校验项有 **22 项，名字与顺序是外部契约**（`archive.test.ts` 里逐项断言，`docs/map.md`、RQ-001 都按 22 项写）。**本计划不加第 23 项**（理由见 §2.4③）。
- `manifest.lockedSettlements` 是**顶层字段**，`archive.test.ts` 有一处「顶层键清单一个不多一个不少」的断言（`archive.test.ts:767`）—— 所以本计划原则上**不增删顶层字段**，可加的东西一律进 `counts`（`payments` 就这么加）。
  - **唯一的例外**是清库凭据 `clearance`（YG 2026-11-11 裁决 N1 明确要求「写进档案 manifest」）：它是清库那一刻产生的对账记录，不是档案内容的一部分，塞进 `counts` 会毁掉「counts 只数条数」的语义。代价是同步改 `archive.test.ts:767` 的键清单断言——那是**内部断言**，22 项校验的名单与顺序（对外契约）一个字不动。

### 1.5 基线与环境事实

- 迁移版本 **v7**，14 张表（`db.test.ts` 的表清单与版本号字面量按此写死）。
- 测试基线：24 文件 / **587 通过 / 3 跳过**（D-025 记录）。
- `main/index.ts#bootDatabase` 现在是「`openDb` → 直接 `migrate`」，**迁移前没有快照**；`SNAPSHOT_KINDS` 已含 `pre-migrate`。
- `migrate` 只应用 `version > 当前版本` 的迁移（`migrate.ts:90-91`）。**这条事实决定了「旧代码能不能开新库」**（见 §6）：旧构建的迁移清单里最大版本更小，遇到 v8/v9 库一条都不跑，照常启动。

### 1.6 本轮核对到的八条硬事实（v1 写错或没写的地方，逐条对应红队意见）

1. **启动顺序**：`index.ts:386-398` 是「先 `bootDatabase`（open + migrate）、后 `registerIpc`」，而注入目录默认值的 `setPathDefaults` 在 `registerIpc` 内部（`ipc.ts:1441`）。`createSnapshot` 内部走 `resolvePaths`（`snapshot.ts:143-144`），拿不到默认值就抛 `E_NOT_FOUND`（`paths.ts:471-475`）。**v1 说「`createSnapshot` 可直接用」是错的**；照 v1 做，所有 v1–v7 老库都会在启动阶段就失败，迁移一次都跑不到（红队 #1）。
2. **快照轮转**：`rotateSnapshots` **不看 kind**（`snapshot.ts:450-455` 的注释自己写着），保留份数就是 `snapshot_keep`（默认 7），而每次退出都留一份 `auto`（`index.ts:311-325`）。**v1 §4 的「分层轮转」不存在**；`pre-migrate` 会被启动七次挤掉（红队 #13）。
3. **取整基准**：`sumAmounts` 是「一趟精确累加、各分项各取整一次」（`calc.ts:377-409`），`map.md:75` 自己记着「月度逐月相加 ≠ 全年一次取整」。所以 `ceil(A∪B) ≠ ceil(A)+ceil(B)`，「区间内各自取整」与「全史一次取整」必然会在某个人身上差 1 分（红队 #4）。
4. **金额上限**：`validate.MAX_CENTS = 1_000_000`（= 1 万元，`validate.ts:14`）；预支另有 `MAX_ADVANCE_CENTS = 100_000_000`（= 100 万元，`advances.ts:49`）。验收 6 要存 999999 元，**照抄 1 万元那个当场挂**（红队 #17）。
5. **看板行集合**：`creditBoard` 的行 = 在职 ∪ 有应发 ∪ 有预支（`advances.ts:537-551`），**没有「只有发放」的人**；但它已经有 `asOf` 参数（`advances.ts:516-521`），这正是 `balance` 缺的那一个（红队 #11 / #24）。
6. **档案对 `settlements` 的依赖点**：第 22 项比的是 `manifest.counts.settlements`（`archive.ts:1422`），编辑前的结构闸门也比它（`archive.ts:2418`）；而 `manifest.lockedSettlements` **不参与 22 项**（只出现在生成回包 `archive.ts:1242` 与查看器）。所以「`lockedSettlements` 恒写 0」不需要动 22 项，但「`counts.settlements` 省略不写」会把第 22 项弄红（红队 #14 / #22）。
7. **性能现成判据**：300 人 × 30 天（9000 条）工资表 ≤ 5 秒（`payroll.test.ts:805-847`，`ATT_PERF=1` 手动跑）；而 `rangePayroll` 现在给每条记录生成 3 段算式文本（`payroll.ts:296-300`、`:388-425`），结余只要数字（红队 #18）。
8. **Windows 上「目录设只读」拦不住建文件**：仓里自己的结论与手法在 `paths.test.ts:492-514`（必须用 `icacls`，并且写完探针文件自证真的锁住了）；v1 的「把 snapshots 目录设成只读 → 启动中止」既验不出来，也已经被 YG 的新裁决推翻（红队 #23 / #30）。

## 2. 方案

### 2.0 交付形态：一次交付，8 步，5 处硬绑定（答必答问题 1）

**一次交付**。理由：需求 C9 明确「不锁」，与现有锁定是**互斥的两套对账语义**；两批交付会让软件在中间态同时存在「结算单锁区间」和「发放记账算结余」，用户拿哪个数去发钱说不清，SDS 也要同时维护两套写路径。YG 原话「全做」。

**但实施切成 8 步，每步做完都能启动、能跑测试、能人工验一条**。切分原则：先立数据结构 → 再立唯一口径 → 再上页面 → 才允许删锁定 → 最后动档案与清库。

| 绑定 | 哪两步 | 为什么不能拆 |
|---|---|---|
| **B1** | S2（结余 + 发放记账）必须**先于** S4（拆锁） | 锁定是「对账口径」的守卫。先把结余立起来，拆锁后才有东西替代「发过的钱和现在算的对不对」；反过来先拆锁，用户会有一段时间既没有锁、也没有结余 |
| **B2** | S3（发放与结余页）与 S4（拆锁）**同一步交付** | S4 要删 `settlements:markPaid` / `unlock` 通道与 `settlement.ts` 的整套函数，旧 `Settlement.tsx` 当场报错。所以新页面必须先把用户接过去，旧页同一提交里下线 |
| **B3** | **S4 必须同批删掉 `createArchive` 的 paid 拒绝**（v1 把它排在 S6） | 拆锁后界面上没有「解锁」了，归档却还在报「需先解锁再归档」（`archive.ts:1102-1114`）→ S4–S6 之间，所有曾有过 paid 单的区间都归档不了，提示还指向一个已经不存在的按钮。归档不删主库，提前删没有风险 |
| **B4** | **S5（档案带发放）与 S6（清库删发放 + 闸门）同一提交，不许分批发布** | 清库的删除清单里现在没有 `payments`（`archive.ts:1908-1959`）。S5 之后 S6 之前点一次清库 = 考勤删了、发放还在 → 结余 = 0 − 0 − 已发（永久负数），而档案已 `purged` 不能重清，残留行也没有任何界面能删 |
| **B5** | 清库侧 paid 拒绝的删除 与 闸门②③① **同提交（S6）** | 只删不建 = 中间态里清库既不拒 paid、也没有净额闸门 → 一次误点把没结清的钱和它的考勤一起删掉，且档案里没有发放记录可查。这是全仓唯一「删钱」的操作，不许出现半套 |

**顺序理由（一句话版）**：S1 让库能装下新数据；S2 让「钱」只有一个算法；S3 让用户看得见、点得到；S4 才允许改历史（顺带让归档不再问 paid）；S5–S6（同一提交）让档案与清库跟上新数据；S7 让钱能导出签字；S8 收尾。

### 2.2 各步详述

#### S1 结构底座（迁移 008 · 迁移前快照 · 快照轮转）

**改哪里**

1. 新迁移 `src/main/db/migrations/008_payments.sql`（**纯结构加法**）：
   - 新建 `payments` 表。列：`id`、`worker_id`（指向 `workers`，禁止删人时留孤儿）、`amount_cents`（整数分，发放为正、冲销为负）、`paid_on`（发放日期，`YYYY-MM-DD`）、`note`、`kind`（发放 / 冲销两种）、`reverse_of`（冲销指向的原记录 id，可为空）、`recorded_at`（记账时刻，ISO，C14 判重键的一项）、`recorded_on`（**记账时的本地日期**，C8「当天可改」的判据）、`created_at` / `updated_at`。
   - 索引：按 `paid_on`、按 `(worker_id, paid_on)`。
   - 约束：一笔原记录只能被冲一次（`reverse_of` 上唯一）；金额非 0 由代码校验（与预支一致，不在库里写业务断言）。
2. **008 不碰 `settlements`**：不新增「历史标记」列、不删 `draft` 行。理由见 §2.4④——加一列会让「标记说发过、`status` 说草稿」这种自相矛盾的行成为可能；而 S1–S4 之间旧页还完整可用，任何在 S1 做的数据处置都会被旧页的新操作破坏（红队 #7 的场景 A/B）。`draft` 行的删除挪到 S4 的 `009`，那时旧页与 `settlements:save` / `unlock` 已经一起下线。
3. `src/main/db/migrate.ts` 的迁移清单追加 008（`009` 在 S4 追加）。
4. **启动顺序修正**（红队 #1）：`src/main/index.ts` 在 `resolveBootPaths()` 成功后**立刻**注入目录默认值，再做建库。现在这次注入发生在 `registerIpc` 内部（`ipc.ts:1441`），晚于 `bootDatabase`（`index.ts:386-398`），`createSnapshot` 走 `resolvePaths` 会先撞 `E_NOT_FOUND`（`paths.ts:471-475`）——不修这条，**所有 v1–v7 老库都会在启动阶段失败，迁移一次都跑不到**。`registerIpc` 里那次注入保留（幂等）。
5. **迁移前快照（不阻塞启动）**：`src/main/index.ts#bootDatabase` 在 `openDb` + 登记连接之后、`migrate` 之前，当前版本在 1–7 时拍一份 `pre-migrate` 快照。**整段包异常处理：拍不出来只写一行 `console.error` 并在启动日志里注明「迁移前快照失败，继续启动」，绝不改变启动结果**（YG 2026-11-11 裁决；v1 的「拍不出来就中止启动」作废）。
6. `src/main/index.ts#startupAdvice` 的 `E_MIGRATE_FAILED` 文案加一句兜底：没有 `pre-migrate` 快照时（第 5 条允许它缺失），改用快照目录里最近一份 `auto` 快照，或整目录留存后反馈日志。

5. **闸门①（业务规则）改成「显示 + 确认 + 留凭据」**（YG 2026-11-11 裁决）：

   - **净额 ≠ 0 的提示必须点名日期陷阱**（红队 #3）：发放日期默认是今天（区间结束之后），那样记账**不会**改变这个净额。提示里直接写「还差 X 元；若要它归零，请记一笔**发放日期在 A～B 之间**的发放（日期默认是今天、在区间外，记了也不算这段的账）」。
   - **无论勾没勾，每人净额清单都要写进档案 `manifest`**：新增顶层字段 `clearance`（清库时刻、是否勾选确认、每人四数与净额、合计）。顺序是**先写凭据、后删数据**；写不进 manifest 就中止清库（文案「档案目录不可写，无法留存对账凭据」）——反过来先删再写，凭据丢了就再也补不出来。
   - 新增顶层字段要同步改 `archive.test.ts:767` 的「顶层键清单一个不多一个不少」断言（**这是内部断言，不是 22 项契约**）。`updateArchivedEntry` 回写 manifest 必须是「读原文 → 只改要改的字段 → 写回」，不许重建对象，否则会把 `clearance` 抹掉。
6. 删除范围：按 `paid_on` 删区间内 `payments`；`settlements` **不再删**（历史单与区间无因果关系，删掉等于删「曾发过钱」的证据）；`deletedSettlements` 字段保留恒 0（界面不再展示）。
7. 界面：`pages/Archive.tsx` 的清库确认弹窗（`:239 / 245 / 487 / 620-621 / 638` 那几处）改成三块——要删的条数（考勤 / 预支 / 发放 / 照片）、**每人期间净额表**（红队 #20 的落点）、确认勾选。「草稿结算单」「跨区间结算单保留」「删除结算单」「manifest 的结算单展示」一并删掉。

**与现有「区间指纹 + manifest 比对」怎么衔接**（必答问题 4 的核心）
- 四个问题互不覆盖，所以是四道不是一道：指纹问「档案装的是不是主库现在这一批」（id 集合）；闸门② 问「主库有没有档案不知道的数据」；闸门③ 问「这批数据的内容是不是跟档案里一样新」；闸门① 问「账结清没」。
- 为什么闸门② 排闸门① 前面：先证明「这批数据有副本」（可逆性），再谈「账结没结清」（业务规则）。顺序反了，用户会被一句「先去结清」推着去结清，而真正的问题是档案里根本没有这笔钱。
- 已有闸门一个不动：档案存在 → 22 项校验 → 指纹比对 → 主库不比档案多。新闸门插在指纹之后。
- **为什么不把「期间净额」放进 S3 的结余表**（红队 #20 建议的落点）：C10 只给了「这段时间两列 + 总结余」，同一屏再出现一个也叫「还差多少」的数，就会出现「结余 / 期间净额」两套口径（D-003 记过这种死法）。需要这个数的场景只有清库，所以放在清库确认弹窗，并且四个数都摊开给人看。

**为什么这么切**：B4 + B5。删 paid 拒绝、建三道闸门、删发放、写凭据必须同一提交 —— 这是全仓唯一「删钱」的操作。

**不要做什么（这条写进 SDS）**：**不给 `verifyArchive` 加第 23 项**。22 项是被 8 处断言 + `map.md` + RQ-001 钉住的外部契约；而 payments 的比对是「主库 ↔ 档案」的跨库比较，塞进「包内自洽」校验里会把两种语义混在一起（D-015 危险点 3 已经因为混语义返过一次工）。

**做完能验证什么**

1. 某人净额 ≠ 0 → 清库返回「待确认」而不是硬拒；不勾选直接调清库 → 服务层拒绝（带「需要确认」标记），主库一条不少、档案一个字节没动（验收 16 前半的新形态）。

3. **日期陷阱用例**：某人差 500 → 记一笔 `paid_on = 今天` 的发放 → 净额**不变**（仍 500），且提示里给出那句话；把日期改成区间内 → 净额 0，不勾选也能过（红队 #3 的自动化证据）。

11. 手工删掉档案库里一行 `payments` → 清库被闸门② 拦（集合包含关系不成立）。
12. 老档案（无 `paymentIdsHash`、区间内主库 0 发放）→ 清库正常完成；若主库有发放 → 被闸门② 拦。

### 2.4 五个关键取舍（答「理由 + 否决了什么」）

**① 新建 `payments` 表，不复用 `settlements`（必答问题 5）**

- 选：新表 + `settlements` 保留为只读历史；历史单按 `status='paid'` 派生，**不加「历史标记」列**（理由见 ④）。
- 理由：一张发放是「工人 + 金额 + 发放日期 + 备注 + 记账时刻」，**没有区间**（C4）；`settlements` 的行以 `period_from / period_to` 为身份，`status` 是「草稿/已发放」的状态机。硬塞进去要让区间列同时表示「区间」和「一天」，让状态列同时表示「草稿」和「已发放发放」。更要紧的是需求约束已经写明「period_* / status / paid_at / unlocked_at 废弃但不删列」——复用等于让「废弃列」重新有意义，与需求字面直接冲突。
- 代价（认了）：多一张表，归档采集 / counts / 合并 / 清库 / 指纹各加一套；`settlements` 成为永久死表（很小，且老档案还要按原样读）。
- 否决了什么：否决复用 `settlements` 加列当发放表（判重键与状态机互相污染、老 paid 行与新发放行混在一张表里，任何 `SELECT *` 都要先过滤）；否决「删表重建」（需求禁止删列，且会让老档案与主库结构不对称）；否决「发放记进 `advances` 用负号表示」（预支与发放是两种钱，混表会让「累计预支」与「累计已发」再也分不清，而 C1 的公式正是靠这两项分开）。

**② 结余只有一个实现：`repo/balance.ts`（必答问题 5 的邻座）**

- 选：结余表、预支页可支额度、导出印的那行结余，三处都调同一个函数；页面只做格式化与整数域求和。
- 理由：C1「只有一处实现」；D-003 决策三的教训（同一个词三处不同义，界面换个页面数字就对不上）。
- 否决了什么：否决在 `payroll.ts` 里加结余（工资表是月度、不含预支与已发，混进去会被误读成账本）；否决页面自己减（渲染层不许算钱 —— 旧 `Settlement.tsx` 的头注释把这条写死，该文件在 S4 下线，规则本身留在 `map.md` 与新页面注释里）。

**③ 档案包带 `payments`，但不把 `verifyArchive` 从 22 项扩到 23 项**

- 选：发放条数进 `manifest.counts`（可选字段）；校验项保持 22 项；「主库 ↔ 档案」的发放比对放在清库闸门②。
- 理由：22 项的名字与顺序是被 8 处断言 + `map.md` + RQ-001 钉住的外部契约（界面上就是「校验明细」那张表）；而「主库有没有档案不知道的发放在」是跨库问题，不是「包内自洽」问题，塞进 `verifyArchive` 会把两种语义混在一起（D-015 危险点 3 已经因为混语义返过一次工）。
- 否决了什么：否决「加第 23 项 `payments 条数`」（要改 8 处断言、`map.md`、验收卡与 22 项名单契约，换来的能力闸门② 已经覆盖）；否决「只靠指纹不看条数」（指纹回答「是不是同一批」，答不了「有没有多出来」）。

**④ 迁移拆成 008（结构）+ 009（数据），历史单用 `status='paid'` 派生（红队 #7 的正解）**

- 选：008 只建 `payments` 表与索引，**不碰 `settlements`**；`settlements` 里 `draft` 行的删除做成 009，落在 S4。
- 理由：迁移只在启动时跑一次，而 v1 把「删 draft、标历史」放在 008，等于在**旧页还活着**的时候清账 —— S1 到 S4 之间旧页还能保存草稿、还能把 paid 解锁回 draft，清完立刻被写回脏数据（红队 #7 场景 A/B）。把数据处置推到「旧页与 `save`/`unlock` 通道一起消失」的那个提交，才是唯一没有窗口的时点。
- 理由（为什么要派生而不是加列）：加一列「历史标记」意味着「标记」与 `status` 两处状态，而 `unlock` 只改 `status`（`settlement.ts:484-500`）—— 立刻出现「标记说发过、`status` 说草稿」的行，提示条会照着标记念瞎话。用 `status='paid'` 当历史单的判据，两者永远一致，且**不加列就不用改老库结构**。
- 代价（认了）：多一个迁移文件、多一次启动时的数据清理、`db.test.ts` 的版本字面量要写到 9。

**⑤ 清库闸门① 用「全史 − 区间外」，并把每人清单写进 manifest（红队 #4 的正确取整口径 + YG 的凭据要求）**

- 选：闸门① 的「区间应发」= 全史累计应发 − 区间外累计应发，两段都走同一套「一趟精确累加、只取整一次」；「区间外」把区间前、区间后合成一次累加。
- 理由：结余本身是「全史一趟取整」（`calc.ts:377-409`）。若闸门用「区间内各自取整」，`ceil(A∪B) − ceil(A) ≠ ceil(B)` 会差 1 分，清库后同一个人的结余就变了，验收 17 直接挂。这不是措辞问题，是算法问题，只能改取整基准。
- 理由（为什么凭据必须进 manifest）：清库是全仓唯一不可逆的删钱操作，而「这段时间到底结清没有」程序无从判断（C4 明确发放不绑区间）。把每人四数与「用户勾了确认」一起写进档案，等于给这次删除留一张可复核的凭据；只写在主库或日志里，档案被拷走后凭据就跟不上了。
- 代价（认了）：清库从此要求档案目录可写（只读介质上清不了库，会给出明确文案）；manifest 多一个顶层字段，要改 `archive.test.ts:767` 的内部键清单断言。

## 4. 风险与对策

| 风险 | 对策 |
|---|---|
| **历史账目变成可变的**（RQ 已知风险 1）：改一条旧考勤会改变「当年发的够不够」 | 这是 YG 的取舍。落地：结余实时算 + 导出留痕（印「截至今天结余」）+ 循环快照；界面让「应发按当前价算」可见（工资表已如此）；**归档后改动还有闸门③ 兜住**（不许悄悄清库） |
| **追溯改价让结余跳动**（风险 2） | 改价前 `manual` 快照保留（拆锁后这是唯一退路）；改价提示照旧说明「追溯重算」；改价写进考勤行的 `updated_at` 会被闸门③ 看见 |
| **清库不可逆**（风险 3） | 闸门②（数据有副本）+ 闸门③（副本是新的）+ 闸门①（期间净额，显示 + 确认 + 凭据）+ 清前全库快照 + dryRun 先跑三道；全部在服务里，不靠界面自觉 |

| **闸门③ 只靠时间戳**（新增风险） | 系统时钟被回拨会漏判；第二道是闸门① 的净额（内容被改过，净额通常会变），第三道是用户手上的导出凭据。不额外加内容哈希（三张表全量哈希的代价与收益不匹配） |

| **22 项校验契约被顺手扩** | S6 明确否决第 23 项；清库闸门独立成函数；`archive.test.ts` 的名单断言不改 |

## 6. 回滚方案（答必答问题 8）

### 6.1 两个前提事实

1. **迁移只升不降**：`migrate` 只应用 `version > 当前版本` 的迁移（`migrate.ts:90-91`）。所以 **v9 库 + 旧代码能正常启动**：旧构建的迁移清单最大到 007，遇到 v8/v9 一条都不跑，`payments` 表与 `clearance` 字段它不认识、不查就不会报错。反过来 v7 库 + 新代码会先拍 `pre-migrate` 快照再升到 v8（S1）／v9（S4）。
2. **回滚的不可逆点只有两个**：① `draft` 结算单行被删（草稿本就可重算，无实质损失）；② 008 之后记的发放，**旧代码看不见**（不进结算单、不进工资表）。

### 6.2 回滚第一步（强制，且要有兜底）

**先导出 `payments` 全量，把文件路径写进回滚记录**，再动代码。这份导出就是「旧代码世界里那批钱」的唯一凭据；不导出就回退，等于把钱从账上抹掉（数据还在库里，但没有任何界面能让用户看见它）。

**导不出来的时候**（红队 #27 列的三种情形，三种都真实存在）：
1. 新构建启动即失败（最需要回退的时候）→ 通道根本调不到 → 用第 2 档。
2. 工资发放页因 `balance` 报错打不开 → 用第 2 档（这一档**不经过任何应用代码**）。
3. 已经先恢复了 `pre-migrate` 快照 → 库里 `payments` 已回到迁移前（老库就是空表）→ **顺序必须是「先导出、再恢复」**，这条写死在回滚步骤第一行。

第 2 档：用任意 SQLite 客户端直接打开 `app.db`，把 `payments` 表连列名一起导出 CSV（操作步骤写进 `DELIVERY.md` 的「回滚」小节；本计划不贴语句）。导出前先关掉软件，避免读到 WAL 里的半截状态。

### 6.3 从后往前退

| 退哪一步 | 怎么做 | 退完的状态 |

### 6.4 回退后必须做的两件事

1. **告诉用户锁定回来了**：`paid` 行还在，回退后旧代码会按 `[period_from, period_to]` 重新锁区间，改价与考勤会重新被拒 —— 这是回退的预期代价，不写清会被当成新 bug。
2. **用 6.2 的导出人工补账**：`settlements` 里没有草稿可对照，所以「这段时间发了多少」只能按导出补记一张结算单或手工记账。

### 6.5 代码侧的可回退性设计（实施时必须遵守）

- 把 **S1（迁移+备份）**、**S2（新表读写）**、**S4（拆锁）** 做成三次独立、互不掺杂的改动。S4 的主体是纯删除，**唯一的新增是 `009` 那个独立的数据清理迁移文件**（回退时连文件一起 revert，不散落在别的改动里）—— 它是这几步里唯一需要精确反向的提交。
- **S5 + S6 是一个提交**（B4），回退也是整体反向：别把「档案带发放」和「清库删发放」拆成两次 revert，那会在中间态留下「清库删了考勤、发放还在」的负结余。
- 新增的通道、函数、页面都放在新文件里，旧文件只做「调用删除」或「一行改指向」，让回退可以用 `git revert` 而不是逐行手改。

## 7. 与需求卡的冲突

> 只记录，不改需求卡。7.1–7.5 已由 §7.6 裁决覆盖（v2 又改了 7.1 的形态，见 N1）；7.6 里 N1–N3 是 YG 2026-11-11 本轮新裁的。所有需要回写到需求卡的条目集中列在 **§10**，本计划不自己改卡。

### 7.1 【实质冲突】C15① 的「该区间结余」在 C1 / C10 的定义里不存在

- C1 把结余定义为 `累计应发 − 累计预支 − 累计已发`，C2 规定三个累计都按「日期 ≤ 本地今天」，C10 又明确「时间范围只是筛选窗口，**不改变结余算法**」。也就是说：**结余是全库口径，没有「区间结余」这个东西。**
- 但 C15① 要求「清库前若该区间有人结余 ≠ 0 → 拒绝清库」，验收 16 也按「在该区间结余 ≠ 0」取证。两处不可能用同一个函数实现。
- 反推：只有按「区间口径」（区间应发 − 区间预支净额 − 区间内发放）才可能让**验收 17**（清库前后未归档部分结余数值不变）成立 —— 因为清库会同时删掉该区间的应发与发放，只有该区间净额为 0 时总结余才不动。
- 本计划的默认处理：清库闸门用**区间口径**，在代码里标成「清库闸门的区间净额」，**不与 `balance` 的「截至今天总结余」共用一个名字**，界面上也不叫「结余」（叫「这段还没结清」），避免出现第二个「结余」。
- 已裁决：用**区间口径**（§7.6 的 7.1 行）；判定动作按 **N1** 改成「显示 + 确认 + 留凭据」，不是硬拒。

### 7.2 【实质冲突】「迁移只许加法」与 C16「删掉库里那张 draft 结算单」

- 约束段写「新增迁移只许加法」，C16 又要求删掉 `draft` 结算单。若「只许加法」管的是**结构**（不删列、不删表），那删数据行不违背；若它管的是**数据**，那 C16 只能改成「保留并在界面隐藏」。
- 本计划的默认处理：**结构只加、数据按 C16 处置**。理由：draft 单是「还没定的中间产物」，迁移后既无页面可看、也无函数可读，留着只会变成没人认领的垃圾行；而 `paid` 行按 C16 明确保留并标历史。
- 已裁决：**结构只加、数据按 C16 处置**（§7.6 的 7.2 行）；并且拆成两步 —— 008 只建表，删 draft 做成 009 落在 S4（§2.4④ 说明为什么不能提前）。

### 7.3 【命名冲突】C12 的「结算单页」在拆锁后不再叫这个名字

- C12 说「未结清提示只在**结算单页**」，而「做什么 §11」要求删掉结算单页的「标记已发放」「解锁」与整个区间选择 —— 那个页面的职责已经变成「发放 + 结余」。
- 已裁决：标签用「**工资发放**」（§7.6 的 7.3 行）。页面保留原导航位置，`map.md` 记明「C12 所说的『结算单页』= 工资发放页」。**否决**保留「结算单」这个标签：页面里已经没有任何结算单，标签会骗人。

### 7.4 【口径歧义，按默认处理】C12 的「跟当前筛选联动」是否包含时间范围

- 若包含：切到上月时「未结清人数」会变成「按上月口径算的人数」，但那与「结余按今天算」矛盾（一月的数字会随筛选窗口跳）。
- 本计划默认：N / M **只跟按人筛选与「含停用工人」联动**，**不随时间范围变**（因为它们是「截至今天」的口径）。C10 的「时间范围只影响这段时间两列」优先。

### 7.5 【验收覆盖面，建议补一句】验收 19 没提「历史单不计入结余」

- C16 明确「老 paid 单标历史、**不计入结余**」，验收 19 只写「每人结余按考勤与预支正确算出」，没提历史单。
- 本计划按 C16 实现（历史单不进结余），验收时额外核一条「历史单金额没有进累计已发」。建议在验收卡里补这一句，不改需求卡正文。
