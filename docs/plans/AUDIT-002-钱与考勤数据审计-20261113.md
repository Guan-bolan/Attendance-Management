## 3. 已修的两类

### 3.1 【真 bug · 会多算钱】合并时结转的**冲销行**被「区间闸」吞掉

**现象**（D 路挖出，主会话独立复现）：档案包里是「+63000 结转＋它的 −63000 冲销」（净 0），主库只剩那条 +63000（例如整库恢复到了冲销之前的备份）。合并之后**主库仍是 63000**，冲销行一条都没进来 → **多算 630.00 元**。

**根因**：`services/archive.ts` 的合并有三道结转闸。第三道「区间闸」的键是 `(工人, source_from, source_to)`，**冲销行的来源区间与它要冲的原记录必然相同**，所以必然命中；一旦命中就走 `continue`，冲销行永远进不来。

**修法**（1 行）：区间闸只拦「新的一段账」，`row.reversed_by !== null` 的冲销行不走区间闸——它的正确性由上面已有的 `reversedBy` 映射保证（映射不出就 `continue`，**绝不写 `null`**）。

**反证**（我亲自做的，不是听 D 说）：把修复临时改回去 → 新增用例变红
```
AssertionError: expected +0 to be 1     // insertedCarryovers 修前 0、修后 1
```
装回修复 → 绿。回归用例落在 `src/main/services/archive.test.ts` 的「⑥ AUDIT-002 回归」。

## 4. 待你裁定的 8 项（都没改代码）

### 4.1 【待裁定 · 会堵住功能，不是算错】清库结转的单笔 100 万元上限

三路（A / D / G）独立撞到同一处：`carryovers.ts:142` 的 `Math.abs(value) > 100_000_000` 拦的不只是手工录入，**系统生成的结转也被拦**。

- D 的实测：日薪 1 万元 × 101 天无发放 → 期间净额 101 万元 → `createCarryovers` 抛 `E_VALIDATION` → **整个清库事务回滚**（数据不丢，但清库做不下去，提示是「单笔结转金额不能超过 1000000 元，请核对后再记」——没有出路）
- 真实规模：日薪 600 元需 1,667 天（≈4.6 年）才撞到；一个春节年（354 天）撞到需 ≥2,825 元/日；费率硬上限是 1 万元/日
- D 还实测了**拆两段清库可以走通**（50 万 + 51 万，两段都 purged，结余不变）

**建议**：让清库生成的结转绕过这个上限（上限只留手工录入），或在闸门① 就明确报「本区间净额超上限、请拆区间」。

### 4.2 【待裁定 · 口径缺口】加班折算没有下限

`calc.ts` / `settings.ts` / `workers.ts` 三处都只要求「正整数」。实测折算设成 **1 分钟**：

| 场景 | 加班费 |
|---|---|
| 日薪 300 元、24 小时加班（1440 分） | **432,000.00 元**（默认口径的 **480 倍**） |
| 日薪取上限 1 万元/天 | **14,400,000.00 元** |

界面挡住（设置页与覆盖输入框都是 `min=0.5h / max=24h`），但**仓库层不挡**，经 IPC 或脚本可以写进去。

**建议**：给 `overtime_unit_minutes` 加区间校验（30–1440，与界面一致），`settings` 写与工人覆盖写共用同一个断言。

### 4.3 【待裁定 · 界面缺入口】清库产生的结转，在界面上无处冲销

`Archive.tsx:166` 的注释写着「结转的冲销入口在『工资发放』页（`api.carryovers.reverse`），这里只指路」，而 **`src/renderer/**` 里 `carryovers.reverse` 的调用数是 0**（只有 `api.ts` 的声明）。而清库的重复结转检查报错文案正是让人「先去结转页冲销原来那条」。

**后果**：用户被「这段账已经结转过」挡住时，界面上**找不到**解除它的按钮。

**建议**：在「工资发放」页结余表的「看明细」展开区里，给每条结转加一个「冲销」按钮（`api.carryovers.reverse` 已经能用）。

### 4.5 【已修】`from > to` 用的是未 trim 的原串

`payments.ts:listPayments` 与 `advances.ts:listAdvances` 现在先用 `assertDate` 拿到**trim 后的值**，再用它比大小。

**为什么原先是漏洞**（两步都核过）：① `assertDate` 内部 `value.trim()` 后才校验、并返回 trim 后的串；② 而比较用的是 `q.from > q.to` **原始串** → `' 2026-11-30' < '2026-01-01'`（空格 0x20 < `'2'`）**不抛错**，落库参数却是 trim 后的合法闭区间 → 静默返回**空表**（本该报错却没报）。其余入口（`balance` / `payroll` / `summary`）本来就用断言后的值比，只有这两处漏了。

### 4.6 【待裁定 · 显示口径】`formatUnits` 与 Excel `0.00` 在「半分位」上分家

`unitsMicro = 75000`（= std 480 时按小时录 36 分钟，**真实可达**）：
- `formatUnits(75000)` = `0.08`（十进制四舍五入）
- 单元格写 `0.075`、`numFmt='0.00'`，Excel 按二进制舍入显示 `0.07`

**存的值无损**，只是**同一个工数在页面和 Excel 里显示成两个数**。可达组合：遍历 std 60–1440 × 出勤，共 1,680 组命中（默认 std=540 命中 **0** 组）。

**建议**：导出写 `Number(formatUnits(unitsMicro))`，让两处永远同字（代价：单元格值变成 2 位小数）。

### 8.1 复审抓到的最大一条：**我引入了一个新 bug**（A 路与 B 路各自独立发现）

**现象**：合并时同一笔结转会被**冲两遍** → 结余从 0 变成 **−63000 分（−630.00 元）**。

**成因**：我为了修「冲销行被区间闸吞掉」，让 `reversed_by !== null` 的行跳过区间闸——但上面那道 `byKey` 判重键**含 `created_at`**，所以「同一笔原结转、另一次冲销」键不同，会被当成新行插进来。而 `carryovers.reversed_by` 的硬规则是「同一笔原结转只许有一条冲销行」。

**触发条件（很窄，但不是理论）**：主库有未冲销结转且该段考勤已删（= 清库后的真实状态）+ 档案里同时有结转与它的冲销。日常「清库 → 归档 → 合并」路径踩不到。

**修法**：插冲销行前查**实时库** `SELECT id FROM carryovers WHERE reversed_by = ?`，命中就跳过并进冲突清单。**必须查实时库**——`carryoverState` 是合并前的快照，看不到本次合并里「自动冲销段」刚在同一事务内插进去的行。

**反证**（我亲手做）：把守卫关掉 → 新用例 ⑦ 变红，报 **`expected -63000 to be +0`**；装回即绿。用例：`services/archive.test.ts` 的「⑦ AUDIT-002 复审回归」。
