## 现象

在设置页改过照片目录（例如指到 `D:\照片`）的库上，恢复一份「改路径之前」拍的旧快照：

1. 恢复看起来成功（界面提示已恢复、数据回到那个时点）；
2. **重启后照片全部显示缺失**——因为 `photo_root` 跟着快照回退成了旧路径，新库去那儿找照片，那里没有；
3. 数据根（`data_root`）与收件箱（`inbox_dir`）同理。

与之同源、但代价小得多的一条（YG 已选择「照现状接受」）：`snapshot_keep` 也回退，导致下一次退出按回退后的份数轮转、**真删**多出的快照，界面无提示。

## 坐标

- 主犯：`src/main/services/snapshot.ts#restoreSnapshot`（`:759-841`）—— `replaceDbFile` 用快照文件整体换掉 `app.db`（`:704-712`），库里的 `settings` 表随之回退。
- 设置读取处：`src/main/services/paths.ts#resolvePaths`（`:471-488`）—— `data_root` / `photo_root` / `inbox_dir` 三项「库里有值就以库为准」，所以回退即刻生效。
- 设置键定义：`src/shared/constants.ts#SETTING_KEYS`（`:173-178`），含「空串 = 未设置，回退默认值」口径。
- 轮转读份数：`src/main/services/snapshot.ts:595`（`getNumbers(db).snapshotKeep`），调用点 `src/main/index.ts:439`（退出）、`src/main/ipc.ts:1039` / `:1056`。
- 既有先例（同哲学）：`src/main/services/migrateDirs.ts#rewriteStagedDb`（`:1031-1097`）把三个路径设置写进**新库副本**；`services/archive.ts#mergeArchiveIntoMain` 回包 `settingsSkipped: true`。

## 根因

快照是**整个 `app.db` 的副本**，而 `settings` 表就在这个库里。所以「恢复快照」= 连设置一起回到那个时点。这不是本次改动引入的缺陷，是结构决定的既有行为；`DEFAULTS.snapshotKeep` 从 7 降到 3 之后，它的后果才第一次变得可见（回退值与用户设定值之间出现了差距）。

## 影响范围

- 任何「改过三项目录设置 → 之后恢复过旧快照」的库：照片打不开、数据根指向别处。
- 任何「显式存过 `snapshot_keep` → 恢复过早于这次保存的快照」的库：份数静默回退 + 真删快照。
- **不受影响**：从未改过设置（`settings` 表为空）的库——回退前后都取默认值，行为一致。本机真实库目前正是这种形态（`settings` 表 0 行）。
- 数值型设置（标准工日 / 加班折算 / 餐补）同样会回退，但**本次明确不处理**（见 D-033 第 2 条的范围限定）。

## 修复建议

照 `docs/decisions.md` D-033 的裁决：

1. **三项目录不回退**：`restoreSnapshot` 在 `detach(db)` **之前**读出 `data_root` / `photo_root` / `inbox_dir` 三行的原值（无此行 → 空串），在 `reopen` 之后、补登记快照（`:830-831`）那一步前后，把这三行写回新库。写空串即「用默认」，与既有口径一致。
   - 落点天然：现有代码已经在换库后做「把刚用到的两份快照补登记回新库」（`:828-839`），三行设置的回写与它是同一形状、同一时点。
2. **`snapshot_keep` 不回退**（= 保持回退行为，不改代码）：但要 ① 在 `docs/DELIVERY.md` 的恢复说明里写明；② 补测试钉住，防止以后被无意改掉。
3. **范围严格限定**：只动这三行路径。不许顺手把数值型设置也纳入（属范围蔓延）。

## 复现路径

1. 用一个临时数据目录（`ATT_DATA_ROOT` 指到 `.tmp` 下，**禁止碰真实目录**）起软件。
2. 在设置页把照片目录改到一个**与默认不同**的位置（例如 `<tmp>\photos-b`），保存。
3. 拍一份快照 A（此时库里三行设置是「默认」，因为还没改）。
4. 再把照片目录改成第三个位置（例如 `<tmp>\photos-c`），保存。
5. 用快照 A 恢复。
6. 重启后看设置页：三行设置回到「默认」（第 3 步的状态），而照片实际在 `photos-c` → 照片全缺失。

## 修复记录（2026-11-12）

### 改法

`src/main/services/snapshot.ts#restoreSnapshot` 分两步：

1. **换库前抄**：在 `detach(db)` **之前**用新增的 `readPathSettings(db)` 把 `data_root` / `photo_root` / `inbox_dir` 三行原值读出来（此时读的还是当前库 = 用户此刻生效的值）。必须在 `detach` 之前——换完文件旧连接就没了，读不到「恢复前」的值。
2. **换库后写回**：`reopen(dbPath)` 之后，在既有「把刚用到的两份快照补登记回新库」那一段的**同一时点、同一形状**，用 `setMany` 把三行写回新库。写回失败**不致命**（数据已恢复成功，只降级为「设置回到快照时点」的老行为，只记 warn）。

`readPathSettings` 的口径：**该行不存在 → 空串**（不是 `undefined`）。与 `SETTING_KEYS` 注释「空串 = 未设置，回退默认值」一致；把 `undefined` 写进去会变成字符串 `"undefined"`，比不写还坏。空串写回 = 「用默认」，`resolvePaths` 的 `getString` 同一口径。

### 明确没有做的事

- **`snapshot_keep` 仍回退**：不改代码。YG 2026-11-12 选择「照现状接受」（D-033 第 1 条）。代价是恢复后份数跟着回到快照时点，下次退出按那个数轮转、**真删**多出的快照，界面无提示——已在 `docs/DELIVERY.md` §5.1 写明，用户必须知道。回退行为本身有用例钉住（`snapshot.test.ts:485-502`），防止以后被顺手改成「不回退」。
- **数值型三项仍回退**：标准工日 / 加班折算 / 餐补默认值同样跟着快照回到那个时点，本次**有意不处理**（D-033 第 2 条的范围限定：只动三行路径，纳入数值型属范围蔓延）。有用例钉住这个「有意」（`snapshot.test.ts:470-483`）。
- 未改 `RestoreResult` / `SnapshotRestoreResult` 回包形状（改 IPC 形状要同步渲染层类型，收益只是多一个 UI 提示，不值当）。成功/失败看日志：成功 `[snapshot] 已按恢复前的值写回三项目录设置：…`，失败 `[snapshot] 恢复后写回三项目录设置失败（不影响已恢复的数据）：…`。
