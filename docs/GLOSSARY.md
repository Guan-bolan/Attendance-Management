# 术语表

> 这个项目里的词，有一半是业务词（人事和工人嘴里的说法），一半是内部词（代码里的说法）。**同一个概念两边叫法经常不一样**，新人最容易卡在这里 —— 比如界面上叫「工数」，代码里叫 `units_micro`，数据库里存的是 `units_micro` 的整数，而需求卡里叫「工」。
>
> 这份表按「你会在哪里遇到它」组织：先讲业务概念，再讲内部机制，最后是状态与枚举。**每条都标了真实出处**，对不上就是文档过期了，以代码为准。

## 一、业务概念

### 工 / 工数 / 出勤工数

工人干活的计量单位。干满一天 = 1 工，只干上午或只干下午 = 0.5 工，不足半天按小时折算。

- 需求卡叫「工」，界面叫「工数」，代码叫 `unitsMicro` / `units_micro`
- 内部存储是**整数**，真值 × 10⁶（`MICRO = 1_000_000`）：18.5 工存成 `18_500_000`
- 为什么用整数：浮点数累加会漂，工数要参与金额计算，一分钱都不能错
- 计算：`unitsMicro = round(attendMinutes × 1_000_000 / stdMinutes)`，见 `src/shared/calc.ts`
- 界面显示固定 2 位小数（`formatUnits`）：`18_500_000` → `"18.50"`

**注意**：工数在**界面上**四舍五入到 2 位（口径 7），但**计算全程不取整**，只在金额处取到分。别把显示值拿去算钱。

### 标准工日（stdMinutes）

一天算几个工的时间基准，默认 **540 分钟（9 小时）**。只干半天时，半天 = 标准工日 ÷ 2。

- 存在 `settings.standard_workday_minutes`，键名见 `SETTING_KEYS.stdMinutes`
- 必须是**正偶数**：半天要能落成整数分钟，541 分钟切一半是 270.5，说不清
- 工人可以单独覆盖（见下面的「口径覆盖」）

### 加班折算（overtimeUnitMinutes）

「多少分钟加班算一个工」，默认 **480 分钟（8 小时）**。加班费 = 日薪 × 加班分钟 ÷ 这个值。

- 存在 `settings.overtime_unit_minutes`
- 和标准工日是**两个独立的基准**，不要混：基本工资用 stdMinutes 当分母，加班费用 overtimeUnitMinutes 当分母

### 时段（Period）

一条考勤记录覆盖的时间段，四个值：

| 值 | 含义 | 出勤分钟 |
|---|---|---|
| `AM` | 上午 | stdMinutes ÷ 2 |
| `PM` | 下午 | stdMinutes ÷ 2 |
| `FULL` | 整天 | stdMinutes |
| `HOURS` | 按小时填 | 用户填的 `hoursMinutes` |

同一个人同一天可以在不同工地各记一条（上午 A 工地、下午 B 工地），这叫「拆工」。判重键含时段，所以 `(工人, 日期, 工地, 时段)` 唯一。

### 口径 / 口径覆盖

「口径」= 算钱和算工数的规则集合（标准工日、加班折算、餐补、取整方向……）。需求卡里编号到 **22 条**（口径 1～22），代码注释里说的「口径 19b」「口径 21」就是在引用这些编号。

「口径覆盖」= 某个工人单独设一套，不跟全局。**两级**：全局默认 → 工人单独设。**没有工地这一层**（曾经有过，YG 2026-11-05 取消了）。

优先级：工人 > 全局。

### 固化（frozen）

每条考勤保存时，把**当时生效**的标准工日、加班折算、日薪、餐补四个值抄一份存进这条记录。之后改全局设置，只影响新记录，不动历史。

- 四个字段在 `entries` 表上：`std_minutes`、`overtime_unit_minutes`、`daily_wage_cents`、`meal_allowance_cents`
- 为什么固化：改设置不能让历史工资悄悄变
- **例外**：日薪和餐补会被「改价」自动重写（追溯重算）；标准工日和加班折算不重写，要改历史必须显式执行「按当前设置重算某区间」

### 追溯重算

改了某工人的价目（日薪/餐补），自动把该价生效区间内所有记录的金额重算一遍。

- 区间 = `[该价生效日, 下一条价生效日 − 1]`
- 实现见 `src/main/repo/workers.ts`
- 改价**不受「已发放」限制**（v6.9 取消了结算单锁定）

### 预支 / 冲销

「预支」= 工人提前支走的钱。只增不改：记错了不能删，只能「冲销」—— 记一笔等额的负数抵掉，原来那笔留着。

- 表：`advances`，`kind` 字段区分 `advance`（正常）和 `reverse`（冲销），`reverse_of` 指向被冲销的原记录
- 一笔原记录只许冲一次（`ux_payments_reverse_of` 那类唯一索引）
- 累计金额恒为**净额**（含冲销的负数）

### 发放 / 记一笔

「工资发放」= 真把钱给出去了，记一笔。一笔 = 工人 + 金额 + 发放日期 + 备注（+ 可选凭证照片），**不含区间**。

- 表：`payments`，同样只增不改，跨天纠错走冲销
- 录入当天可以原地改金额和备注；隔天才发现就只能冲销
- **不再有「结算单」**：旧的「选区间生成结算单 → 标记已发放 → 锁定」机制已下线（D-026），`settlements` 表只留历史行

### 结余

一个人到目前为止还差多少钱（或者超支多少）。

```
结余 = 上期结转 + 累计应发 − 累计预支 − 累计已发
```

- 四个加项都只算**日期 ≤ 本地今天**的记录
- 可以为负（超支），界面标红，但**不阻止**继续记预支
- **唯一实现**在 `src/main/repo/balance.ts`。预支页的「可支额度」和发放页的「还欠多少」读的是同一处，页面不许各算一套

注意「结余」和「档案内区间小计」不是一回事：后者只算档案里那一段，前者是全史累计到今天的。

### 结转（carryover）

清库时把没结清的钱带下来，当作下一段的期初余额。

- 表：`carryovers`，由清库在**自己的事务里**自动生成
- **不做手工新增**（避免伪造期初），纠正只能冲销
- 为什么需要：清库把某个区间的考勤从主库删掉了，但那段挣的钱还没发完，不结转的话结余会凭空少一块

### 清库 / 归档

「归档」= 把某个时间段的考勤、照片、工资打成一个独立的包（档案包），放到档案柜里。「清库」= 归档校验通过后，把这段数据从主库删掉，让主库轻下来。

清库有三道闸门，顺序固定（D-027）：

1. **期间净额**：逐人列出应发/预支/已发/净额，净额 ≠ 0 时必须勾选「我确认这段时间已结清」
2. **主库 ⊆ 档案**：主库该区间的 id 集合必须全部出现在档案里（含发放）
3. **副本比主库新**：档案的 `updated_at` 要比考勤和发放新，还要比照片位漂移

判断「清没清库」只看 `archives.status`，不看别的。

### 档案包 / 档案柜

档案包是**目录形态**：一个文件夹 = `manifest.json` + `data.db` + `photos/`。整体可拷贝、可重指路径。

「档案柜」= 归档页里的列表，每行可打开、重指路径、校验、作废重建、清库。

### 快照（snapshot）

数据库在某一刻的完整副本（`VACUUM INTO` 出来的 `.db` 文件），存在 `snapshots/`。

四种 `kind`：

| kind | 什么时候拍 |
|---|---|
| `auto` | 自动 |
| `manual` | 手动点「立即快照」 |
| `pre-migrate` | 迁移前（只在迁移会改业务数据时拍） |
| `pre-restore` | 恢复前 |

常规快照（auto/manual/pre-restore）共用 `snapshot_keep` 名额，默认保留 3 份；迁移前快照另有名额，最多 2 份，不占常规名额。

**快照 ≠ 备份**：快照只含数据库，不含照片文件。要连照片一起，用「整库备份」。

### 整库备份 / 整库恢复

「整库备份」= 数据库 + 照片 + 档案 + 快照，打成一个 zip。「整库恢复」= 拿这个 zip 把整个数据目录替换掉。

- 恢复是**不可逆的整目录替换**，不是只换库：照片、档案、快照一起换成包里那一套
- 恢复前会自动打一个「退路包」写到数据目录的上一级
- 恢复后**必须重启**

### 照片池 / 收件箱

「照片池」= 所有导入过的照片，按内容哈希去重。「收件箱」= 一个被监听的目录，把照片扔进去会被自动吸入照片池，处理完移到 `inbox/processed/`。

- 照片存相对路径（`photos.rel_path`），实际文件在 `photoRoot` 下
- 引用计数：一张照片可以被多条考勤、预支、发放引用，删照片前要看引用数

### 照片位（slot）

一条考勤挂的照片是「上班照」还是「下班照」，存在 `entry_photos.slot`，值 `IN` / `OUT` / `NULL`。

**`NULL` 只有一个意思：当年没标上下班。** 读出仍是 `NULL`，不按 id 顺序猜、不回写库（D-025 取消了曾经的「读时兜底」）。

## 二、内部机制

### IPC 通道

渲染层调主进程的唯一方式，形如 `域:动作`（`workers:create`、`summary:byWorker`）。全部定义在 `src/shared/constants.ts` 的 `CHANNELS` 数组里。

- 主进程的处理器表是 `Record<Channel, Handler>`，**漏一个通道 tsc 直接报错**
- preload 的白名单由同一个数组生成，两侧不可能漂移
- 回包信封：成功 `{ok:true, data}`，失败 `{ok:false, code, message, detail?}`

### 只读通道白名单（READ_ONLY_CHANNELS）

一张「哪些通道在迁移期间还能用」的白名单，定义在 `src/main/ipc.ts`。**默认拒绝**：不在表里的一律在迁移期间被 `E_DB_LOCKED` 挡住。

- 加通道时判断错的后果：该进不进 → 迁移期某个只读操作被误拒（难看，不丢数据）；不该进却进了 → 迁移期写进旧库，重启后静默消失
- 典型的必须在表里的：`migrate:cancel`、`migrate:progress`、`settings:all`、`app:info`、`app:relaunch`

### 迁移（migration）

数据库结构的版本升级，一条一个 `.sql` 文件，在 `src/main/db/migrations/`。当前 **12 条**，`schema_version = 12`。

规则：

- 版本号严格递增，只按 `version > 当前版本` 执行，已应用的永不重跑
- 每条迁移在**自己的事务**里执行（DDL + 版本号写入同一事务）
- **只加不删**：加表、加列、加索引，不删
- `touchesBusinessData: true` 表示这条会删/改业务数据 → 启动时先拍 `pre-migrate` 快照

**两条血泪规则**：

1. 迁移只跑一次。已升到版本 N 的库永远不会再执行第 N 条。**要改语义必须新开版本号**（009 就因为这个提前落地，见 `migrate.ts` 里的注释）
2. 守卫测试只扫 `DELETE`/`UPDATE`/`DROP`，**扫不出 `INSERT`**。纯 INSERT 的迁移改不改业务数据，靠人判断 + 用例显式钉住

### PRAGMA 五件套

`openDb` 每次建连接都设的五个 SQLite 参数：`journal_mode=WAL`、`foreign_keys=ON`、`busy_timeout=5000`、`synchronous=NORMAL`、`wal_autocheckpoint=1000`。

顺序不能乱：`journal_mode` 必须最先设，`synchronous` 才作用在 WAL 上。

### 数据根（dataRoot）

数据库、照片、快照、档案都在这个目录下。解析优先级：

```
ATT_DATA_ROOT 环境变量  >  userData\data-root.json 指针  >  %USERPROFILE%\Documents\Attendance
```

- 环境变量分支：目录不存在会**自动创建**（验证/联调都指到 `.tmp`）
- 指针分支：目录不存在**弹错误框并退出，绝不回退默认目录建空库**（回退的后果是用户看到「数据全丢了」）

### att-photo 协议

自定义协议，渲染层用它显示照片：`att-photo://photo/<id>` 原图、`att-photo://thumb/<id>` 缩略图。

为什么不用 `file://`：Vite dev 下渲染层 origin 是 `http://localhost:5173`，`file://` 会被拦；读成 base64 塞 DOM 又会吃光内存。

为什么 host 是 `photo` 而不是裸 id：`att-photo://1` 会被 Blink 当成 IPv4 归一化成 `att-photo://0.0.0.1/`，取不回 id。这是实测踩过的坑。

安全边界：请求方只能给 **id**，给不了路径；真实路径由主进程从库里取 `rel_path` 再经 `resolveInside` 做几何判定，绝对路径、`..` 逃逸、UNC 路径一律 403。

### 错误码（ErrCode）

统一 `E_xxx`，定义在 `src/shared/constants.ts`。抛错用 `DbError` / `CalcError`（带 `code` 字段），**不许裸 `throw new Error(字符串)`**。

当前错误码：`E_DUP_ENTRY`、`E_PERIOD_OVERLAP`、`E_NO_RATE`、`E_INVALID_STD`、`E_INVALID_PERIOD`、`E_PHOTO_MISSING`、`E_DB_LOCKED`、`E_MIGRATE_FAILED`、`E_INSUFFICIENT_SPACE`、`E_NOT_FOUND`、`E_OVERPAY`、`E_PERMISSION`、`E_VALIDATION`。

渲染层拿 `ApiError.code` 分派界面行为（`E_DUP_ENTRY` + `detail.nextSeq` 就是「仍然添加」那条分支）。

### 三套单位

| 量 | 单位 | 后缀/字段 |
|---|---|---|
| 时间 | 分钟（整数） | `*Minutes` |
| 金额 | 分（整数） | `*Cents` |
| 工数 | ×10⁶ 的整数 | `units_micro` / `unitsMicro` |

**跨单位计算一律走 `src/shared/calc.ts`**，页面里不许手工换算。

### 只入不舍（ceil）

金额取整方向恒为向上。只要还有余数就进 1 分，恰好整除时不多进。

三个分项（基本、加班、餐补）各自独立向上取整，应发 = 三个已取整分项之和，**永不少给工人一分钱**。

实现是 `ceilDiv`，纯 BigInt 整数运算，**禁止浮点**。

推论：明细 3 位相加与合计之差可能差几分，这是**有意**的（D-013 三条路径对比里选 C 的理由），界面必须注明「合计按精确值向上取整」。

### 本地今天（today）

结余、发放、累计口径里的「今天」一律指**本地日期**，不是 UTC。所有「日期 ≤ 本地今天」的判断都按这个。

## 三、状态与枚举

| 枚举 | 值 | 出处 |
|---|---|---|
| `Period` | `AM` / `PM` / `FULL` / `HOURS` | `entries.period` |
| `PhotoSlot` | `IN` / `OUT` / `NULL` | `entry_photos.slot` |
| `snapshots.kind` | `auto` / `manual` / `pre-migrate` / `pre-restore` | `001_init.sql` |
| `archives.status` | `created`（档案已生成、主库数据还在）/ `purged`（该区间已从主库清出） | `005_archives.sql` |
| `advances.kind` | `advance` / `reverse` | `003_advances.sql` |
| `payments` | 无状态机。只增不改，跨天纠错走冲销 | `008_payments.sql` |

`settlements` 表里的 `status` / `paid_at` / `unlocked_at` 等列**已废弃但保留**（死列不删）。它不再驱动任何行为，只按 `paid_at IS NOT NULL` 派生出「历史单」用于只读展示。

## 四、几个容易混的词

| 别混 | 区别 |
|---|---|
| 快照 vs 整库备份 | 快照只含数据库；整库备份含数据库 + 照片 + 档案 + 快照，打成 zip |
| 结余 vs 档案内区间小计 | 结余 = 全史累计到本地今天；区间小计只算档案里那一段 |
| 工数显示值 vs 工数真值 | 显示 2 位小数（四舍五入）；真值是 ×10⁶ 的整数，计算全程不取整 |
| 标准工日 vs 加班折算 | 两个独立基准：基本工资分母用前者，加班费分母用后者 |
| 归档 vs 清库 | 归档是打包（数据还在）；清库是打包校验通过后删主库那段 |
| 预支 vs 发放 | 预支是工人提前支走；发放是公司真把钱给出去了。结余公式里两个都减 |
| 固化 vs 重算 | 固化是保存时抄一份值；重算是显式执行「按当前设置重算某区间」 |
| 逻辑删除 vs 硬删除 | 工人/工地有记录时**不许删**（只能停用）；无记录才允许硬删 |
