## D-002 产品定位与替代对象确定

日期：2026-11-05

**决策**：软件的使用者是公司人事（单机、单人），不是工人，也不是管理层自助。打卡入口继续留在微信群，软件承接的是「汇总 + 算钱」这一段，不承接打卡动作本身。替代对象是自己维护的 Excel 台账（照片插单元格 + 手数工数与加班）。形态为 Windows 桌面端。范围为「都做」：台账、录入、照片、按人汇总、按工地汇总、工资表、导出、备份。

**理由**：YG 三个痛点是照片乱、手算慢易错、算错钱无从核对；这三件都在「汇总与算钱」环节，不在打卡环节。

**否决了什么**：不做照片自动识别/OCR、不做微信自动同步、不做工人自助端、不做工资发放与个税、不做多人在线协作、不做云同步——理由与逐条排除项写在 `docs/requirements/RQ-001-考勤汇总与工资表.md` 的「不做什么」。

**残留风险**：「都做」与「先跑通最小切片」冲突。已由 D-003 收窄为两批。

## D-003 三个结构性决策：照片引用、预支只增不改、口径集中配置

日期：2026-11-05

**背景**：YG 补充三项需求——合影多人共用（一张照片 5 个人）、支钱（预支工资）、备份恢复；并锁定八条口径。

**决策一：照片与考勤记录是「引用」关系，不是从属关系。**
一张照片可被多条记录引用，一条记录可引用多张照片，照片本体只存一份。
理由：一个月 1000 张照片被 5 人引用，复制模型会变成 5000 份，磁盘与备份都会失控；且事后改照片（补发、替换）要改 N 份。
**否决了**：把照片复制进记录目录（实现最省事，但迁移代价极高——一旦上线就不能改）；也否决了「照片只挂在一个人身上，其余人复制」（同样的重复存储问题）。

**决策二：预支记录只增不改，纠错走「冲销」。**
录错的预支用一笔反向金额抵消，原记录保留，界面上两笔都在。
理由：预支是真钱，删痕迹等于断了对账链；年底对不上账时，唯一能查的就是痕迹。

**决策三：所有计算口径集中在「设置」一处，页面不各算一套。**
日工时基准、加班折算系数 K、餐补默认额、计薪方式都只存一份，汇总、工资表、导出三处引用同一处。
理由：同一个词三处不同义是这类软件最典型的死法——界面换个页面数字就对不上，且没人知道哪个是对的。

**决策四：开发分两批。** 第一批 = 台账、录入、照片池、按人汇总、按工地汇总；第二批 = 工资表、预支、导出、备份。
理由：前五块是数据地基，先把「录得进去、查得出来」跑通，再算钱。工资口径（U1～U4）未定死前动手，返工最贵。

**代价与残留风险**：第一批做完时软件「能记不能算」，YG 会想提前看工资表；口径 U1～U4 若拖到第二批才定，工资表会被迫返工。故 U1～U4 的截止仍定在需求定稿前。

## D-005 v5 的五项结构性变更

日期：2026-11-05

**决策一：取消月薪制，只有日薪。**
理由：月薪引入了「应出勤 30 天」「缺勤按天扣」「月薪加班基数」「天与工混用」四个互相纠缠的口径，每个都能在月底算出不一样的数。YG 一句话拆掉：只填日薪。整条月薪算法、E-3 验收条目、G6/G7/G12 三个未决项随之消失。
**否决了**：给月薪做「按到场天数 / 按工数当量」开关——需求方明确不要月薪。

**决策二：预支不进月度工资表，改为「自选区间结算单」。**
理由：工地是年底一次发钱，月度表扣预支会造成「10 月借 500 只在 10 月表扣、年底再算一遍」的双重口径。结算单由用户选区间（默认本年初至今），扣该区间预支得实发，正好对上「年底发钱」这个真实动作。
**否决了**：月度表带预支列（会产生跨期归属争议）。

**决策三：口径三级覆盖 + 记录固化 + 不自动重算。**
全局 → 工地 → 工人（优先级 工人 > 工地 > 全局），可覆盖标准工日与加班折算；每条考勤保存时把当时生效值固化在该记录上。改设置只影响新记录，改历史必须显式「按当前设置重算某区间」（二次确认 + 先快照）。
理由：同时解决 G8（改设置是否重算历史）与「某工地 / 某人单独算」两个诉求，且让归档包里「该区间用到的口径」有真实值。

> **已修订（同日）**：YG 收回「工地可单独设」这一层，覆盖层级降为两级，见 D-006。

**决策四：数据出口提前到第一批。**
数据库快照 + xlsx 导出进第一批，归档仍留第二批。
理由：第一批就要跑几个月，其间没有任何导出方式，硬盘坏或误删就是整年的工与照片。

**决策五：归档可编辑，恢复进主库走「合并不覆盖」。**
理由：YG 明确「改完还是归档，用户可手动恢复进主库，不覆盖原来的数据，增加考勤内容就行」。因此恢复按「同日同人同工地同时段」判重，只增不覆盖，冲突跳过并报清单。

**代价**：三级覆盖 + 固化让「这个数为什么这么算」变复杂，界面必须显示每一层用了哪个值、从哪继承。此约束已写入 RQ-001 已知风险 3。

## D-006 口径覆盖降为两级

日期：2026-11-05

**决策**：口径覆盖只有两级——全局默认值，加上「每个工人可单独改」。取消工地这一层。

**理由**：YG 原话是「按照工人来，有一个默认值，每个工人能单独改」。工地层会带来「同一个工人在两个工地被判成两套工日」这种没人能解释的情况，而现实中差异只出在人身上（临时工、老师傅谈好的条件）。

**代价**：如果将来真出现「整个工地统一按 10 小时算」，只能在工人上逐个改，或者另提需求加回工地层。加回来要动记录固化字段的继承链，不是小改。

## D-007 技术栈：Electron + SQLite + React/Vite

日期：2026-11-05

**决策**：Electron（主进程）+ better-sqlite3（本地库）+ React + TypeScript + Vite（渲染进程）+ electron-builder（打包 NSIS 安装包 / 免安装 exe）。

**理由**：实测这台机器 Node v24.16.0 / npm 11.13.0 现成，.NET 只有运行时没有 SDK，也没有 Rust 工具链——选 Electron 可以零安装直接开工。需求里最重的几件事（拖拽导入、收件箱文件夹监视、大量本地图片的缩略图与原图查看、xlsx 导出、大文件打包校验）在 Node 生态里全是现成能力。只做 Windows 并不排斥 Electron。

**否决了什么**：
- **Tauri**：包 8MB、内存低、启动快，但要装 Rust 工具链、编译慢，批量图片处理得写 Rust，迭代速度最慢。
- **.NET WPF / WinUI**：原生、可单文件发布、性能最好，但要装 SDK，界面迭代成本最高——这个项目后面还要改很多轮。
- 顺带否掉了「用 sharp 生成缩略图」：改用 Electron 内置 `nativeImage` 缩放，少一个原生模块就少一处打包事故。

**已知技术风险**（进 SDS 前必须验）：better-sqlite3 是原生模块，需与 Electron 的 Node ABI 对齐（electron-rebuild）；若装不上，退路是 `node:sqlite` 或 `sql.js`（WASM，写盘序列化，几千到几万条完全够用）。

## D-009 档案包采用目录形态，不做单文件包

日期：2026-11-05

**决策**：档案包 = 一个文件夹，内含 `manifest.json`（版本、区间、记录数、照片数、生成时间）、`data.db`（该区间的数据子集）与 `photos/`（该区间引用到的照片）。整体可拷贝、可裁剪、可重指路径。需要单文件时另做「导出为 zip」的可选动作，不是主形态。

**理由**：需求同时要求「档案可编辑」（G-4）与「档案可挪走后能重指路径」（G-5）。单文件包做前者要解包 3–5G 再重打，临时空间翻倍；目录形态可原地改一条记录、可只拷走部分照片，且「找不到」的语义从文件变成文件夹，用户更容易理解。

**否决了什么**：单文件 zip 包（可挪动性最好，但编辑代价随档案体积线性增长，几年后不可用）；也否决了「档案存在主库里加个年份字段」——那不能清库，等于没归档。

**代价**：G-4/G-5 的措辞已从「文件」改为「文件夹」；档案目录可被用户手动拆散，重指路径时必须校验 `manifest.json` 与 `data.db` 是否配套。

## D-010 环境实测结论：无编译器也能用 better-sqlite3，asar 内可加载

日期：2026-11-05

**实测结论**（T1a 探针，非推断）：`better-sqlite3@13.0.3` 自带 Node-API 预编译（`prebuilds/win32-x64.node`，N-API 10），`gypfile:false`，安装期不调用 node-gyp。本机无 MSVC / 无 Rust / 无 .NET SDK 完全不影响。Electron 45.2.3 主进程加载成功（ABI 150），**打包成 asar 后（未 unpack）也加载成功**——Electron 把包内 `.node` 落到临时文件后 dlopen。全程未出现 `NODE_MODULE_VERSION` 不匹配，`@electron/rebuild` 与「换 `node:sqlite` 退路」都没被触发。

**顺带钉死的事实**：

1. `electron@45.2.3` 的 `package.json` **没有 install 脚本**，只导出 bin `install-electron`；宿主 `package.json` 必须自己加 `"postinstall": "install-electron"`，否则 `npm install` 成功后也没有 `dist/electron.exe`。
2. 本机 **GitHub 直连不通**（`TypeError: terminated`），取 Electron 二进制必须先设 `ELECTRON_MIRROR=https://npmmirror.com/mirrors/electron/`。这一条已写进 `AGENTS.md`「怎么跑」。
3. 本 shell 环境带**空值的 `ELECTRON_RUN_AS_NODE`**，会让 electron 走 Node 模式；启动前要 `Remove-Item env:ELECTRON_RUN_AS_NODE`。
4. `vite@8.3.6` 是 `electron-vite@6` 的硬 peer，必须装；`@vitejs/plugin-react` 骨架阶段不必装。
5. `better-sqlite3` 13.x **不自带 TS 类型**，也没有装 `@types/better-sqlite3`——改为在 `src/main/db/driver.ts` 自己声明最小接口，正好落实「repo 只依赖驱动抽象，不依赖 better-sqlite3 类型」。
6. `tsx` 未装，`seed:demo` 脚本是占位（跑起来 exit 1），留到 T5/T6 造数时补依赖。

**否决了什么**：不再考虑 Tauri / WPF；不再预留 `node:sqlite` 作为主路径退路（Electron 45 内置 Node 24.x 虽支持，但 better-sqlite3 实测可用，换驱动没有收益）；不用 `electron-builder` 做 asar 验证（`@electron/asar` 一个 126 KB 的 CLI 就够，代价≈0）。

**残留**：asar 验证是手工 `@electron/asar` 打的包，`asarUnpack` 策略、代码签名、NSIS 安装包仍属 S9，未验。

## D-011 第一批实施完成：实现与文档的偏离、以及仍未追认的一条口径

日期：2026-11-05

**事实**：T1–T7 全部落地。独立门禁（主会话亲跑，非实施者自报）：`npm run test` → 15 files / **234 passed | 2 skipped**；两个 `tsc --noEmit` → 0；`npm run build` → 0。第一批 32 条验收里 30 条已有自动化证据，剩 2 条性质上只能人工（B-7 的定位跳转、C-4 的缩略图目视）。

**实施中形成的、需要留档的口径偏离**（逐条都是「SDS 没写清 / 写错了，实施时定下来的」，已同步回 SDS 的 T1c/T2/T4/T5/T6/T7 裁定表）：

1. better-sqlite3 13.x 是 Node-API + 预编译，**不需要编译器也不需要 electron-rebuild**（D-010）；asar 内可直接加载。
2. 自定义协议不能用裸数字主机（`att-photo://1` 会被 Blink 归一化成 `0.0.0.1`），id 必须放路径段。
3. `overwriteEntry` 的 `photoIds` **缺省 = 保留原照片**，`[]` 才清空（安全侧兜底）。
4. 非 `HOURS` 却传分钟数 → 报 `E_INVALID_PERIOD`，不许静默丢弃。
5. 导出 xlsx **不放合计行**（放了会让用户框选求和翻倍，反而破坏 G-1）。
6. 快照轮转**按价值分层淘汰**：`auto` → `manual` → `pre-migrate` → `pre-restore`，不分桶。

## D-013 金额取整选 C 路径：精确累加后取整 + 明细显示 3 位

日期：2026-11-06

**背景**：口径 19 从 v6.3 起一直挂「待追认」。YG 要的是「最后算出来的钱和实际没偏差」，所以把三条路径摊开比较（例：日薪 300 元、标准工日 9 小时，某人 3 天各干 100 分钟）：

| 路径 | 算法 | 三天结果 | 明细和 = 合计 | 与真值差 |
|---|---|---|---|---|
| A 逐条取整 | 每天 round(5555.56) 再相加 | 166.68 元 | 是 | +1.33 分（公司多给） |
| B 精确累加后取整 | 16666.67 分一次性 round | 166.67 元 | 否（差 1–2 分） | +0.33 分 |
| **C（选定）** | 同 B，明细显示 3 位并注明合计按精确值算 | **166.67 元** | 是（3 位足够时） | +0.33 分 |

**决策**：走 C。每条记录**不预先取整**，保留整数分子/分母的精确值（禁止浮点）；每人每月的分项金额 = 该分项全部记录精确值累加后**一次性**四舍五入到分；应发 = 三个已取整分项之和；明细展示到元后 3 位，界面注明「合计按精确值计算」。

**理由**：A 虽然账目最省心，但方向恒定是「多给」，一年下来是几百块级别且说不清；B 钱最准但人事逐行核对时会发现加不上，那种不信任比一分钱贵；C 同时满足「钱准」和「账能对上」。

**实现要求**：精确累加用 BigInt 分数（分子/分母逐步约分），因为不同记录的标准工日与日薪不同、通分后分母会膨胀——**不许用浮点累加**（虽然量级上安全，但这是钱）。

> **已修订（同日，见 D-014）**：取整方向从「四舍五入」改为「只入不舍」（向上取整到分）。

**代价与影响面**：

1. 三处金额出口必须同时改，否则工资表与结算单两个口径：`repo/payroll.ts`、`repo/settlement.ts`、`export/xlsx.ts`。
2. 验收 E-3 的措辞从「三项之和 = 应发」改成「每项精确累加后取整，再相加 = 应发；明细 3 位相加允许 ≤0.001 元差」。
3. 附录三人的数字**不变**（6750.00 / 956.25 / 337.50 / 8043.75 全部整除），所以切换口径不需要重录数据、不改任何验收期望值。
4. 明细行从 2 位变 3 位，界面要加一行说明，否则会被当成显示错误。

## D-014 取整方向改为「只入不舍」

日期：2026-11-06

**决策**：金额取整从「四舍五入」改为**向上取整到分**（`ceil`）。只要还有余额数就进 1 分；恰好整除时不多进。三个分项（基本 / 加班 / 餐补）各自独立向上，应发 = 三者之和。

**理由**：YG 要求「永远不会少给工人钱」。四舍五入在余数 < 0.5 分时会舍掉，方向不确定；向上取整让误差方向恒为「公司多付」，最多多付 0.99 分/人/分项/区间，对账时人事的心理负担最小。

**否决了什么**：保持四舍五入（金额最接近理论值，但要向工人解释「为什么少了一分」）；「余额大于半分才进」（又回到四舍五入的模糊地带）。

**代价**：

1. 每个分项每人每区间最多多付 0.99 分；三个人一个月最多几分钱。
2. 「一次性取整」必须保留——如果改成逐条向上再相加，误差会放大 n 倍，等于把 C 路径的收益抵消掉。
3. E-3 的差异上限改写成公式「≤ 0.001 × 明细条数 + 0.01 元」（明细 3 位与合计都向上，上界随条数增长；写死 0.05 会在一月 62 条时被越过），并新增硬约束「合计不得小于三项精确值之和」——后者才是「永不少给」的数学表达。

**不受影响**：附录三人的全部验收数字（全是整除，ceil 与 round 同值），所以切换不需要重录数据、不改任何期望值。

## D-018 两次编码事故：不要用 shell 管道改中文源码

日期：2026-11-06

**事故一（主会话）**：给 `src/main/export/xlsx.ts` 改一处字符串时用了
`(Get-Content -Raw $f) -replace ... | Set-Content $f -Encoding utf8`。
该命令把 UTF-8 按 GBK 读入、再按 UTF-8 写出，**中文全部变成 U+FFFD、换行被吞**，`tsc` 报 30 多条语法错。恢复手段：按 `out/main/index.js` 的编译产物逐段重建，并用 SHA-256 证明重建后的编译产物与原产物**逐字节等价**（只差被要求改掉的 `creator` 三处）。

**事故二（打包任务）**：用 `Set-Content -Encoding utf8` 写 `package.json`，PowerShell 5.1 会加 BOM，electron-builder 直接报 `Unexpected token '﻿'`。

**结论（写进 AGENTS.md 的约定）**：
1. **改中文源码用编辑工具做字面替换**，或用 `[System.IO.File]::WriteAllText($p, $s, (New-Object System.Text.UTF8Encoding($false)))` 显式指定无 BOM 的 UTF-8。
2. **禁止 `Get-Content | Set-Content` 往返**——默认编码不一致时会静默毁文件。
3. 生成 JSON/YAML 配置时同样显式无 BOM。
4. 事故后的恢复优先级：**编译产物 > 测试 > 记忆**。`out/` 里的产物是可验证的真相，SHA 比对能证明等价性。

## D-022 目录迁移的四个丢数据漏洞与修法（审计驱动）

日期：2026-11-06

RQ-003 实施完、427 测试全绿后，派了独立只读审计，判定**不能交付**。测试全绿是因为它们都在 IPC 层与进程内假路径上测，审计问的是「真实使用会怎么坏」。

**四个会丢数据的洞**：

1. **迁移成功后、重启前的窗口**：`migrating` 已清、设置已指向新根，但当前进程还连着旧库。此时录的考勤写进旧库，重启后从新库读 → **数据静默消失**；watcher 吸入的照片落到新根成孤儿。原来只有一句界面软提示。
2. **迁移期只挡 IPC**：`withMigrateGuard` 只包写通道白名单，而 `services/inbox.ts` 的 watcher 直接写库；照片迁移一次性读完 `rows` 后吸入的照片不会被复制。
3. **指针目录存在但 `app.db` 不在**：只判 `isDirectory` → 启动在空目录里建新库，界面一片空白（正是 D4 要防的观感）。
4. **指针写失败无补偿**：数据已搬、设置已写、指针没写 → 下次启动回默认目录，而默认目录还留着旧库 → 用户看到旧数据继续录 → **新旧库分叉**。

**修法**：

| # | 修法 |
|---|---|
| P1 | 迁移成功后置进程级 `pendingRestart`，**所有写通道**返回 `E_DB_LOCKED`（文案带新路径与「请重启」）；同时停 watcher；界面弹**不可关闭**的 Modal + 顶部红条 + 按钮全灰 |
| P2 | 不再维护「写通道白名单」，改为**只读白名单**：不在只读集合里的一律在迁移中被拒。加一条测试**遍历全部 81 个通道**，断言「非只读通道必被拒」，以后新增通道默认受保护 |
| P3 | 指针目标必须同时满足「目录存在」**且**「`app.db` 存在」，否则按「数据目录找不到」报错退出，**绝不建库** |
| P4 | 顺序改为「探针写临时指针 → 落位 → 原子改名指针 → 写新库设置」；探针失败则**在 rename 之前中止**，已落位但指针失败则回滚（目标改回暂存名并删除） |
| P5 | **迁移过程不写旧库**：`pre-migrate` 快照直接 `VACUUM INTO` 到暂存目录并在**新库**登记；settings 只写新库；不清旧 `thumbs`。旧库 SHA-256 迁移前后一致（实测 `0090f975…398a60` 相等） |
| P6 | 照片冲突清单收集到上限 20 条再中止（原来 push 一条就 `break`，`LIMIT` 是死代码） |
| P7 | 复制循环改 `await fs.promises.copyFile`，文件之间检查取消标志，取消才真机可达 |

**已知取舍（可接受）**：`migrate:cancel` / `migrate:progress` 在等重启期间仍放行（不写库，取消必须可达）；`VACUUM INTO` 与校验仍是同步调用（better-sqlite3 同步 API，单次 < 1s）；「已落位但指针 rename 失败」的回滚分支无自动化用例（Windows 无法稳定构造）；设置页以外的写按钮未逐个禁用，靠主进程 `E_DB_LOCKED` + 红条兜底。

**教训**：`withMigrateGuard` 用「白名单」而不是「黑名单」是这次的关键设计错误——白名单意味着**新增通道默认不受保护**。凡是要挡写操作的地方，都应该默认拒绝、只放行明确的只读集合。

## D-023 照片位（上班/下班）落库为 `entry_photos.slot`

日期：2026-11-09

**背景**：YG 要求一条考勤能挂两张照片（上班 / 下班）。第一版靠「照片 id 升序第 1 张算上班、第 2 张算下班」这种约定，**只拍了下班一张时会显示成上班照**——对账时会被误导。这是「功能做了但语义是假的」。

**决策**：给 `entry_photos` 加 `slot TEXT CHECK (slot IN ('IN','OUT'))`（`006` 加法迁移，可空）。写入只认调用方明确给的值；老数据 `NULL` 在**读时**按 id 升序兜底成 IN/OUT，**不回写库**（避免把约定当事实）。

**连带必须改的三处**（都已处理或已排期）：

1. `attachPhoto` 改成 UPSERT：同一张照片重复 attach 时只更新 slot；不带 slot 时用 `COALESCE` 保留原来的位置标记（不许用空值覆盖）。
2. **归档包要带 slot**：`archive.ts` 的 `entry_photos` 复制列清单原本固定两个列，加列后档案往返会把「这是上班照」静默丢掉。**已修**：复制列加 `slot`，合并用 `INSERT OR IGNORE ... (entry_id, photo_id, slot)`，老档案（v5，无该列）用 `pragma table_info` 探测后退 `NULL AS slot`，不猜成 IN（有断言钉住 `slot IS NOT NULL` 计数为 0）。
3. 两处测试里的 `schemaVersion` 字面量（`archive.test.ts` / `snapshot.test.ts`）跟着版本号走——属于加迁移的必然连带，已追认。

**顺带记一笔**：批量登记是本批落照片引用、成功后逐条补写 slot（`services/recalc.ts` 的 `BatchCreateInput` 不带 `photos`）。补写失败只影响角标（退回按 id 兜底），照片本身不受影响。

## D-024 日志写失败不得崩主进程（EPIPE 模态框）

日期：2026-11-10

**现象**：用启动脚本 / 子进程方式跑本程序时，反复弹红色模态框「A JavaScript error occurred in the main process」，不点「确定」程序就卡死（YG 实测）。

**真因（实测修正过的表述）**：不是 `console.log` 同步抛异常——是 `process.stdout` 这个 Socket 上的**未捕获 `'error'` 事件**（`EPIPE`，`errno=-4047`）异步抛出。链条：启动它的父进程（脚本 / 管道读端）先退出 → `fd1` 断管 → 主进程任意一次 `console.log` 写失败 → error 事件无人监听 → Electron 主进程默认的未捕获异常处理弹模态框 → 主线程被 `showMessageBoxSync` 卡死。

**因此**：给那一行 `console.log` 包 `try/catch` **治不住**（异步事件拦不到），必须监听 stream 的 `error` 事件。

**修法**（`src/main/index.ts:54-55`，import 之后、任何日志之前）：

```ts
process.stdout.on('error', () => {})
process.stderr.on('error', () => {})
```

这是**流级**兜底，`src/main/**` 里 124 处 `console.log/error/warn` 全部被覆盖，一个都不用改。管道正常时日志照常输出，断管后静默丢弃。

**明确禁止**：用 `process.on('uncaughtException')` 做全局兜底——那会把真正的崩溃一起吞掉，以后出问题连报错都没有。

**验证**：修复后同场景捕获到 **6 次真实 EPIPE**（errno -4047）全部被吃、无框、主进程与界面正常；关窗仍正常写 `auto` 快照并 `checkpoint + close`。修复前有 `#32770` / `Error` 框的类名 + 标题 + 截图 + 主进程侧 EPIPE 栈。

**注意**：error 事件是异步回来的，**弹框可能在写日志后 0~3 秒才出现**，表现为「脚本退出后过一会儿弹、每点一下界面又弹」。

## D-026 取消「已发放锁定」，结算单改为发放记账

日期：2026-11-11

**决策**（需求 `docs/requirements/RQ-005-发放记账与结余.md` v6 · C1–C18；方案 `docs/plans/PL-004-plan.md` v2）：

1. **取消全部「已发放锁定」**。`settlements.status = 'paid'` / `paid_at` 从「锁区间」降级为**只读历史**，四个方向的拦截一并删：① 考勤侧（新增 / 修改 / 删除 / 并入 / 批量登记的前置拦截）；② 照片侧（挂上 / 摘掉 / 彻底删除的前置拦截，IS-012 那批）；③ 改价侧（改日薪/餐补时「与已发放区间相交就拒绝」，IS-008 末句）；④ 归档侧（「区间内有已发放单就拒绝归档 / 拒绝清库」）。发过钱之后照样能补录、改、删考勤，改价，合并恢复。
2. **结算单改为「工资发放」**（页面标签、`map.md`、导出文件名同此）：一笔发放**只记（工人、金额、发放日期、备注）**，**不按区间、不锁考勤、没有 draft/paid 状态机**；跨天纠错走冲销，录入当天可原地改金额与备注。落库新建 `payments`（迁移 008，S1），`settlements` 只留历史单、死列不删。
3. **结余（= 可支额度）= 累计应发 − 累计预支 − 累计已发**，三个累计都只算「日期 ≤ 本地今天」；旧式「累计应发 − 累计预支」作废。**只有一处实现**（`repo/balance.ts`），页面、导出、预支页的可支额度都读它。
4. **清库改三道闸门**（顺序固定，`dryRun` 也跑）：闸门② 数据有副本 → 闸门③ 副本是新的 → 闸门① 期间净额「**显示 + 确认 + 凭据**」——弹窗逐人摊开（期间应发 / 期间预支 / 期间已发 / 期间净额），净额 ≠ 0 **默认拦住**、可勾「我确认这段时间已结清」越过，清单**无论勾否**都写进档案 `manifest.clearance`。不是硬拒。

**为什么**：YG 的实际用法是「**干一年、年底结；甚至一次结不清，分几次给；每次只是某天给某人一笔钱**」。发放不对应任何时间段，所以「选区间出账」这层结构本身是多余的；而「标记已发放 → 整个区间锁死」直接让日常的**补录、改价、合并**做不下去——发过钱之后照样要补记漏掉的考勤、改错的单价。锁定挡住的恰好是最常做的事，只留一个「解锁」按钮等于把代价转嫁给用户。

**否决了什么**：

1. **按区间出账 + 人级锁**（RQ-005 v1/v2 的方案）：区间一旦重叠，「结余」按哪段算说不清；同一笔考勤同时落进两张单时结余必然算不准。→ 否决，改为总账口径（全史累计，按本地今天）。
2. **硬拦清库**（期间净额 ≠ 0 就禁止清库）：**补发的日期默认是今天、落在清库区间外**，记了也不改变该区间净额——硬拦等于让清库**永远**做不了。→ 否决硬拒，改成「默认拦住 + 勾选越过 + 留凭据」，并把「程序不知道每笔钱补的是哪段时期」写在界面上。
3. **复用 `settlements` 表当发放表**（加列或改语义）：需求约束已写明 `period_from / period_to / status / paid_at / unlocked_at` **废弃但不删列**，复用等于让废列重新有意义；同一张表还要用区间列同时表示「区间」和「一天」、用 `status` 同时表示「草稿」和「已发放」。→ 否决，新建 `payments`。
   - 连带否决：把发放记进 `advances` 用负号表示（预支与发放是两种钱，混表后公式里的「累计预支」与「累计已发」再也分不开，而结余公式正是靠这两项分开）；删表重建（需求禁删列，老档案还要按原样读）。

**影响面**（**只在此处补注，既有决策与工单正文一字不改**）：

## D-027 清库三道闸门与「期间净额」口径

日期：2026-11-11

**决策**（RQ-005 v6 · C15 / C15b / N1；实现 `src/main/services/archive.ts#purgeArchiveRange`，界面 `src/renderer/src/pages/Archive.tsx`）：

1. **三道闸门顺序固定：② 有副本 → ③ 副本是新的 → ① 期间净额**。`dryRun` 也把三闸跑完，且**零写入**（不拍快照、不写 manifest、不删数据）。顺序不能换：②③ 证明「删了还找得回来」，① 只是账上的确认 —— 前两闸不过就永远不该走到摊账那一步，否则用户会以为只差勾一下。
   - **闸门②**：主库该区间的 id 集合必须 ⊆ 档案（`entries` / `advances` / **`payments`**），缺一条就拒。
   - **闸门③**：副本必须比主库新 —— 区间指纹 → `updated_at`（考勤与**发放**都要比）→ **照片位漂移**（`countSlotDrift`：`attachPhoto` 只改 `entry_photos.slot`、不碰 `entries.updated_at`，光比时间戳看不见「上班照改成下班照」）。老档案没有 `slot` 列时如实回 `slotChecked:false`，不比、不假装通过。
   - **闸门①**：期间净额**逐人四数**（应发 / 预支 / 已发 / 净额）显示；净额 ≠ 0 的人默认拦住，勾「我确认这段时间已结清」可越过；清单**无论勾否**都写进档案 `manifest.clearance`。
2. **「期间净额」≠「结余」**，两者不许混用、也不共用一个函数名：期间应发 = **全史累计应发 − 区间外累计应发**（区间外前后段合并、只取整一次，C15b），期间预支 / 已发 = `paid_on` 落在区间内**且 ≤ 今天**的合计，净额 = 期间应发 − 期间预支 − 期间已发；行集合 = 期间有应发 ∪ 有预支 ∪ 有发放的人（净额为 0 的人也在表里，供人核对）。唯一实现是 `repo/balance.ts#periodNetForRange`，界面只画不算。因为取整发生在区间层面，它可能与工资表上同区间差 1 分，界面须注明。
3. **「清没清库」只看 `archives.status`**（`created` / `purged`）；`manifest.clearance.purgeState` 只表示**凭据写到了哪一步**。

**为什么**：

- **为什么不能拿总账结余判清库**：结余是「截至本地今天」的全史一趟取整，人还在干活、应发每天在长，**永不归零**；拿它当条件等于清库永远做不了。而且清库清的是**某一段**，唯一有意义的问题是「这段的账对不对」，不是「这个人一辈子还差多少」。
- **为什么闸门全在留快照之前**：闸门失败必须**零写入**。先拍快照再验闸门，被拒一次就在 `snapshots\` 留一份莫名其妙的副本、还可能把轮转里有用的旧份挤掉（默认只留 7 份）。
- **为什么 `clearance` 要写进 `manifest`**：档案包是这段数据的唯一存档，几年后没人记得「当时凭什么认为这段结清」。写进去的是**用户勾选那一刻的账**，可以复核、可以对账。凭据分两版写 —— 删数据**之前**先落 `purgeState:'pending'`（写不进去就整体拒，一个字节都不删），删完再改成 `'done' + finishedAt`（收口失败只记日志、回包 `clearanceFinalized:false`，不许把「已删」说成「没删」）。
- **为什么只看 `archives.status`**：`purgeState` 有两种 `pending` —— 「算过账但没删」和「删完但收口写失败」。拿它当「清没清」会得出**相反**结论（后者库已经清了）。`status` 是库里的一行、由清库动作自己写，是唯一可靠判据。

**否决了什么**：

1. **硬拦（净额 ≠ 0 禁止清库）**：补发的日期默认是今天、落在清库区间之外，记了也不改变该区间净额 —— 硬拦等于让清库**永远**做不了。→ 改为「默认拦住 + 勾选越过 + 留凭据」，并把「程序不知道每笔钱补的是哪段时期」写在界面上。
2. **用总账结余代替期间净额**：结余永不归零（人还在干），且回答的不是「这段结清没」。→ 否决，另设 `periodNetForRange`。
3. **先拍快照再验闸门 / 只写一版 `clearance`**：前者留垃圾快照并挤掉轮换、后者无法区分「算过没删」与「删完没写进去」。→ 否决。

**关联**：`docs/requirements/RQ-005-发放记账与结余.md` v6 C15 / C15b / N1；`docs/plans/PL-004-sds.md`（T4 结余与期间净额、T12 三道闸门）；D-026 第 4 条；`docs/map.md` P-12 / F-11③ / F-12 /「已知的坑」。

## D-028 档案合并的发放判重键

日期：2026-11-11

**决策**（RQ-005 v6 · C14；实现 `src/main/services/archive.ts#mergeArchiveIntoMain`，界面 `src/renderer/src/pages/ArchiveViewer.tsx`）：把档案包并回主库时，`payments`（发放）的身份键 =**（工人、发放日期、记账时刻）**，**金额不进键**：

- 键命中且金额相同 → **跳过**（重复恢复不翻倍；同样记进清单，理由写「主库已有同一笔发放」，方便核对）。
- 键命中但金额不同 → 进**冲突清单**（`kind='payment'`），**不重复插入、不覆盖**，由人确认。
- 冲销行按 `reverse_of` 映射到**新**记录 id；**映射不出就跳过、计入冲突清单，绝不写 `null`**。

**为什么**：

- **为什么金额不进键**：发放允许在录入当天原地改金额（`payments:update` 只动 `updated_at`）。归档之后又改过、再合并回来时，同一笔的金额可能已经和档案里不一样。金额若进键，这笔会被判成「另一笔」→ **同一笔钱记两遍**、结余凭空少一截，而且事后看谁都像「真的多给了一次」。金额不同但身份相同，是**人**要裁决的事，所以进冲突清单而不是自动处置。
- **为什么冲销映射不出就跳过而不是写 `null`**：`reverse_of` 的意思是「这笔负数抵的是哪一笔」。映射不到（原记录既不在档案也不在主库）却写 `null`，就会造出一笔**没有原记录的冲销** —— 凭空一笔负账把结余永久压低，而且再也查不出它抵的是谁。跳过只损失一条无法自洽的记录，且冲突清单里点名可见。
- **为什么不用 id 判重**：档案是独立 `data.db`，两边 id 空间互不相干；按 id 判重会把「同一笔在两库 id 不同」当成两笔，等于每次都重复插入。

**否决了什么**：

1. **（工人、发放日期、金额）判重**：同日同人同额的两笔**真实**发放会被合并成一笔（先给 500、又给 500 是常态）。
2. **按 `payments.id` 判重**：两库 id 空间独立，见上。
3. **冲销映射不出就写 `null` / 整包拒绝合并**：前者造假账，后者让老包的个别残缺拖死整次恢复。

**关联**：`docs/requirements/RQ-005-发放记账与结余.md` v6 C14；`docs/plans/PL-004-sds.md` T11；D-016 第 2 条 / D-017 第 2 条的结算单部分已由 D-026 影响面作废（合并只处理 `entries` / `advances` / `payments`）；`docs/map.md` P-13 / F-12 /「已知的坑」。

## D-029 发放改成「一笔一人 + 可挂凭证照片 + 历史单提示条」（RQ-005 v7）

日期：2026-11-11

**决策一：一次发放只能选一个工人。**
理由：YG 的实际用法是「某天给某人一笔钱」，而每笔发放要挂**自己的一套凭证**（截图/收条）。一笔发放若含多个人，凭证就无法归属到具体哪个人那一笔；而且结算时是一人一签。给多人发就存多次。
**否决了**：保留多选 + 逐行金额（v6 的形态）。它省几次点击，但凭证归属会变成「这张图是给谁看的」说不清。

**决策二：发放凭证走关联表 `payment_photos(payment_id, photo_id)`，可多张。**
与预支的多凭证（`advance_photos`）同一模式：照片本体在照片池只存一份，发放记引用。拖入/点选即导入照片池，并把**拍摄日期设为该笔发放的发放日期**（这样照片池按日期分组就归到那天）。
**冲销行不带凭证**（收据留在原记录上）；删照片只解除引用、不删原图（`detach`），彻底删除时关联行由 `ON DELETE CASCADE` 带走、发放本身一字节不动。
**否决了**：`payments.photo_id` 单列（一笔只能挂一张，与"凭证可能是好几张截图"不符）；把照片复制进发放目录（重复存储，与 D-003 决策一同一条理由）。

**决策三：`countRefs` 把发放凭证数进引用计数，但**没有**同时收口 `advance_photos` 与 `photos.ref_count`。**
现状是三处口径不一致：`repo/photos.ts#countRefs` = `entry_photos + payment_photos`；`advance_photos` 不在其中（`advances.test.ts` 有一条用例明写「预支引用不算在这个数字里」）；`photos.ts` 的 `ref_count` 列仍只数 `entry_photos`（照片池角标可能比删除弹窗的数字小）。
**这是既有缺口，不是本次引入**。收口要同批改那条用例 + 照片池文案，属独立改动，记在 `docs/map.md` 的坑里。

**决策四：历史单提示条是**信息级**，不做弹窗、不用红色。**
判据抽成纯函数 `unrecordedHistoryCount()` 放 `@shared/types.ts`（结构化参数 `{ paidAt, clearedAway, hasPayments }`，不 import 渲染层手抄类型）：`paidAt` 非空 且 **未清库** 且 **未补记** 才算。
理由：YG 升级后会有 **1 张**「曾标记已发放、后来解锁」的历史单（真实库实测），程序无法把它折算成发放记录（旧模型不记"发给谁、发多少"），所以只能提示人核对。提示条必须**能自动消失**，否则会永久挂在页面上变成噪声。

**代价与影响面**：

1. 新增迁移 `010_payment_photos.sql`（纯加法）；库版本 **9 → 10**，表 **15 → 16**。
2. `createPayments` 签名从「多行」收窄为「一笔一人」；**legacy 多行形状暂时保留**（`CreatePaymentsBatchInput`，`@deprecated`），因为仓里还有 4 处测试按老形状调用、不在当轮授权内。收口动作：把那 4 处改成新形状后删掉 legacy 分支。
3. 归档与清库必须把 `payment_photos` 接进"收集照片 / 跨区间保护 / 孤儿检查 / 合并映射"，**否则只被发放引用的照片既进不了档案包、也逃过跨区间保护，清库后档案里查不到凭证**（本决策落地的同一批已处理）。
4. `verifyArchive` **仍是 22 项**：发放凭证的孤儿检查并进第 18 项「照片引用完整（孤儿引用条数）」，条数一致性放进编辑闸门 `assertManifestCountsMatch`（条件式）。**否决了**新开第 23 项——22 项的名字与顺序是外部契约，`archive.test.ts` 逐项断言。

## D-030 「被谁引用」的口径收口：四类来源、一处实现、读取时现算

日期：2026-11-11

**背景（D-029 决策三留下的缺口）**：D-029 落地时只把 `payment_photos` 数进 `countRefs`，`advance_photos` 与 `advances.photo_id` 仍在计数之外，`photos.ref_count` 列更是只数 `entry_photos`。结果是同一个数字有三套口径：照片池角标、删除门、删除弹窗的分项。**本次已收口**，这条决策把「收口成什么」定下来。

**事实一：引用只有四类来源。**

| 来源 | 语义 | 备注 |
| --- | --- | --- |
| `entry_photos (entry_id, photo_id)` | 考勤打卡照片 | 006 起还有 `slot`，与计数无关 |
| `advance_photos (advance_id, photo_id)` | 预支凭证（007 起可多张） | |
| `advances.photo_id` | 预支凭证的**老单列**（004 的列） | 007 回填后与新库里「第一张」重合 |
| `payment_photos (payment_id, photo_id)` | 发放凭证（010 / C19） | |

**事实二：去重规则——老单列与关联表算同一笔。**
`advances.photo_id` 与 `advance_photos` 里的同一张图**只算一次引用**：007 回填让一笔预支同时落在两处，不去重的话「一张图挂在一笔预支上」会被数成 2，删除弹窗会说「被 2 条记录引用」而实际上只有 1 笔预支用到它。实现方式是给老单列那一段加 `NOT EXISTS(advance_photos 里同一笔的同一张)`——只补「没有关联行」的老数据。计数单位因此是**笔**（预支）/ **条**（考勤、发放），不是「行 × 位置」。考勤侧与发放侧没有「老单列」，不存在同类去重问题。

**事实三：唯一实现是 `repo/photos.ts#refExpr`。**
一份 SQL 表达式同时喂给四处消费方：照片池角标 `ref_count`、删除门 `countRefs`、分项明细 `countRefsDetail`（`photos:countRefs` 的回包）、`unreferenced` 过滤。**加第五类引用只许改 `refExpr` 这一处**——四处各写一遍正是 D-029 那个缺口的成因。

**事实四：选「读取时现算」，不选「存储列」。**
`photos` 表**从来没有** `ref_count` 列，所谓 `ref_count` 一直是 `refExpr` 的别名（SQL 里的 `AS ref_count`）。本次收口**不引入**物化列，理由：
1. 物化列要求每条写入路径（考勤挂图 / 解图、预支挂图 / 解图、发放挂图 / 解图、四类 `CASCADE` 与 `SET NULL`、合并、清库）都记得维护它——漏一处就是长期错数，而漏的那处通常没人测；
2. 现算的代价已被实测压住（见下），没有非物化不可的理由；
3. 物化列一旦与真值漂移，**没有自愈路径**：用户只能看到错数，直到有人手动重算。

**性能实测**：8000 张照片的库上，`refExpr` 走完「角标 + 删除门 + 分项 + 孤儿」这套读取合计 **14.8 ms**（一次查询级聚合，不是 N+1）。照片池一屏只显示一页，这个量级不构成交互延迟。

**界面口径：照片池卡片只显示合计，分项在预览与删除弹窗里。**
卡片上只放一个总数（避免三行小字把卡片撑高，与 IS-009「格子里不放解释性文字」同一条道理）；「考勤 N / 预支 M / 发放 K」的分项放在**点开预览**与**删除确认弹窗**里——那里才是用户要决定「删还是只解引用」的时刻。

**关联**：D-029 决策三（本条补上它的缺口）；`docs/map.md`「已知的坑」里「照片『被谁引用』只有一处实现」那条；`repo/photos.ts#refExpr`；`RQ-005` C19 / 验收 22–26。

## D-031 清库时把欠款「结转」下来（期初余额）

日期：2026-11-12

**背景**：YG 的真实场景——「上一年账目已经算清了，但现在没钱发工资。下一年考勤又开始，我想清库，不影响这一年。」

原设计会**把这笔欠款清掉**：清库删掉该区间考勤 → 累计应发归 0、累计已发本来就是 0 → 结余 0，欠的钱凭空消失；而且清库闸门①（期间净额 ≠ 0 就拦）会**直接拒绝清库**，两头堵死。

**决策：新增 `carryovers` 表（迁移 011），清库时把未结清金额结转下来。**

```
还欠多少 = 结转合计 + 累计应发 − 累计预支 − 累计已发
```

- 结转是**存量**：无日期、无区间条件，不受 `asOf` 影响；`periodNetForRange` 不参与
- `balanceBoard` 的**行集合**加「有结转」（只有结转、无考勤无预支无发放的工人也要出现）
- 清库闸门① 的**拒绝行为不变**（净额 ≠ 0 且未勾确认 → 拒绝），但拒绝回包的 `clearance` 多带每人「将结转的金额」；勾确认放行后，**删数据前的同一事务内**生成结转行；净额 = 0 的人不生成
- 结转**只增不改**：记错走冲销（插一条负数、`reversed_by` 指向原记录），不真删

**账期按农历年（春节）算**（YG 明确：「我们都是按照农历年，也就是春节算，一般都是春节算清本年的账，无论结不结得清楚」）：
- `src/shared/lunar.ts` 内置 2024–2031 春节日期表，提供 `lunarYearRange(year)` → `[该年春节, 下一年春节前一天]`
- **不引入农历库**（一年用一次的便利不值得一个依赖 + 闰月处理）；表外年份返回 `null`、让用户手填
- **不加「必须等春节后才许清上一年」的日期检查**（YG：「用户自己知道什么时候该清」）；程序只保证「清掉那段、未结清的金额会结转下来」

**结转随档案包走**（`TABLE_COLUMNS` / `INSERT_ORDER` / `counts.carryovers` 恒写）：
- 采集条件 = **`source_from`/`source_to` 与归档区间重叠**（不是按 `created_at`）。理由：结转没有"发生在某天"的语义，"这笔结转是从这段账来的"只记在 `source_*` 上；按 `created_at` 会漏掉「半年前清库、现在归档这段」——而那正是换机恢复最需要的那笔欠款
- 只被结转引用到的工人要并入 `workerIds`（否则 `carryovers.worker_id` 撞 FK、整次归档失败）

**合并的两道闸**：
1. **硬闸**：档案某条结转的 `(worker_id, source_from, source_to)` 与主库已有结转相同 → 跳过并进冲突清单（这段已经结转过）
2. **双算告警**：合并前主库某条结转的来源区间与**档案里任意一条考勤**的 `work_date` 相交 → 回包 `carryoverOverlapWarnings`（人话，可直接显示）。**不拒绝整次合并**——拒绝会让「只想补几条记录」的人做不下去；改为强提示 + 冲突清单 + 界面 `Alert type="warning"` + 建议用冲销处理

**清库侧防重**：主库已有同来源区间、且该人这段结转合计 ≠ 0 → **拒绝重清**（`E_VALIDATION`，`detail.kind='purge-duplicate-carryover'`，dryRun 也拒）。
**否决了**「跳过生成结转、照删考勤」——那会让欠款凭空消失。
用「合计 ≠ 0」而不是「有行就算」，是为了留出「清错 → 冲销 → 重清」的合法路径。

**否决了什么**：
1. 清库前强制发完（用户场景就是没钱发）
2. 不许清库（2027 数据会跟 2026 混在一起，越积越多，正是要避免的）
3. 把欠款记成一笔「负数预支」（语义错乱，导出与报表都会歪）
4. 结转手工新增（只能由清库自动生成，避免伪造期初）

**已知未堵的缺口**（记为可接受）：
- `previewArchiveMerge` 不数结转 → 确认弹窗的数字不含结转条数；真合并按实时判重（与 D-016 同一取舍）
- `rangeFingerprint` 不含结转 id → 归档后往主库补一条结转不会被清库指纹拦住（结转不被清库删除，且合并有硬闸）
- `verifyArchive` 不比对 `counts.carryovers`（22 项契约所限）→ 档案库手工删一行结转行抓不到，只由编辑闸门 `assertManifestCountsMatch` 兜
- 第 18 项名字是「照片引用完整」，现在也数结转孤儿；契约锁死改不了名，只能在 `note` 里点明
- 档案查看页没有结转列表：带得走、合得回来，但「打开看」看不到包里那几条结转

**关联**：`docs/requirements/RQ-007-清库欠款结转.md`、`docs/plans/PL-004-sds.md`、`docs/decisions.md` D-027（清库三道闸门）、D-029（发放记账）。

## D-032 常规快照默认保留份数 7 → 3（迁移前快照仍为 2）

日期：2026-11-12

**决策**：`DEFAULTS.snapshotKeep` 从 **7** 改为 **3**。轮转的**两个池与两级上限的语义一个字不动**（组 A `auto`/`manual`/`pre-restore` 共用这个上限；组 B `pre-migrate` 仍按常量 `PRE_MIGRATE_KEEP = 2`，不占组 A 名额）。

**为什么**：

- 实测发现总份数不是用户填的那个数，而是「填的数 + 2」——因为迁移前快照单独成池。用户看到「我设了 7，磁盘上却有 9 份」，直接把设置理解错了（YG 2026-11-12 实机核对：`snapshots\` 里 7 份 manual + 2 份 pre-migrate）。
- 快照体积是**库整体的一份完整副本**：7 份常规 + 2 份迁移前 ≈ 库体积的 9 倍。小库无所谓，库一大（照片索引、几年考勤）就是纯冗余。
- 常规快照的真实用途是「防手滑」——最近几次退出/手动备份能退回去就够；真出事用的是「整库备份压缩包」（`RQ-008`）。把默认从 7 降到 3 是让默认值贴合用途，而不是削弱保护。

**不受影响 / 明确没改**：

1. **用户显式存过的值不受影响**：`settings` 表里已有 `snapshot_keep` 行的库继续按那个值轮转；只有没存过（或存过又被快照恢复回退掉）的库才吃这个新默认值。
2. **`PRE_MIGRATE_KEEP = 2` 不动**（D23 的理由仍然成立：`auto` 每次退出都拍一份，混池算会挤掉升级前的退路）。
3. 轮转分组、组内淘汰顺序、`keep` 的入参语义、`E_VALIDATION` 边界（`keep ≥ 1`）全部不变；测试里显式传 `rotateSnapshots(db, 7)` 的字面量属算法证据，**保留**。

**本条对既有文字的影响（只在此处注明，历史记录不改写）**：

|---|---|
| D-027「为什么」栏里「默认只留 7 份」 | 该数字已过期，以本条为准（那是当时的观测，不改写） |

## D-033 恢复快照后的设置归属：保留份数跟着回退，三项目录不回退

日期：2026-11-12

**背景**：快照 = 整个 `app.db` 的副本，而 `settings` 表就住在这个库里。所以 `restoreSnapshot` 换库之后，**设置整体回到那份快照的时点**。这条本身是既有行为，但 D-032 把默认保留份数从 7 降到 3 之后，它的后果第一次变得可见：用户把份数设成 7，恢复一份「早于这次保存」的旧快照 → 份数回退成默认 3 → 下一次退出按 3 轮转、**真删 4 份快照**，而且只有一行 `console` 日志、界面无任何提示。

同一机制下还有一个更严重的后果：**照片目录**（`photo_root`）如果在设置页改过（例如指到 `D:\照片`），恢复一份更早的快照后这个路径也会回退，重启后软件去旧路径找照片 → **照片全部显示缺失**。

**决策**（YG 2026-11-12 逐条选定，两条代价不同所以处理不同）：

1. **`snapshot_keep`：允许回退，照现状接受。**恢复旧快照后保留份数跟着回退，按回退后的值轮转。理由：代价只是少几份快照，可以接受；而且「恢复」的语义是回到那个时点，设置也是那个时点的一部分。
   - **本条追认 D-032 里那处曾被独立复核指为「擅自加入、未经需求方授权」的豁免**：现在它有明确的授权来源（本节）。
   - 连带要求（复核 C 条）：① 在 `docs/DELIVERY.md` 的恢复说明里写清这条；② **补测试钉住**这个行为（防以后被无意改掉，这是唯一会删用户文件的可逆点）。
2. **三项目录设置（`data_root` / `photo_root` / `inbox_dir`）：不回退。**恢复完成后，按**本机恢复前**的现状把这三行写回新库（恢复前该行不存在 → 写空串，即「用默认」，与既有「空串 = 未设置，回退默认值」口径一致）。
   - 理由：这三项是**本机属性**，不是数据内容。回退会让软件在**功能层面**坏掉（照片打不开），而不仅仅是不方便。
   - **既有先例**：档案合并时 `settings` **一律不并**，理由正是「全局口径属于本机，不随数据走」（D-016 第 2 条 / D-017 第 2 条）；数据目录迁移时也会把三个路径设置写进**新库副本**（`migrateDirs.ts#rewriteStagedDb`）。本条沿用同一哲学，不是新发明。
   - **范围严格限定**：本次只处理这三行路径。**数值型设置**（`standard_workday_minutes` / `overtime_unit_minutes` / `meal_allowance_default_cents`）**不纳入**，理由：它们错了只是「算得不一样」，界面上看得见、改得回来；路径错了是功能性故障。要扩大范围须单独立项。
3. **两个时点**：恢复前读出这三行的原值（含「无此行」→ 空串），恢复后写回。落点见工单 `docs/issues/IS-018-恢复快照后目录设置回退.md`。

**否决了什么**：

- **「恢复就该 100% 原样回退，什么设置都不许动」**：它会让用户在恢复之后立刻失去照片（功能性故障），而这正是他要靠恢复解决困境的时刻。→ 否决了「三项也回退」。
- **「保留份数也一起保留，不让它回退」**（即 U13 的选项①）：多一条「恢复不回退设置」的特例、多一层与 `snapshot_keep` 语义的张力，而收益只是保住几份快照。YG 选了接受回退。→ 否决。
- **把数值型设置一起纳入「不回退」**：属范围蔓延（反模式第 8 条「顺手重构」）。→ 否决，单独立项再说。

**已知代价 / 未堵的缺口**：

- `snapshot_keep` 回退仍会**静默删文件**（只剩一行日志）。本轮只做「写进交付说明 + 补测试钉住」，**不做界面提示**（YG 未选 U13 的选项③）。
- 本次只治「恢复快照」。**RQ-008 的「整库恢复」走的是另一条路**（换整个数据目录），它按 U5 的裁决把三项目录设置改写成本机生效数据根——两处口径一致，但实现是两套，不许互相调用。

**关联**：D-032（默认份数 7→3，本条追认其豁免）、D-016 / D-017（`settings` 属于本机）；`docs/issues/IS-018-恢复快照后目录设置回退.md`；`docs/requirements/RQ-008-整库备份与恢复.md` U5；`src/main/services/snapshot.ts#restoreSnapshot`。

**背景**：RQ-008 的「整库备份与恢复」要**读**用户给的 zip（备份包）。本仓运行期依赖里只有 `archiver`（只能压、不能解），此前**没有任何直接声明的解压库**。需求卡约束段要求：若必须引入，须是 `package.json` 里的**显式**依赖（不许直接 import 传递依赖），并记进本条。

|---|---|---|
| **A. 显式依赖 `unzipper`（选）** | 它本来就在 `node_modules`、lock 与**现成产物**里，改成显式依赖**不新增下载**；流式逐条读、支持 ZIP64 | **选** |
| B. 在 `services/` 内自写最小解压（store + deflate + ZIP64） | 只依赖 `node:zlib`、零新依赖；但 ZIP 解析的边界（数据描述符、ZIP64 EOCD、文件名编码、加密位、目录项与本地头不一致）要自己扛 | **否决**：这段代码的**失败面 = 用户唯一的备份读不出来**，是全仓最不该手写的一段 |

## D-035 整库恢复的四个关键取舍

日期：2026-11-12

**背景**：RQ-008 的「用整库包恢复」是**全仓唯一会真动用户数据的不可逆操作**（`closeDb` → 换整个数据目录 → 换库）。它与既有的「数据目录迁移」（`migrateDataRoot`）在形状上同族，但有三处必须自己拍的地方，外加一条 YG 中途改掉的口径。四条一起定，是因为它们互相约束：少定一条，实施的人就会照抄迁移那一路，而照抄必然错。

### 1. 与「目录迁移」共用同一把锁，不新造第三把

恢复与迁移共用**同一对模块级状态**：`migrating`（进行中，恢复时置成 `'restore'`）与 `pendingRestartRoot`（已换、等重启）。判定顺序固定为「先等重启、后迁移中」。于是四种交叉组合全部由既有判定覆盖：迁移中 → 恢复 `E_DB_LOCKED`；恢复中 → 迁移 `E_DB_LOCKED`；等重启 → 两者都拒；空闲 → 互不影响。

**备份**那一侧**不持这把锁**（它要跑几分钟，锁住全部写操作不可接受），它持一个**单飞标志**（同一时刻只允许一个备份）。这个标志**不参与任何写通道判定**，所以**不是第三把锁**——它只用来做 U18 的双向互斥（备份中 → 恢复拒；恢复中 → 备份拒）。

**否决了**「给恢复新造一把 `restoring` 锁」：多一个状态就多一组要与 `migrating` / `pendingRestart` 对齐的交叉判定，而收益为零——恢复与迁移本来就不可能同时进行（两者都要动数据根）。

### 2. **不改** `data-root.json` 指针

恢复**完全不碰** `%APPDATA%\xinmiao-attendance\data-root.json`。

理由：迁移必须写指针，是因为「下次启动去哪找库」**变了**；恢复的路径**没变**，只是那个目录里的内容被换掉了，`IpcPaths`（启动时算出的 `dataRoot`/`photoRoot`/`inboxDir`/`dbPath`）与指针目标都仍然有效。这条差异意味着**不要照抄 `migrateDataRoot` 的指针预写 / 提交 / 回滚三段**。

代价与不对称之处：`ATT_DATA_ROOT` 接管时，迁移**拒绝**（改了设置也不生效），恢复**必须放行**（验收 15 就是要在接管状态下恢复）。理由不对称，因为恢复根本不改「去哪里找库」，它只换内容。

### 3. 旧目录在「落位成功 + 重开新库 + 置等重启」之后**立刻删**

顺序写死：`closeDb`（第 17 步）→ 旧目录改名 `<根>._replaced_<时间戳>`（第 18 步）→ 暂存一次 `rename` 落位（第 19 步）→ `openDb` 打开新库并 `setDb` 接管（第 20 步）→ 置 `pendingRestart`（第 21 步）→ **删旧目录**（第 22 步）。

两个细节：① 删之前**必须先 `closeDb`**——旧 `app.db` 还开着时 Windows 上删不掉，这也是为什么顺序是「重开新库 → 置等重启 → 删旧目录」；② 删失败（外部占用 / 权限）**不改变恢复成功的结论**，只 warn + 在回执与日志里写清残留目录的绝对路径。

**否决了**「下次启动再清理」：要在 `userData` 多留一个待清理标记、动启动流程、多一次启动分支，收益只是「删不掉时自动重试」；而删不掉几乎总是因为用户自己开着里面的文件，那时报出路径比静默重试更清楚。

### 4. **正式包与退路包都包含 `snapshots\`**（U17b；推翻最初「只有退路包带快照」）

这是 YG 2026-11-12 中途改掉的口径，**必须写清前后两版**，否则下一个人会照旧版实现：

| 版本 | 口径 | 后果 |
|---|---|---|
| 最初（U17） | 只有**退路包**带 `snapshots\`，正式备份包不带（体积理由） | 用正式包恢复后，快照史**永久消失**；用户手里只剩一个退路包 |
| **现在（U17b）** | **正式包与退路包都带 `snapshots\`** | 恢复后**快照史跟着包回来**；`snapshots` 登记行**一条都不删** |

**因此 U14（「恢复后清空 `snapshots` 登记行」）作废**。恢复侧第 15 步改写暂存库时只剩两件事：① 三行路径设置写**空串**（回落本机启动解析根）；② 按包内 `archives/` 里实际存在的目录名重写 `archives.path`。**不删 `snapshots` 行**——删了就是「文件在、账上没有」，维护页会变成一片「未登记」。

代价：包会大一些（快照是库的副本，通常几 MB 到几十 MB）。**明确没改**：`thumbs\` 与 `inbox\` 里未吸入的照片**仍然不进包**（这两项按需重建 / 需自己另拷），所以「退回去」不等于「逐字节完整副本」，这句话在交付说明与恢复回执里各写一句。

**附带说明（实施侧不复用的两个既有函数）**：恢复侧的「改写暂存库」**不复用** `rewriteStagedDb`（它做的是另一套：按旧根改写快照与档案路径、且没有 DELETE，被迁移路径的测试钉着），也**不复用** `pathsPatchFor`（它的 `isSameDir(新根, join(新根,'photos'))` 在恢复场景恒 false，会把三行钉成本次临时根的绝对路径，下次不带环境变量启动就指向一个已删的目录）。两处都自己写，理由写在 `migrateDirs.ts` 的注释里。

## D-037 计算审计的五条处置：改备注不再改钱、清库不再丢钱、并入相加、删除门补结转、区间反了要报错

日期：2026-11-13

**背景**：YG「仔细核查所有和数据计算有关的，看有没有计算错误的地方。一切可以错，但考勤数据和算的钱不能错」。5 路只读审计 + 主会话自建可复现台架逐条真跑（台架在 `.tmp/audit-verify/`），结论：**核心算术没有错**（附录三人 21143.75 元逐格对上、BigInt 精确累加与三项各自取整、元↔分拒绝 `1.005` 这类静默改钱、乘式溢出边界、结余四项含冲销），但**找 5 处会让钱/工数与预期不符的地方**。完整审计与复现见 `docs/plans/AUDIT-001-计算实现审计-20261113.md`。

### 1. `updateEntry` / `overwriteEntry` 不再无条件重解「固化基线」（F1，YG 选方案 A）

**决策**：只有 `workerId` 或 `workDate` **真的变了**才重解 `std_minutes` / `overtime_unit_minutes`；身份没变时这两个值**沿用原记录**。`daily_wage_cents` / `meal_allowance_cents` **仍按 `rateAt(workerId, workDate)` 现取**（口径 9，不受影响）。落点 `repo/entries.ts#frozenForEdit`。

**为什么**：原写法（`PL-001-sds.md` 原 §接口 `:205`「基线按当前覆盖重解」）与**需求卡 RQ-001 口径 11** 直接冲突。实测后果：K=480 时录的「加班 120 分」记录（加班费 7500 分），把全局 K 改成 360 后，用户**只改一句备注**，加班费就变 10000 分（+25.00 元）——没有二次确认、没有快照、界面无提示。口径 11 明写「之后改设置只影响新记录……标准工日与加班折算仍按录入时固化，要改历史必须显式执行『按当前设置重算某区间』（二次确认 + 先自动快照）」。

**否决了什么**：
1. **保留 SDS 行为、补二次确认 + 快照**：改一句备注就弹「要不要按当前口径重算这条」，等于把内部实现细节变成用户的负担；而且用户点「确定」就等于改了历史金额，那不是他要的。
2. **一律不重解（连换工人也不重解）**：换到另一个工人后，K 会与该工人的口径覆盖不一致，反而产生新的错账。

**边界（写清以免以后争）**：`siteId` / 时段 / 加班 / 工时 / 备注 / 照片变了都**不**重解基线——它们不改变「这条记录属于谁的哪一天」。

### 2. 清库闸门的 `asOf` 改取 `max(本地今天, 区间末端)`（F2）

**决策**：`services/archive.ts#purgeArchiveRange` 调 `periodNetForRange` 时传 `asOf = to > todayIso() ? to : undefined`。`periodNetForRange` 的**签名与默认值一个字没动**——默认「今天」是**结余侧**的口径，是对的。

**为什么**：清库按 `[from, to]` **整段删**（不看今天），但期间净额当时只算 `work_date <= 今天`。实测：区间 `2026-01-01~2026-12-31` 里两条记录（11-03 与 12-20，各 300 元）→ **工资表看到 600 元、闸门只看到 300 元**，两条都删、只结转 300 → **300 元凭空消失**。反向同理：一笔未来日期的发放不计入「期间已发」→ 结转偏大。

**代价（必须记住）**：改完之后，若清库区间**延伸到今天之后**，清库完成那一刻「还欠多少」会**变大**，增大量 = 未来那段的净额（实测 31500 → 63000）。因为结转是存量、不受 `asOf` 约束，而那部分钱从「还没到期的应发」变成了「已确定的结转」。**「清库前后结余不变」只在 `区间末端 ≤ 今天` 时成立。**宁可余额变大，也不能让钱消失。

**否决了什么**：
1. **拒绝「区间末端 > 今天」的清库**（一行判定）：能同时消除副作用，但会挡住「年内提前清库」这种用法，属于产品取舍，YG 未选。**这条随时可以补，是本次留下的第一个候选后续。**
2. **让结转也带日期**：那要给 `carryovers` 加列 + 改结余公式 + 改档案判重键，量级完全不同。
3. **清库时只删 `≤ 今天` 的部分**：会让档案（按 `[from,to]` 建）与实际清掉的范围不一致，闸门② 的「id 集合 ⊆ 档案」也会跟着说不清。

### 3. 并入两条「按小时」记录时，工时**相加**（F3，YG 选方案 A）

**决策**：`repo/entries.ts#applyMerge` 的 `hours_minutes` 从 `Math.max(kept, incoming)` 改为 `kept + incoming`，并补「相加后 > 1440 → `E_VALIDATION`」的拦截（与同函数的加班上限同形状、同语气）。落点 `entries.ts`，SDS 变更记录同步。

**为什么**：同一函数里「加班相加、工时取大」是两套语义，且需求卡没规定并入的工数算法。实测已有 120 分再并 240 分 → 只留 240，丢 0.22 工 ≈ 66.67 元。**注意 `AM + AM` 并入保持 0.5 工是对的**（同一上午不能重复计），矛盾只在 `HOURS`。

### 4. 删除工人的「历史」多一类：上期结转（F4）

**决策**：`repo/workers.ts#countWorkerRefs` 加 `carryoverCount`；`workerDeleteGate` 的文案顺序固定为「考勤 → 预支 → 发放 → **结转**」；`renderer/src/api.ts` 的手抄镜像同批补字段；`listWorkers` 的标量子查询按「表在不在」动态拼（老库退化成 0）。

### 1. 备注截断会把 emoji 切成半个（**会静默改字**，P2 挖出、主会话复现）

**缺陷**：`joinNotes` 用 `joined.slice(0, MAX_NOTE)` 按 **UTF-16 码元**截断。`'😀'.length === 2`，切口落在两个代理之间时，落库后那半个字符变成 **U+FFFD（替换字符）**——用户备注被静默改字，还不报错。实测：kept 备注 `'a'` + incoming `'b'.repeat(497) + '😀' + 'c'` → 截断后 `U+FFFD = 1`、末位码元 `0xfffd`。

**修法**：`repo/validate.ts` 新增 `truncateText(value, limit)`——按码元截断后检查末位是否为孤立高位代理（`0xD800–0xDBFF`），是就退一格。**5 处同型代码全部改走它**（`entries.ts#joinNotes`、`advances.ts` / `payments.ts` / `carryovers.ts` 的冲销备注、`archive.ts` 的自动冲销备注），全仓 `slice(0, MAX_NOTE)` 零残留。

**代价（明确接受）**：截断结果可能比上限少 1 个码元。丢掉半个字符是对的，留半个字是错的。

**反证**：修前 `U+FFFD=1`（红）→ 修后 `0`、长度 499（绿）。回归用例：`entries.test.ts` 的「并入备注截断不切坏代理对」。

**否决了什么**：「按码点截断（`Array.from`）」——会改变 `MAX_NOTE` 的计量单位（`validate.ts` 用 `text.length` 校验，是码元），两套口径并存比现在更容易出错。现在只多退一格，计量单位不变。

### 2. 预支明细的备注列不截断（同族不一致）

`export/xlsx.ts#writeAdvanceDetailSheet` 直接写 `note: row.note`，而同族三处（工资表明细 / 日历明细 / 发放明细）都走 `noteCellText`。后果：同一条 250 字备注，发放导出读回 201 字（带 `…`）、预支导出读回 250 字。**修法**：改成 `noteCellText(row.note)`。
