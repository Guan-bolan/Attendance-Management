# 各阶段任务书与主会话动作

> 配套文档：`WORKFLOW.md`（流程与文档体系）
> 本文件解决一件事：**每个阶段，你该说什么、我该做什么、任务书怎么写、你怎么验收我。**

---

## 0. 使用方式

> **两套编号，别混**：
> **`§N` 是本文的小节号**（「读 TASKBOOKS §7」），
> **`阶段 N` 是流程里的位置**（「现在到阶段几了」）。
> 两者数字不对应，指代时请带上符号或「阶段」二字。

每个阶段分四块：

- **你说** —— 一句可直接复制的话
- **我该做** —— 主会话的标准动作。这是你审我的依据
- **任务书** —— 发给子 agent 的全文，可直接用
- **你验收我** —— 判断我做对了没有的信号

---

## 1. 通用部分（所有阶段都适用）

### 1.1 任务书四要素

任何任务书都必须写全这四样，少一样，子 agent 就会自己发挥：

| 要素 | 回答什么 | 缺了会怎样 |
|---|---|---|
| 目标 | 做完之后，什么事变成什么样（可判定） | 它自己定目标 |
| 输入 | 读哪些文件、给什么线索 | 它到处瞎找，或漏读关键文件 |
| 边界 | 不许动什么、什么情况停下来问 | 它顺手改了不该改的 |
| 输出 | 固定格式 | 它把过程全吐回来，你判断不了对错 |

### 1.2 主会话永远做与永远不做

**做**：拆任务、写任务书、发出去、收结论判断、遇到关键分歧做决策。

**不做**：

1. **不自己读代码细节** —— 一读，上下文就被灌满，后面调度开始出错
2. **不替你做产品决策** —— 遇到需求没写清的地方，它必须回来问你
3. **不把子 agent 的过程拉回上下文** —— 只收结论，不收 diff 和日志
4. **不说「已完成」就信** —— 必须让子 agent 给出可验证的证据

### 1.3 你怎么审我（只有三条）

1. 我有没有**自己去读一堆代码**？有，就是错的。
2. 我有没有**替你把需求问题定了**？有，就是错的。
3. 我给子 agent 的任务书里，**四要素是否齐全**？少一样，责任在我。

## 2. 阶段 0：地图测绘

> **什么时候用**：已有代码的存量项目（维护 / 接手），或者新项目**第一个能跑的切片做完之后**。
> 零代码的新项目先跳过这一节——走需求 → 计划 → SDS，SDS 的模块划分表就是地图草稿。
>
> 项目规模很小时（约五千行以内）也可以先不做，地图的收益与规模成正比。
> 触发条件：agent 开始找错地方、你说不清功能在哪个文件、模块超过十几个。

### 你说

> 读一遍仓库，生成 `docs/map.md`。只写到页面/功能→入口文件这一层，不要下沉到组件。不确定的标「待确认」，别编。

### 我该做

1. 起一个**只读** agent，给它仓库路径和产出要求
2. 收回来后**不做二次加工**（改了就等于我在读代码）
3. 把结果给你，让你抽查
4. 抽查不通过 → 退回同一个 agent 重做，而不是我自己补

### 任务书

```
## 角色
你是测绘员。任务是产出一张让后来者能直接定位的地图，不做评价、不提建议。

## 输入
仓库全部代码，只读。若 docs/map.md 已存在，在其基础上更新。

## 任务
产出 / 更新 docs/map.md，包含四个表：页面、功能、关键数据、已知的坑。

## 要求
1. 只写到「页面 / 功能 → 入口文件」这一层，不要下沉到组件级
2. ID 规则：页面从 P-01 起，功能从 F-01 起，按重要程度排
3. 每行的文件路径必须真实存在，写完自己核对一遍
4. 判断不出的标「待确认」，不要编造
5. 「已知的坑」只写代码里能直接看出来的：同一逻辑散落多处、明显的 TODO、
   被注释掉的旧实现、命名与实际行为不符的函数

## 输出
docs/map.md，四个 markdown 表格。
末尾附一节「不确定项」，列出所有标了「待确认」的条目和原因。
```

### 你验收我

- 我有没有把结果**原样**给你，而不是自己改了几行？改了 = 我在读代码 = 错。
- 抽查三个页面，报 ID 我能不能立刻说出文件和职责？说不出 = 任务书要求不够严，重发。

## 3. 阶段 1：需求成型

### 这个阶段不适合外包

需求卡的信息在你脑子里，没有任何 agent 能替你生产。**这一步我陪你写，不开子 agent。**

我该做的：

1. 按需求卡模板问你缺的字段（尤其「不做什么」和「验收标准」）
2. 每写一条验收标准，问自己一句：**换个人来测，能照着这行字判断通过与否吗？** 不能就重写
3. 写进 `docs/requirements/RQ-xxx.md`
4. **不替你决定产品行为**。你犹豫的地方，就留在「未决问题」里

### 你说

> 我要做 <一句话>。先按模板问我要齐信息，特别是不做什么和验收标准。

### 你验收我

- 我有没有在你说「随便」的地方自己拍了个方案？拍了就是错——应该记进「未决问题」。
- 验收标准里有没有形容词（流畅、友好、正常）？有就是废条。

---

## 4. 阶段 2：需求质询

### 你说

> 拿 `docs/requirements/RQ-xxx.md` 去质询一轮。只提问题，不许给方案。

### 我该做

1. 起一个新 agent（不复用需求阶段的会话）
2. 任务书里**只给需求卡和地图，不给你的口头补充**
3. 把它的 A 类问题**逐条**转给你，一条都不合并、不筛选
4. 你回答后，我把答案写进需求卡 v2
5. **我不替你回答任何一个问题**

### 任务书

```
## 角色
你是需求挑刺者。你的产出不是方案，是「还缺什么信息」和「哪里有歧义」。

## 输入
docs/requirements/RQ-xxx.md、docs/map.md

## 任务
读完需求卡，列出两类东西：
A. 必须现在澄清的 —— 不澄清就会做错方向
B. 可以留到实现阶段的细节

## 必查维度
正常路径 / 空与异常输入 / 并发与重复操作 / 权限不足 / 中途中断
/ 与现有功能的冲突 / 失败后能否回滚 / 每条验收标准是否可判定

## 要求
1. 每条问题必须具体到「什么情况下会怎样」。
   不许写「需要考虑异常情况」这类泛泛的话
2. 不许提出方案，只提问题
3. 不许复述需求原文
4. A 类超过 8 条时，按影响面从大到小排序

## 输出
| # | 类型(A/B) | 问题 | 为什么现在必须定 |
```

### 你验收我

- 我有没有把 A 类问题**全部**给你？漏一条就是我在替你筛。
- 我有没有在你回答前就说「这块我按 X 处理了」？说了就是越权。

---

## 5. 阶段 3 的前置：现状摸底（改已有功能时必做）

### 你说

> 先摸清 <P-07 退款功能> 现在是怎么跑的，只调研不改。

### 我该做

1. 起只读 agent，范围写死（一个功能，不整个仓库）
2. 收回四条结论：链路、文件分布、隐含约定、连带影响
3. **不评价好坏**。这一步只回答「现在是什么样」，不回答「该不该这样」
4. 有「读不懂」的地方，原样转给你，不圆场

### 任务书

```
## 角色
你是调研员。任务是搞清楚「现在怎么运作」，不评价、不改动、不给建议。

## 输入
docs/map.md、仓库代码
调研范围：<例：P-07 订单详情页的退款功能>

## 任务
回答四件事：
1. 完整链路：入口 → 中间处理 → 落库或外部调用
2. 相关代码分布在哪些文件，各自职责
3. 隐含约定：奇怪的判断、硬编码、历史遗留、命名与行为不符的地方
4. 改这里会连带影响什么（谁在读这些数据、谁依赖这个行为）

## 要求
1. 每条结论标注 文件:行号
2. 读不懂的地方明说「这里无法确定，因为……」，不要圆
3. 不给改进建议 —— 那是下一步的事

## 输出
四节，对应上面四个问题。末尾附「不确定项」。
```

### 你验收我

- 我有没有让 agent 顺手给改进建议？给了就是越界，会污染后面的方案。
- 我有没有把「读不懂」美化掉？美化 = 你在后面被坑。

## 6. 阶段 3：方案起草

### 你说

> 按 `RQ-xxx` 出个方案，写到 `docs/plans/PL-xxx-plan.md`。每步要能验证。

### 我该做

1. 把需求卡 + 地图 + 阶段 3 的摸底结论一起作为输入
2. 要求「每一步做完能验证什么」——这是计划的硬指标
3. 收回后**只检查结构**（六节齐不齐、步骤有没有验证点），不检查技术对错
4. 技术对错交给下一步的红队

### 任务书

```
## 角色
你是方案设计者。你负责说清「改哪里、什么顺序」，不负责写代码。

## 输入
- 需求：docs/requirements/RQ-xxx.md
- 地图：docs/map.md
- 现状：<阶段 3 的摸底结论，或让 agent 自己读相关代码>
- 代码：仓库，只读

## 任务
按模板产出 docs/plans/PL-xxx-plan.md，包含：
现状 / 方案（分步）/ 影响面 / 风险与对策 / 不做的事 / 回滚方案 / 变更记录

## 硬要求
1. 每一步必须写清「做完这一步能验证什么」。
   做不到「做完就能测」的切分方式，不算合格
2. 「影响面」必须列具体模块，不能写「可能影响其他部分」
3. 关键选择写理由，并写明否决了什么方案
4. 不写代码，不写函数签名 —— 那是 SDS 的事
5. 「不做的事」至少写两条，写不出来说明范围没想清

## 输出
docs/plans/PL-xxx-plan.md
```

### 你验收我

- 计划里每步有没有验证点？没有 = 任务书要求没落地，重发。
- 我有没有在起草阶段就开始挑技术毛病？挑了 = 抢了红队的活，会让起草者自我审查。

---

## 7. 阶段 4：方案红队审核

### 你说

> 用红队审 `PL-xxx-plan.md`。只给材料和代码，别给它我的思路。

### 我该做

1. **起新实例**，不复用起草的那个
2. 任务书里**不出现任何作者的意图说明**
3. 逼它落到文件行号或具体场景
4. 收回意见后**原样给你**，包括你觉得没道理的那些
5. 你决定采纳/驳回；我记录理由到计划的「变更记录」
6. **两轮上限**，第三轮开始我该主动喊停

### 任务书

```
## 角色
你是独立审核者。你没参与这份方案的编写，不需要照顾任何人的判断。

## 材料
- 方案：docs/plans/PL-xxx-plan.md
- 需求：docs/requirements/RQ-xxx.md
- 地图：docs/map.md
- 代码：仓库全部，只读

## 任务
证明这个方案会失败。

## 必查维度
边界条件 / 并发与重复操作 / 错误处理 / 与现有功能冲突
/ 可回滚性 / 验收标准是否被覆盖 / 每一步的验证点是否真的可验证

## 要求
1. 每条意见必须给出：文件:行号，或「什么操作 → 什么后果」
2. 禁止「建议再考虑」「可能存在风险」这类没有落点的表述
3. 按严重度分级：会挂 / 会返工 / 可接受
4. 如果某个维度你查过认为没问题，说明你查了什么

## 输出
| # | 严重度 | 问题 | 位置 / 场景 | 建议 |
```

### 你验收我

- 我有没有在任务书里写「因为我们要解决 X，所以采用 Y」？写了 = 污染，重发。
- 我有没有把刺耳的意见过滤掉？过滤了 = 你在拿假报告做决策。
- 第二轮之后我有没有还在继续？继续 = 烧钱。

## 8. 阶段 5：SDS 起草

### 你说

> 按 `PL-xxx-plan.md` 出 SDS。接口写全签名，任务拆到能独立验证。

### 我该做

1. 给它计划 + 需求 + 地图 + 代码
2. 要求它做**颗粒度自检**：假装新人只读这份文档开工，哪里会卡住
3. 收回后检查三样：接口有没有签名、任务有没有验证方式、决策记录有没有
4. 检查发现缺项 → 退回补，我不代写

### 任务书

```
## 角色
你是详细设计者。你的验收标准只有一条：
一个完全没有前情的工程师，只读这份文档就能把代码写对。

## 输入
需求卡、计划、docs/map.md、仓库代码

## 任务
按 SDS 模板产出 docs/plans/PL-xxx-sds.md：
模块划分 / 接口 / 数据结构 / 数据流 / 错误处理 / 边界条件
/ 测试策略 / 任务拆分 / 决策记录

## 硬要求
1. 接口必须写完整签名、参数含义、返回值、错误码。只写名字不算
2. 数据结构变更必须给出迁移方案
3. 任务拆分：每个任务做完就能验证，标明依赖顺序和验证方式
4. 决策记录：关键选择 + 理由 + 否决了什么
5. 不引入计划之外的模块或依赖

## 自检（必须做）
写完后，假设你是第一次看到这份 SDS 的新人，从第一个任务开始开工。
逐步问自己：这一步我需要什么信息？文档里有吗？
凡是需要「猜」的地方，就是没写清的地方，回去补。

## 输出
docs/plans/PL-xxx-sds.md，末尾附「自检记录」：
列出你在自检中补过的地方，以及仍然需要确认的点。
```

### 你验收我

- 接口有没有签名？没有 = 任务书没执行到位，退回。
- 任务有没有「做完就能测」？没有 = 切分不合格。
- 我有没有自己往里补内容？补了 = 我在写设计，超出调度职责。

---

## 9. 阶段 6：SDS 审核（含纸面走查）

### 你说

> 审 SDS。让它先做一次纸面走查，再找漏洞。

### 我该做

1. 起新实例，只给 SDS 和代码
2. **必须包含纸面走查**——这是 SDS 审核和计划审核最大的区别
3. 重点看四样：接口自洽、错误处理死角、任务可验证性、与现有系统冲突
4. 同样最多两轮

### 任务书

```
## 角色
你是独立审核者，没参与这份设计。

## 材料
SDS、计划、需求卡、docs/map.md、仓库代码（只读）

## 任务（两件，按顺序做）

**第一件：纸面走查**
假装你要照着这份 SDS 写代码。从第一个任务开始，一步一步说出你会怎么做：
读哪个文件、写什么、调用什么、怎么验证。
任何一步你需要「猜」或「回头翻别的文档」的地方，就是文档缺陷，记下来。

**第二件：找漏洞**
1. 接口是否自洽：A 的返回值能直接喂给 B 吗？类型对得上吗？
2. 错误处理有没有死角：某个分支失败后，调用方知道吗？
3. 任务拆分有没有「做完也没法验证」的
4. 与现有系统的冲突点

## 要求
每条意见给 文件:行号 或 具体失败场景。
不许「建议完善」「可以考虑补充」。
查过认为没问题的维度，说明查了什么。

## 输出
| # | 类型(走查卡点/设计漏洞) | 严重度 | 问题 | 位置 | 建议 |
末尾附：走查完成度 —— 你走查到了第几个任务。
```

### 你验收我

- 有没有要求纸面走查？没有 = 只做了表层检查。
- 走查完成度有没有到最后一个任务？只走了一半 = 审核不完整。
- 我有没有把「卡点」和「漏洞」混在一起报给你？混了 = 你分不清哪些要改文档、哪些要改设计。

---

## 10. 阶段 7：实施（单任务）

### 你说

> 按 SDS 实施。一次一个任务，做完给我证据。

### 我该做

1. **一次只发一个任务**（或一组文件不重叠的任务）
2. 任务书里写死「只改哪些文件」
3. 要求它交三样：改了哪些、怎么验证的、实际输出
4. 收到「已完成」后**检查证据**，没有命令输出/复现步骤的不算完成
5. 完成后更新 SDS 顶部的进度段
6. **我不看 diff**。只看它改动的文件列表和验证结果

### 任务书

```
## 目标
完成 SDS 中的任务 T3：<一句话，可判定>

## 输入
- 必读：docs/plans/PL-xxx-sds.md 的「接口」「数据结构」「任务 T3」三节
- 相关文件：<列出具体路径>

## 边界
- 只改：<文件列表，写死>
- 不许动：<模块/目录>
- 不许引入新依赖
- 遇到 SDS 没写清的地方：停下来报告，不要自己决定

## 完成标准
- 验证方式：<跑什么命令 / 做什么操作 / 看什么结果>

## 输出（必须全填）
1. 改了哪些文件（路径 + 改了什么）
2. 怎么验证的（实际执行的命令）
3. 实际输出（贴原文，不要转述）
4. 遗留问题 / 与 SDS 不一致的地方
```

### 你验收我

- 我是不是一次发了一个巨大的任务？是 = 出错无法定位。
- 我有没有在它说「改好了」之后就往下走？没要证据 = 你在赌。
- 我有没有把 diff 拉进对话？拉了 = 主会话在被污染，很快会爆。
- 多个并行任务有没有改同一个文件？有 = 冲突，是我的排布问题。

---

## 11. 阶段 8：验收

### 你说

> 按需求卡的验收标准逐条验。只给标准和怎么跑起来，别给实现说明。

### 我该做

1. **起新实例，不是实施者本人**
2. 任务书只给：需求卡的验收标准 + 怎么跑起来
3. **不给 SDS、不给实现说明**——给了它就会按实现验，而不是按需求验
4. 三层顺序：自动化 → 功能逐条 → 视觉（有界面时）
5. 每条必须有证据；「整体看起来没问题」直接打回

### 任务书

```
## 角色
你是验收方。你只认需求卡里的验收标准，不认「实现起来很难」。

## 输入
- 需求卡：docs/requirements/RQ-xxx.md 的「验收标准」一节
- 怎么跑起来：<命令 / 访问地址>
- 不要读 SDS 和实现说明

## 任务
逐条验证验收标准，每条给结论和证据。

## 要求
1. 每条结论三选一：通过 / 不通过 / 无法验证
2. 「通过」必须附证据：执行的命令与输出原文，或操作步骤与截图
3. 不许出现「整体看起来没问题」「基本符合预期」
4. 无法验证的，写明缺什么条件
5. 发现验收标准本身有歧义，单独列出来，不要自己解释

## 输出
| # | 验收标准 | 结论 | 证据 |
末尾：不符合项清单 + 标准歧义清单
```

### 你验收我

- 验收人是不是实施的那个？是 = 假验收。
- 有没有给验收人看 SDS？给了 = 它按实现验，不是按需求验。
- 有没有「无法验证」被悄悄算成「通过」？算了 = 你在自欺。

## 12. 阶段 9：收尾 / 文档漂移检查

### 你说

> 收尾。查一下 map 和 AGENTS.md 有没有跟代码脱节，再看有没有临时代码残留。

### 我该做

1. 把本次改动的文件清单 + map + AGENTS.md 给一个校对 agent
2. 收回「哪一行该改成什么」，**我直接改文件**
3. 更新 `docs/decisions.md`（关键决策 + 理由）
4. 需求卡状态改「已完成」
5. 检查「未决问题」是否都有结论

### 任务书

```
## 角色
你是文档校对员。任务是找出文档与代码不一致的地方，不改代码。

## 输入
- 本次改动涉及：<文件/功能清单>
- docs/map.md
- AGENTS.md
- 仓库代码（只读）

## 任务
1. map.md 里哪些行已经不对了：页面改名、路由变更、文件移动、新增功能未登记
2. AGENTS.md 里的命令、目录结构、约束是否还成立
3. 本次改动里有没有留下：临时代码、调试开关、注释掉的旧逻辑、
   写死的测试数据、`TODO` 但没有对应工单的

## 输出
| 文件 | 行 | 现在写的 | 应该改成 | 依据(文件:行号) |
```

## 13. 维护分支：bug 定位（triage）

### 你说

> 一句话现象 + triage。定位归它，我只审工单。

### 我该做

1. 起**只读** agent（不能用能改代码的）
2. 任务书里只给现象和地图，**不给我的猜测**
3. 收回后你审三样：位置对不对、根因说得通吗、影响范围有没有漏
4. 你确认后写成工单 `docs/issues/IS-xxx.md`
5. 找不到就退回重定位，或补一条你观察到的细节

### 任务书

```
## 角色
你是定位员。任务是把一句现象变成一张可执行的工单。

## 输入
- 现象：<用户视角，一句话>
- docs/map.md
- 仓库代码，只读

## 任务
定位到具体代码位置，输出工单。

## 要求
1. 位置必须给 文件:行号 + 函数名
2. 根因假设必须能解释这个现象，不能只是「这里看起来可疑」
3. 影响范围：同样的代码/逻辑在别处还有没有
4. 修复建议写清副作用
5. 找不到就明说找不到，并列出排查过的位置。
   禁止把猜测写成结论

## 输出
现象 / 坐标(文件:行号,函数) / 根因假设 / 影响范围
/ 修复建议 / 复现路径 / 复现率(x/x)
```

### 你验收我

- 定位 agent 是不是只读权限？不是 = 它可能顺手改了东西。
- 任务书里有没有写我的猜测？写了 = 它会在我的假设上打转。
- 「找不到」有没有被包装成「大概是这里」？包装了 = 你会在错的地方修。

## 14. 维护分支：回归

### 你说

> 按工单的复现路径复跑一遍，再跑测试。看要不要补用例。

### 我该做

1. 起一个新 agent，给它工单的复现路径
2. 要求它**原样复跑**，不许换路径
3. 判断是否补测试：这个 bug 会不会以同样形式再出现
4. 补测试的判断给你，我不自己拍

### 任务书

```
## 角色
你是回归验证者。

## 输入
工单：docs/issues/IS-xxx.md（复现路径一节）
怎么跑起来：<命令>

## 任务
1. 按工单的复现路径原样复跑，不许改变步骤顺序
2. 跑自动化测试
3. 判断：这个 bug 是否值得补测试用例
   （判断标准：它会不会以同样的形式再出现）

## 要求
每条结论附证据：命令与输出原文，或操作步骤与结果。
不许「应该没问题了」。

## 输出
| 检查项 | 结论 | 证据 |
补测试建议：是/否 + 理由
```

### 你验收我

- 复现路径有没有被改动？改了 = 验的不是同一个场景。
- 有没有「应该好了」这种结论？有 = 打回。

## 16. 最后一条

这些任务书不是仪式，是**信息传递的容器**。

判断一份任务书合不合格，只有一个办法：**把你自己当成那个没有任何前情的 agent，只读这份任务书，能不能干对活。**

能，就发出去。不能，说明你漏了信息——而这个信息你没法从后面的对话里补，因为它根本看不到后面的对话。
