## 已知的坑

- **汇总页只有一个滚动区**：`Summary` 根节点是 `flex` 列（工具条固定 / 内容区 `overflow-y:auto` / 底部合计固定），`Layout.Content` 在汇总页被设成 flex 容器。别加回页面级滚动，否则会出现两层滚动条（RQ-004 v4）。
- **日历浮窗点开图片用 `ImageViewer`**，与照片池「点开原图」是同一个组件；「用系统看图打开」只收 `photoId`，主进程校验 `resolveInside` 后才 `shell.openPath`，**不接受任意路径**。
- **数据目录迁移是单向的、且启动依赖指针文件**：`settings.data_root` 只影响本进程内的子目录解析；**下次启动去哪找库由 `userData\data-root.json` 决定**。改这块要同时看 `services/paths.ts#resolveDataRootForBoot` 与 `main/index.ts#resolveBootPaths`（RQ-003 / D4 / D-022）。
- **迁移成功后会锁住所有写操作直到重启**：`pendingRestart` 置位后，非只读通道一律 `E_DB_LOCKED`。写保护是**只读白名单**（不在名单里就拒），新增通道默认受保护——不要改回写白名单。
- **迁移临时目录建在目标同级**（`<目标名>._migrating_<时间戳>`），最后一次 `renameSync` 原子落位；失败只删临时目录，目标一个字节没动。
- **整库恢复是「整目录替换」，不是「换个库」**（RQ-008 U4 / PL-005）：包里没有的旧东西**一律不要**——旧快照史、`thumbs\`、`inbox\` 里未吸入的照片、数据根下的杂项文件，恢复完统统不存在。所以恢复前想留什么，自己先拷出去；这也是为什么「立即备份」默认落在数据根**外面**。
- **退路包也带 `snapshots\`，所以恢复后快照史跟着包回来，别再说「清空」**（U17b，YG 2026-11-12 改口径；原 U14「恢复后清空快照登记行」**已作废**）。第 15 步改写暂存库时**一条 `snapshots` 行都不删**——删了就是「文件在、账上没有」，维护页会变成一片「未登记」。这条同时改掉了早期文档里「快照历史已清空」的所有说法。
- **`archives.path` 会被改写，但只改「随包走」的那些**：恢复时按**包内 `archives/` 里实际存在的目录名**重写成 `<本机数据根>\archives\<目录名>`；**未随包走**的档案（原机把它指到 `D:\档案` 之类）**保持原值不动、也不删行**——那是「这份档案本该在哪」的唯一线索。后果：档案柜会提示「目录不存在」，要**手工把档案拷回、再用「重指路径」指过去**；**未重指前不能清库、不能合并档案**（`verifyArchive` 会抛 `E_NOT_FOUND`，清库闸门自己会拒，不会误删主库）。
- **恢复期间不要关窗口**：窗口 `close` 与 `before-quit` 都拦（`main/index.ts`），`snapshotOnQuit` 在「恢复中」与「等重启且 kind = restore」时直接返回。不拦的后果是裸杀落位窗口（数据根不存在）＋退出快照给库拍一份并轮转删文件（「恢复后数据 = 包内内容」当场不成立）。**不提供强制退出口**：落位前有取消检查点，落位后只能等它跑完。
- **档案包里的库文件是 `data.db`，不是 `app.db`**（`archive.ts#ARCHIVE_DB`；`backupPack.ts` 用 `ARCHIVE_DB_FILENAME = 'data.db'` 对齐，两处同值靠注释 + 单测钉住）。S4 曾把它判成 `app.db`，后果是「只要库里有一份档案，备份就必失败」——而**测试夹具犯了同一个错，所以当时全绿是假绿**。**规矩：任何涉及档案包结构的代码，库文件名一律 `data.db`；写夹具时按真实现场造（真档案目录里没有 `app.db`）。**
- **`archiver` 打出来的包，条目顺序不可控**（PL-005 S4 实测：同输入 12 次出现 9 种顺序）。所以「manifest 最后写」**不能**靠条目顺序兜底，真正的防线是**写完立刻自校验、不过就删包**（退路包就是这么做的：回读列清单 → 条目数与两组条数对不上 → 删 `.part` 中止）。别在测试或代码里对条目顺序下断言。
- **照片迁移遇到同名不同 hash 会中止，不覆盖**——防止误指到另一套照片库毁掉别人的文件（D7）。
- **归档会删主库数据**：`purgeArchiveRange` 前必须重算区间指纹与 manifest 比对、必须留清库前快照、必须守住跨区间照片。改这块先读 `docs/decisions.md` D-015。
- **档案内编辑会破坏清库守卫**：S8b 若允许在档案里删照片或删记录，「档案里有副本才删主库」就会退化成「删掉唯一副本」。现已限定只能改备注/加班/出勤，禁止增删。
- **清库三道闸门顺序固定，且「清没清库」只认 `archives.status`**（PL-004 T12）：② 主库该区间 id 集合 ⊆ 档案（**含发放**，缺一笔就拒）→ ③ 副本必须比主库新（先比区间指纹，再比**照片位漂移** `countSlotDrift`；老档案无 `slot` 列时只能如实回 `slotChecked:false`，不伪装成「比过了」）→ ① 期间净额「显示 + 勾选确认 + 清单写进 `manifest.clearance`」。`dryRun` 也把三闸全跑一遍且**零写入**。**别拿 `manifest.clearance.purgeState` 判断清没清库** —— 它只记「凭据写到了哪一步」（`pending` 可能是算过账但没删，也可能是删完收口写失败），唯一判据是 `archives.status`（`created` / `purged`）。改这块先读 `docs/decisions.md` D-027。
